# 개발 아키텍처와 서비스 경계

이 문서는 개발할 서비스의 구조와 경계를 설명한다. 로컬 실행과 공용 배포 기반은 준비돼 있으며 업무 기능은 각 Jira 티켓에서 구현한다. 현재 실행 범위는 [공통 온보딩](team-start.md), 배포 절차는 [서비스별 배포 안내](service-delivery.md)를 따른다.

## 개발 및 공용 시연 환경

각 팀원은 로컬에서 기능을 개발하고 테스트한다. 검토한 변경을 교육장 GCP 프로젝트의 공용 시연 환경 한 세트에 배포해 통합 테스트와 발표 시연에 사용한다. 이 한 세트 안에 C/S, TFT, 플랫폼의 독립 서비스와 Cloud SQL 인스턴스 1개 및 PostgreSQL DB 1개, 파일 저장소와 비동기 실행 구성을 둔다.

공용 시연 환경은 `environment=production`으로 실행하고 실제 Microsoft 로그인과 권한 검사를 적용한다. 개발용 계정 선택은 로컬 개발 환경에서 사용하며 공용 시연 환경에서는 차단한다. production 설정은 인증 및 실행 정책이며 발표 후 운영을 계속한다는 뜻은 아니다. 시연 인력과 업무 자료의 가상 데이터 표시는 유지한다.

배포 대상은 확인한 교육장 프로젝트 `proj-skkuls0106-183255377938`다. CLI의 기본 프로젝트 설정만으로 다른 대상을 선택하지 않으며 리소스 명령에는 해당 프로젝트를 명시한다. 별도 클라우드 개발 및 스테이징 환경을 추가하지 않고 공용 배포 한 세트로 관리한다.

## 공통 API 독립 배포

사용자 결정으로 공통 API를 독립 서비스에 배포한다. 공통 로직과 테이블의 소유자는 플랫폼 모듈이다. C/S와 TFT는 계약된 내부 API로 메일, 파일, 평가 요청을 전달한다. 공통 인증 검사는 공유 패키지와 제한된 인증 조회를 사용한다. API 요청 검증을 공유한다는 이유로 OAuth 토큰 갱신과 메일 동기화도 각 앱에서 중복 실행하지 않는다.

평가 API는 실행 설정 등록, 실행 요청, 결과 조회를 담당한다. 실제 평가는 Cloud Run Jobs에서 수행한다. 무거운 평가가 C/S API 프로세스에서 실행되지 않는다.

세 서비스는 배포와 재시작 주기가 독립적이다. 공통 API가 중단되면 C/S와 TFT의 해당 기능도 영향을 받지만 C/S 업무 앱의 배포가 공통 API의 재시작을 일으키지는 않는다. 서비스별 health, Secret 접근, 서비스 계정, API 계약 버전을 관리한다. 기존 공용 환경을 사용하며 자원 변경은 인프라 담당자가 수행한다.

통합 웹과 플랫폼을 동일 출처 경로로 제공하고, C/S와 TFT의 브라우저 요청은 플랫폼에서 중계한다. React 정적 파일은 별도 공개 Cloud Run 웹 서비스가 제공한다. 현재 웹 서버는 플랫폼 health/ready를 중계하며, 사용자 세션 기반 업무 중계는 구현 대상이다. 브라우저에 서비스 계정 키를 전달하거나 신뢰할 수 없는 사용자 식별 헤더를 그대로 내부 API에 전달하지 않는다.

## 데이터 소유권

사용자 결정으로 세 서비스가 Cloud SQL 인스턴스 1개 안의 PostgreSQL DB 1개를 공유한다. 스키마와 서비스별 접속 계정을 분리하고, 각 실행 계정은 자기 소유 데이터만 수정하도록 제한한다. 스키마 이름만 나눈 것으로 권한이 격리되지는 않는다. 아래 세부 스키마 목록은 이 결정에 따른 구현 제안이다. [PostgreSQL 스키마와 권한](https://www.postgresql.org/docs/18/ddl-schemas.html)

| 스키마 제안 | 소유 데이터 | 쓰기 주체 |
| --- | --- | --- |
| `identity` | 사용자, 다중 역할, 부서 및 프로젝트별 권한, 세션, 암호화된 OAuth 토큰 캐시 | 플랫폼 인증 모듈 |
| `integration` | 메일함, 메시지, 첨부 연결, 동기화 커서, 발송 기록 | 플랫폼 메일 모듈 |
| `catalog` | 원문 파일, 불변 문서 버전, 출처 매핑 | 플랫폼 파일 모듈 |
| `cs` | 문의, 판정 이력, 개선요청, 회신, 조치 및 재요청 | C/S 앱과 해당 워커 |
| `tft` | 프로젝트, 역할, 요청, 후보, 검증, 가용성, 구성안과 결정 | TFT 앱과 해당 워커 |
| `search` | 청크, FTS, 임베딩, 검색 설정 판본 | 데이터 처리 워커. 업무 및 접근 범위별 통제 |
| `evaluation` | 데이터셋 명세, 실행 설정, 실행 기록, 지표 및 사례 결과 | 평가 관리 모듈과 평가 Job |
| `runtime` | 작업, 이벤트, 멱등성 키, 발행 대기 outbox | 소유 앱별로 제한된 레코드만 |
| `checkpoint_cs`, `checkpoint_tft` | LangGraph 실행 상태 | 각 앱의 체크포인터 |

스키마별 마이그레이션 경로와 DB 역할을 분리한다. 마이그레이션 계정은 실행 계정과 다르게 둔다. 다른 스키마의 조회가 꼭 필요하면 공개 조회 뷰나 읽기 포트를 정의하고 최소 권한만 부여한다. TFT가 C/S 문의 테이블을 JOIN해 내부 구조에 의존하지 않는다.

`runtime`의 각 행에는 `owner_service`와 접근 범위를 둔다. 앱별 DB 정책 또는 제한된 저장 프로시저로 상대 작업의 수정과 이벤트 열람을 차단한다. 서비스별 스키마와 DB 실행 계정은 준비돼 있다. 새 업무 테이블은 자기 서비스의 마이그레이션으로 추가하고 세 DB 계정의 접근 격리를 검증한다.

서비스 배포와 DB 계정은 분리되지만 DB 장애와 자원 경합은 세 서비스에 공통으로 영향을 준다. 커넥션 풀 크기와 최대 인스턴스 수는 Cloud SQL의 연결 한도를 함께 고려해 설정한다.

공통 API와 업무 API 사이의 변경은 로컬 트랜잭션과 outbox로 연결한다. 파일 생성, 메일 수신, 업무 연결, 작업 완료를 분산 트랜잭션 한 번으로 성공했다고 가정하지 않는다. 재시도와 재조정으로 누락을 복구한다.

## 인증과 사람의 결정

Microsoft 인증 코드를 MSAL과 PKCE로 교환하고 토큰의 발급자, 대상, 만료와 서명을 검증한다. 사용자 키는 `tid + oid`다. 이메일과 Entra 앱 역할만으로 사용자 등록이나 업무 권한을 부여하지 않는다. [Microsoft 인증 코드 흐름](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)

`users`의 사용자와 `user_roles`의 여러 역할을 분리하는 설계안을 사용한다. `dept_staff`는 소속 부서가 필수다. 역할과 별도로 부서 및 프로젝트 범위를 확인한다. `manager`라는 이유만으로 TFT 확정이나 모든 메일 열람을 허용하지 않는다. 승인 범위는 KAN-57에서 정의하고, 정의 전에는 기본 거부한다.

TFT 프로젝트 책임자는 새로운 로그인 역할을 만들지 않고 기존 사용자에게 프로젝트 단위로 지정한다. 책임자 후보는 해당 프로젝트에 참여 권한이 있는 `sales` 또는 `manager`이며, 지정과 변경은 해당 프로젝트를 관리하는 `manager`만 수행한다. TFT 구성안 최종 확정은 현재 지정된 책임자만 할 수 있다. 프로젝트 생성자나 다른 관리자가 책임자 지정을 대신하는 것으로 간주하지 않는다.

책임자 변경 시 변경자, 이전 및 신규 책임자, 사유와 시각을 보존한다. 책임자 미지정 상태에서는 최종 확정을 거부한다. 이전 책임자의 과거 결정 기록은 보존하며, 변경 후 확정 요청은 현재 책임자를 기준으로 검사한다. 자기 자신을 책임자로 지정할 수 있는지 등 추가 제약은 별도 결정 전 임의로 추가하지 않는다.

부서 인력요청은 해당 프로젝트의 담당 `sales`가 내용을 검토한 뒤 발행한다. 이 요청을 보내기 위한 관리자 또는 프로젝트 책임자의 별도 승인 단계는 두지 않는다. AI가 작성한 초안은 사람이 확인해야 하며, 메일 발송도 담당자가 내용을 확인한 뒤 수행한다. 부서의 후보 추천 및 검증을 거쳐 최종 구성안만 현재 프로젝트 책임자가 확정한다.

시연에서는 부서의 같은 담당자가 후보 추천과 경험 및 가용성 확인을 수행할 수 있도록 구성한다. 추천과 검증 결과 및 근거는 구분해 보존하되, 이 분리를 위해 별도 로그인 역할이나 중간 승인자를 추가하지 않는다. 부서 및 프로젝트 접근 범위 검사와 최종 확정자 검사는 유지한다. 나머지 구현 세부사항은 이 흐름에 맞는 기본값으로 정리하고, 시연 범위와 핵심 권한이 달라지는 사항만 추가 의사결정 대상으로 둔다.

개발 계정 선택은 DB에 준비된 시연 계정만 사용한다. `environment=production`이면 개발 인증 라우트 등록 자체를 막고, 관련 설정을 켠 구성도 시작 시 거부한다. 세 앱과 워커 모두 동일한 환경 값을 검증한다.

플랫폼이 Microsoft 로그인과 서버 세션을 관리한다. 브라우저에는 토큰 자체 대신 불투명한 세션 ID를 HttpOnly 및 Secure 쿠키로 전달한다. access token과 refresh token은 서버에 보관하고 브라우저 저장소, 로그, SSE, 작업 payload에 넣지 않는다. 서비스 인스턴스가 바뀌어도 세션이 유지되도록 PostgreSQL을 사용한다.

동일 출처 웹 경로에서 C/S 및 TFT 요청을 플랫폼이 내부 서비스로 중계하고, 각 업무 서비스는 내부 호출자 인증과 함께 전달된 사용자 및 업무 권한을 검증한다. 플랫폼은 클라이언트가 보낸 사용자 식별 헤더를 제거하고, 검증된 세션에서 얻은 사용자 맥락만 신뢰할 수 있는 내부 요청으로 전달한다. 인증되지 않은 호출자가 업무 서비스를 직접 호출해 중계를 우회할 수 없도록 한다.

상태를 바꾸는 요청에는 CSRF 토큰과 Origin 검사를 적용하고 쿠키의 SameSite 속성을 명시한다. OAuth 콜백은 state, nonce, PKCE 및 정확한 redirect URI로 검증한다. SSE 중계는 버퍼링을 끄고 연결 종료와 재접속을 전달한다. 세션 만료, 로그아웃, 계정 비활성화와 역할 변경은 서버에서 반영하며 상세 만료 시간은 후속 설정 계약에 기록한다.

이 구조는 플랫폼 장애 시 두 업무의 웹 접근에도 영향을 준다. 플랫폼의 가용성 및 시간 제한, 중계 경로별 상태 점검을 배포 검증에 포함한다.

관리자의 조회 및 재배정 범위는 다음으로 확정했다. C/S 관리 대상 부서와 TFT 관리 대상 프로젝트를 명시적으로 부여하고 API에서도 확인한다. 조회 범위의 부여가 업무의 최종 확정 권한을 자동으로 만들지는 않는다.

| 기능 | 관리자 권한 |
| --- | --- |
| 운영 대시보드 | 주관회사 전체의 처리량, 지연, 진행 현황 집계 조회 |
| 업무 상세 | 지정된 C/S 관리 부서와 TFT 관리 프로젝트 안에서 조회 |
| 일반 업무 담당자 재배정 | 같은 관리 범위 안에서 허용 |
| 메일, 첨부, 후보 경험 자료 | 조회 가능한 업무에 연결된 자료만 허용 |
| TFT 최종 확정 | 현재 프로젝트 책임자로 지정된 경우에만 허용 |

집계 조회 권한으로 상세 API, 원문, 파일 다운로드와 개인 메일함 전체 접근을 우회하지 못하게 한다. 고객 답변과 개선요청은 담당자가 확인하며, TFT 구성안은 지정 책임자가 확정한다. 사용자 등록 및 역할 부여와 평가 실행 및 설정 변경의 관리 주체는 별도 결정한다.

## 업무 상태와 AI 작업 상태

문의 종결과 개선요청 완료를 별도로 관리한다. TFT도 후보 추천, 부서 검증, 구성안 결정이 서로 다른 기록이다. AI 작업이 `SUCCEEDED`여도 메일 발송, 업무 승인, 후보 확정 상태로 자동 전환하지 않는다.

Cloud Tasks의 중복 실행과 순서 역전을 전제로 처리한다. 작업 및 단계 키, lease, 결과 저장의 유일성 제약으로 중복 반영을 막는다. 재시도에서 실행 횟수와 토큰 비용이 늘었다면 실제 사용량을 남긴다. [Cloud Tasks 실행 특성](https://docs.cloud.google.com/tasks/docs/common-pitfalls)

SSE는 저장된 작업 이벤트를 전달한다. 연결이 끊겨도 실행은 지속되며 클라이언트는 작업 조회와 이벤트 커서로 복구한다. 업무 처리나 LLM 호출을 응답 종료 뒤의 FastAPI 메모리 작업에만 맡기지 않는다. Cloud Run 요청 제한과 재접속을 고려한다. [Cloud Run 요청 시간 제한](https://docs.cloud.google.com/run/docs/configuring/request-timeout)

## 실데이터 교체 경계

TFT 시연은 주관회사 한 곳의 내부 부서 협업으로 구성한다. 부서별 인력 요청, 후보 추천, 경험 및 가용성 검증, 구성안 작성과 지정 책임자의 확정을 시연한다. 계열사 공동 TFT의 회사 간 자료 공유와 인력 제공 승인 절차는 이번 시연 범위에 포함하지 않는다.

공개 조직 자료의 회사 및 조직 명칭과 프로젝트의 업무 분야 태그, 사용자 역할을 구분한다. 공개 자료는 관련 조직 후보를 찾는 근거로 사용하고, 개인의 경험과 현재 가용성 또는 서비스 승인권의 근거로 사용하지 않는다. 시연 인력과 경험, 가용성은 가상 자료임을 표시한다. 다른 계열사의 조직을 주관회사의 내부 부서로 섞지 않는다.

원천 어댑터가 CSV, 업로드, Graph 메일, 나중의 회사 시스템 응답을 공통 데이터 모델로 변환한다. 업무 로직은 원천 컬럼이나 외부 시스템 ID를 직접 사용하지 않는다. 도입 시 어댑터 외에도 정책, 필드 매핑, 권한, 시점과 평가 사례를 검증한다. 인터페이스가 같다는 이유만으로 실제 도입 검증이 끝난 것은 아니다.

검색은 접근 범위와 유효 문서 버전 필터, FTS 및 벡터 후보, RRF 결합, 재정렬 순서다. 인용은 불변 원문 버전과 위치를 보존한다. FLT-042는 인용을 차단한다. 후보 검색과 재정렬에서도 접근할 수 없는 내용이 유출되지 않도록 한다.

LLM, 임베딩, OCR, 재정렬은 각각 교체 가능한 포트로 둔다. 모델 ID, 임베딩 차원, 캐시 유효성은 사용 키의 지원 목록과 평가 결과로 선택한다. 임베딩 모델이나 차원이 바뀌면 검색 인덱스 판본을 새로 만들고 혼합 비교하지 않는다.

## 구현할 범위와 원본

FastAPI 앱 3개, 공개 웹, 서비스별 DB 연결 및 로컬 시연 계정, 계약 생성과 CI/CD를 개발 기반으로 사용한다. 실제 업무 목록은 일부 stub이며 프론트는 합성 예시로 시작한다.

제품 OAuth·토큰·세션, 사용자·업무 객체 권한, 메일 수집·발송, C/S와 TFT 업무 기능, 검색 파이프라인, Tasks 핸들러·OIDC·중복 방지, SSE 및 평가 Jobs·화면을 구현한다. 개인 Outlook의 로그인·Graph 송수신과 Gemini API 호출은 사전 검증됐으며 제품 기능과 별도로 통합한다.

상태 및 권한의 세부 계약은 KAN-55·56·57, C/S 필드 합의는 KAN-54와 맞춘다. 미합의 권한은 기본 거부하고 합의 전 통합을 완료 처리하지 않는다.
