# 로컬 부하 시험: 일반 API·비동기 작업·동시 사용 (KAN-155)

이 문서는 KAN-155 완료 조건 "사전 합의 부하에서 p50/p95/실패, DB pool/Cloud Run 확장; 모의 LLM과 실 LLM 소규모 분리" 가운데 **모의 LLM 로컬 측정** 결과다. 배포 환경(Cloud Run·Cloud SQL) 측정은 2026-11-09에 가짜 모델과 실제 모델(보통·3배 부하) 모두 했다([배포 환경 측정](#배포-환경-측정-2026-11-09-가짜-모델)).

부하 가정은 KAN-155 Jira 댓글 10930의 가정안을 따른다.

- 사용자 160명 가운데 동시에 활동하는 사람은 약 27명으로 잡았다.
- 보통 부하: 화면 조작 약 2건/초, 열린 SSE 10개, 동시 분석 작업 3건.
- 운영 값(오새결 확인, 댓글 10966, 2026-10-31)과 이 시험의 대응:

  | 항목 | 운영 값 | 이 시험 | 판정에 미치는 영향 |
  | --- | --- | --- | --- |
  | Cloud Run 서비스 동시 요청 | 20(`infra/deploy_private.py` `--concurrency=20`), 서비스당 최소 1·최대 2 | uvicorn 동시 상한 20, 2 인스턴스는 슬롯 40으로 근사 | 같다 |
  | worker Job | 실행 하나에 tasks 1·parallelism 1(`infra/deploy_workers.py`). 작업마다 실행 하나 | 작업마다 worker 프로세스 하나 | 같다 |
  | Cloud SQL | `db-custom-2-8192`(2 vCPU·8GB) | 같은 PC의 PostgreSQL 17 | 최대 연결 수는 운영에서 확인한 값이 없다. 이 메모리 구간(7.5GB 이상 15GB 미만)의 Cloud SQL 기본값은 400이다. 측정 최고 동시 연결 31은 그 8%다 |
  | DB 연결 풀 | 없음. 이번 배포에 넣지 않고 배포 환경 측정 뒤 판단 | 없음 | 같다 |

  그래서 아래 판정은 바뀌지 않는다. 화면당 SSE 수와 조작당 API 수(김종하 확인)는 아직 가정이다.
- 합성 사용자는 DB 역할이 있는 142명이다(C/S 상담원 30, 부서 담당 90, 관리자 12, 영업 10). RFP 검토 15명과 평가 3명은 DB에 따로 역할이 없어 넣지 않았다.

## 실행

```
docker run -d --rm --name kan155-load-db -e POSTGRES_PASSWORD=<임의> -e POSTGRES_DB=team4 \
  -p 127.0.0.1:55434:5432 pgvector/pgvector:0.8.7-pg17-trixie
uv run --frozen python -m scripts.load_run prepare --admin-url postgresql://postgres:<임의>@127.0.0.1:55434/team4 --state <저장소 밖>/state.json
caffeinate -i uv run --frozen python -m scripts.load_run run --admin-url … --state … --profile normal --out <저장소 밖>/normal.json
```

- **DB 안전장치**
  - 역할 SQL(`infra/sql/001_service_roles.sql`)이 DB 이름 team4를 요구하므로 이름은 team4로 둔다.
  - `prepare`는 빈 DB에서만 시작하고, 준비를 모두 마친 뒤 표식 테이블 `public.kan155_load`를 만든다. `run`은 표식이 있는 DB에서만 돈다.
  - 그래서 같은 이름의 로컬 compose DB나 운영 DB에는 쓰지 않는다.
- **조건마다 새 컨테이너**: 한 번 돌린 DB에는 작업·알림이 쌓이므로 조건마다 새 컨테이너에서 준비한다.
- **절전 금지**: 측정 중에는 PC가 잠들지 않게 한다(`caffeinate -i`). 절전에서 깨어나면 DB 시계가 건너뛰어 작업 소유권(lease)이 만료된다. 실제로 그 때문에 `LEASE_LOST`가 나온 측정이 있어 버렸다.
- **상태 파일**: 합성 사용자의 세션 토큰이 들어 있으므로 저장소 밖에 둔다.
- **외부 호출 없음**: 실제 모델·Microsoft·Google은 부르지 않는다. 서비스·worker 프로세스에는 실행에 필요한 환경 변수만 넘기고, 빈 작업 폴더에서 띄워 저장소의 `.env`를 읽지 않는다.

## 무엇을 재는가

`scripts/load_run.py`는 cs·tft·platform을 각각 uvicorn 프로세스 하나로 띄운다. 프로세스 하나가 Cloud Run 인스턴스 하나에 해당한다. 동시 상한은 배포 설정(`infra/deploy_private.py` `--concurrency=20`)과 같은 20이다. 그 위에 세 가지 부하를 동시에 건다.

| 부하 | 방식 |
| --- | --- |
| 화면 조작 | 도착 간격이 지수분포인 열린 부하다. 조작마다 플랫폼 세션 확인(`GET /api/v1/platform/me`, 운영 세션 쿠키)을 한 뒤 업무 API를 한 번 부른다. 업무 API는 C/S 문의 목록·상세·분석·처리 상태·접수(쓰기), 개선요청 목록, 부서 문의 목록, 통계, RFP 프로젝트 목록, 알림 미읽음 수다 |
| SSE | C/S 상담원이 분석 작업 이벤트(`GET /api/v1/platform/jobs/{id}/events`)를 본다. 스트림이 끝나면 1초 뒤 최근 작업에 다시 붙는다 |
| 분석 작업 | 플랫폼에 작업을 접수(`admit_cs_job`)한다. 작업마다 worker 프로세스를 하나 띄워(`CS_JOB_ID`) 실제 인수·체크포인터·저장 경로로 그래프를 돌린다. 모델은 가짜이고 정해진 시간(±30%)을 기다린 뒤 고정 답을 낸다. 분류 6.8초는 gemini-3.6-flash v3 채택 실측의 평균 지연(valid 603건 6.81초)이고, 초안 6.0초와 검증 2.5초는 가정값이다 |

**측정 방식과 근사한 것**

- **중계는 세션 조회만 재현했다.**
  - 운영 경로는 web → platform 중계 → cs/tft다. 중계는 Google 서비스 ID 토큰이 필요해 로컬에서 띄울 수 없다.
  - 대신 업무 요청마다 세션 확인을 먼저 보냈다. 중계가 플랫폼 DB에 주는 부하(요청당 세션 조회)는 이것으로 재현된다. 업무 API는 로컬에서만 믿는 `X-Team4-Principal` 헤더로 직접 부른다.
  - 실제 중계는 업무 요청이 끝날 때까지 플랫폼 슬롯과 스레드를 잡고 있다(`relay.py`, 상류 timeout 20초). 이 근사는 세션 조회 시간만 잡으므로 **플랫폼 슬롯 압박을 실제보다 작게** 잡는다. 중계의 상류 HTTP 왕복과 ID 토큰 검증 시간도 빠져 있다.
- **사용자 체감 시간과 실패**
  - 체감 시간(`total.read`·`total.write`)은 세션 확인 + 업무 요청이다.
  - 실패는 5xx·429·연결 실패, 그리고 세션 확인에서 막힌 조작(401·403 포함)이다. 4xx 업무 응답은 실패로 보지 않는다.
- **슬롯 초과 동작이 Cloud Run과 다르다.**
  - 로컬 uvicorn의 `--limit-concurrency`는 처리 중 요청이 아니라 **열린 연결**을 세고, 넘으면 바로 503을 낸다. 그래서 측정 클라이언트는 keep-alive 연결을 남기지 않는다.
  - Cloud Run의 `--concurrency`는 처리 중 요청만 세고, 넘치면 잠깐 대기열에 두며 인스턴스를 늘린다. 최대 인스턴스에서도 넘치면 429를 낸다.
  - 그래서 로컬의 인스턴스 1개 결과는 "인스턴스가 늘지 않을 때"의 모습이다. 2 인스턴스는 프로세스 하나의 슬롯 40으로 근사했다(CPU는 늘지 않음).
- **같은 PC에서 돌렸다.** 측정 클라이언트·DB·서비스 셋·worker 프로세스(최대 9개)가 PC 한 대(Apple M2 8코어)를 나눠 쓴다.

- **실패율이 흔들린다.** 같은 조건의 실패율은 측정 클라이언트의 연결 방식에 따라 크게 달랐다. keep-alive를 남긴 이전 실행에서는 12.2%와 47.7%였다. 숫자 자체보다 "SSE가 슬롯을 거의 다 채우면 새 연결 대부분이 거절된다"는 점을 결론으로 읽는다. 76%는 로컬 uvicorn이 즉시 503을 내는 특성이 겹친 값이다. Cloud Run은 두 번째 인스턴스로 보내거나 잠깐 대기열에 두므로 운영에서는 더 낮을 가능성이 크다. 이 숫자를 Cloud Run 실패율로 옮겨 쓰지 않는다.

- **SSE 열림 비율**: 원한 시청 시간(스트림 수 × 부하 시간) 가운데 실제로 열려 있던 비율이다. 작업이 끝나 스트림이 닫히면 1초 뒤 다시 붙으므로 슬롯이 넉넉해도 1보다 작다(보통 부하 0.89).

## 알게 된 것

1. **첫 한계는 플랫폼 슬롯을 차지하는 SSE다.**
   - SSE 하나가 열려 있는 동안 플랫폼 인스턴스의 동시 슬롯 하나를 계속 쓴다.
   - 인스턴스 하나(슬롯 20)에서는 SSE가 19개 열린 뒤 슬롯이 차고, 그 뒤 들어온 SSE와 화면 조작(세션 확인)이 함께 거절된다. 19개에서 멈추는 것은 로컬 uvicorn이 새 연결까지 세어 판정하기 때문이다(실효 슬롯 19, 슬롯 40 조건은 39). Cloud Run은 20을 다 쓴다.
   - 2 인스턴스(슬롯 40)면 3배 부하도 통과했다. 하지만 SSE 30개가 슬롯의 3/4을 쓰고 있어 여유가 작다. SSE 연결 p95도 1.18초로 늘었다.
   - 최대 2 인스턴스는 배포 설정(`infra/deploy_private.py` `--max=2`)이자 설계 결정(`docs/decisions.md`, "부하 평가로 조정")의 값이다.
2. **연결 풀이 없어 새 연결이 많다.**
   - 동시 연결은 최대 31개로 작지만, 요청과 SSE poll마다 새 연결을 열어 초당 29~77개를 새로 맺는다.
   - SSE 하나가 1초마다 세션 확인과 이벤트 조회로 연결 2개를 연다.
   - 로컬은 같은 PC라 연결 비용이 작다. Cloud SQL(TLS·커넥터)에서는 연결마다 비용이 커지므로 배포 측정에서 다시 봐야 한다.
   - 동시 연결 수 자체는 여유가 있어 보인다. Cloud SQL 기본 최대 400(8GB 구간, 운영 값 미확인) 대비 최고 31이다. 운영은 서비스당 최대 2 인스턴스라 플랫폼 연결이 두 프로세스로 나뉘지만 합은 같은 부하에서 비슷하다. 문제는 연결 수보다 새 연결을 맺는 속도다.
3. **알림 조회는 읽기인데 쓰기를 한다.**
   - `GET /api/v1/platform/notifications/unread-count`는 매번 대기 중인 알림을 수신자별 행으로 펼친다(`notifications/repository.py` `expand_pending`).
   - 분석 작업이 끝날 때마다 알림이 생기므로, 그 뒤 첫 조회가 C/S 상담원 전원의 행을 만든다.
   - 그래서 이 API는 p50이 0.04~0.07초인데 p95는 0.63~0.86초다(거절이 적은 보통·2 인스턴스 조건). 다른 업무 API는 p95가 0.1초 안팎이고, 체감 읽기의 최댓값(0.74초·1.81초)도 이 API의 최댓값에 세션 확인을 더한 정도다. 알림 조회는 읽기 조작의 약 9%라 전체 p95의 경계에 걸쳐 있다.
4. **worker는 작업 하나에 프로세스 하나다.**
   - 문의 출처가 작업 ID를 `CS_JOB_ID` 환경 변수에서 읽는다(`backend/api/cs/worker_source.py`). 그래서 한 프로세스에서 여러 작업을 동시에 돌릴 수 없다.
   - 플랫폼은 작업마다 Cloud Run Job 실행을 하나씩 만들므로(`jobs/cloud_run.py`) 이 구조와 맞다. 동시 작업은 실행 수로 늘어나며, Job의 `--parallelism=1`은 그대로 맞다.
5. **worker 로그인에는 DB 접속 권한을 따로 줘야 한다.**
   - 역할 SQL이 PUBLIC 접속을 막으므로 `cs_worker`에 속한 로그인 계정도 `GRANT CONNECT ON DATABASE`가 없으면 접속하지 못했다.
   - 시험 도구는 준비 단계에서 권한을 준다. 운영 절차는 `infra/sql/README.md`에 반영했다(#392).

## 배포 환경 측정 (2026-11-09, 가짜 모델)

운영 서비스·worker 설정을 그대로 복사한 별도 환경(`-load`)에서 실제 경로(web → platform 중계 → cs/tft, 작업 배정 스케줄러, Cloud Run Job worker)로 쟀다. 측정이 끝난 뒤 환경은 모두 지웠다.

### 환경과 실행

- `infra/load_env.py`: 운영 서비스·Job 명세를 `gcloud ... describe`로 읽어 이름·주소·Cloud SQL·버킷·DB 비밀값만 `-load`로 바꿔 만든다. DB는 별도 인스턴스 `team4-sql-load`(운영과 같은 `db-custom-2-8192`)다. 메일 수집·발송, 푸시, C/S 모델 기능은 끈다. RFP worker는 `TFT_EXTRACTION_PROVIDER=fake`라 모델을 부르지 않는다. 기본은 명령만 보여 주고 `--apply`일 때 실행한다. 정리(`teardown`)는 `-load`가 들어간 자원만 지운다.
- `scripts/load_remote.py`: `prepare`(빈 DB 준비, 서비스 DB 비밀번호를 무작위 값으로 바꿔 Secret Manager에만 저장), `seed`(영업 사용자로 RFP 프로젝트와 합성 문서 업로드), `run`(web 주소로 화면 조작·SSE·RFP 작업 부하). C/S worker에는 가짜 모델이 없어 분석 작업은 RFP만 걸었다.
- 조건은 로컬과 같다. 보통 2건/초·SSE 10·작업 3, 3배 6건/초·SSE 30·작업 9, 연결 한계 2건/초·SSE 40·작업 3. 각 600초.
- 합격선은 보통이 읽기 p95 0.8초·쓰기 1.5초·실패 0.5% 이하, 3배가 p95 2초·실패 2% 이하다.

### 알게 된 것

1. **DB 연결을 매번 새로 여는 비용이 platform CPU를 채웠다.**
   - `backend/shared/database.py`의 `connection()`은 호출마다 새 연결을 열었다. SSE 하나는 1초마다 세션 확인 두 번과 이벤트 조회 한 번으로 연결 3개를 연다.
   - CPU가 차면 Cloud Run은 인스턴스당 동시 요청 약 20에서 더 받지 않고 요청을 429("waiting too long for an available instance")로 끊는다. web은 이를 502로 돌려준다. 동시 요청을 80으로 올린 3차도 인스턴스당 동시 요청이 20 안팎에서 멈췄다.
   - 연결 pool을 넣은 4차는 같은 3배 부하에서 실패가 없어졌고 CPU는 절반으로 내려갔다. 다만 CPU를 어디에 썼는지 프로파일로 확인하지는 않았다.
2. **CPU가 풀린 뒤의 한계는 platform 자리 수다.**
   - SSE는 열려 있는 동안 platform 자리 하나를 잡는다. 인스턴스 2 × 동시 요청 20 = 40자리를 SSE 40개가 다 쓰면 나머지 요청은 429다(4차 연결 한계, CPU 40% 안팎).
   - CPU 여유가 생겼으니 platform 동시 요청을 올리면 풀릴 것으로 보지만 그 설정으로는 재지 않았다.
3. **작업 배정 스케줄러 호출도 같은 자리를 쓴다.**
   - 1분마다 부르는 `/internal/v1/platform/jobs/dispatch`가 platform 포화 때 429로 실패했다(2차 3배 8분, 연결 한계 10분 연속).
   - 그동안 worker가 하나도 뜨지 않았고, 10분 넘게 시작하지 못한 작업은 정리 규칙(`jobs/sweep.py`, 600초)이 FAILED(`JOB_NOT_STARTED`)로 닫았다. 모델이나 worker 오류는 아니다. 실행된 worker는 모두 성공했다.
4. **끝난 작업의 남은 전송 행이 작업 배정을 막았다(KAN-250).**
   - 4차 3배에서 20:48:19 이후 접수된 9건은 접수 직후 배정이 worker 실행을 하나도 만들지 않았고(약 70ms), 20:49 스케줄러 호출도 39ms 만에 아무것도 보내지 않았다. 10분 안에 시작되지 못한 4건이 `JOB_NOT_STARTED`로 닫혔다.
   - `claim_next`는 대기열을 오래된 행부터 하나씩 집는데, 이미 끝난 작업의 행을 집으면 `begin_send`가 막고 그 호출은 아무것도 보내지 못한다(`sweep`이 멈춤). 이런 행이 앞에 쌓이면 호출마다 한 칸씩만 줄어 뒤 작업이 기다린다.
   - QUEUED·RUNNING 작업의 행만 집게 고친 5차에서는 3배 324건, 연결 한계 76건이 모두 시작됐고 작업 p95가 637초에서 21초로 줄었다.
5. **접수가 몰리면 platform 인스턴스가 20초 동안 멈췄다(KAN-252).**
   - 5차 3배와 실제 모델 3배 측정 시작 직후, platform 인스턴스 하나가 받은 요청이 종류와 상관없이 약 20초 뒤 한꺼번에 끝났다. 작업 접수는 tft의 상류 제한(20초)을 넘겨 사용자에게 503으로 보였지만 platform은 접수를 마쳐서, 다시 누르면 409(이미 처리 중)였다. 그동안 platform CPU는 12%, DB CPU는 5%였다.
   - 원인은 스레드 풀의 순환 대기다. platform 중계는 cs·tft로 넘기는 동기 HTTP 호출을 기본 스레드 풀(CPU 1개면 약 5개)에서 돌리며 상류 응답까지 최대 20초 스레드를 잡는다. 작업 접수 몇 건이 이 풀을 다 잡으면, 그 접수를 받은 tft·cs가 부른 platform 내부 접수는 호출자 토큰 검증 스레드를 얻지 못하고, 중계 제한 20초가 지나서야 풀린다.
   - 중계 전송에 전용 스레드 풀(80)을 준 뒤 같은 실제 모델 3배 측정에서 읽기 최대 1.2초, 접수 503·409 0건이 됐다.
6. **SSE 연결이 끊길 때 DB 연결 오류가 난다.** platform 로그에 `another command is already in progress`가 몇 건 있다. 끊긴 요청의 연결을 정리하다 난 것으로 보이며, 사용자 응답에 영향을 준 흔적은 없다.

## 남은 것

- **부하 가정 확인**: Cloud SQL 크기·연결 풀·worker 동시 상한은 오새결 님이 답했다(댓글 10966, 위 표). 화면당 SSE 수·조작당 API 수는 김종하 확인을 기다린다(댓글 10930). 운영 `max_connections`는 배포 환경 측정 때 `SHOW max_connections`로 확인한다.
- **운영 반영**: KAN-252(#675) 배포. KAN-248·KAN-250·동시 요청 80은 2026-11-09 운영에 반영했다(main d7d3279b).
- **이번에 넣지 않은 부하**: 메일 수집·발송. 배포 환경에서는 C/S 분석 작업(C/S worker에 가짜 모델이 없음)도 넣지 않았다.
