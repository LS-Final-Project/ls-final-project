# KAN-188: 확정된 교육 문서의 프로젝트 소속 정리

이 절차는 40443에 문서별로 등록된 **미분석 문서 5개**에만 적용한다. 일반 프로젝트 병합 기능이 아니다. 현재 문서 UUID·판본·파일과 기존 프로젝트·등록 감사·멱등 기록은 보존한다. DDL·모델 호출·재처리를 하지 않는다.

## 확정 범위

| 대표 접수 | 실제 프로젝트 | 문서 | 용도 |
|---|---|---|---|
| P26-0014, 기존 D14 | 2300096 | D14 유닛 변전소, D15 중전압 개폐장치, D17 배전반 | 개발·시연. D15는 일반화 평가에서 제외 |
| P26-0010, 기존 D10 | Project Alpha / PHX22-5030-00 | D10 유닛 변전소, D12 중전압 개폐반 | 평가·등록조회전용. 분석 승인으로 해석하지 않음 |

2300096은 기획서 최종본 V_1 §3.3 및 세 원본의 식별자로 확인했다. Alpha는 V_1 §3.3 및 두 원본의 Project Alpha / PHX22-5030-00으로 확인했다. 원본 SHA256·현재 UUID는 `scripts/local_business/group_rfp_documents.py`에 고정돼 있다. D19~D22 등 관계가 미확정인 문서는 포함하지 않는다.

## 적용 결과

D15·D17의 `documents.project_id`는 D14로, D12는 D10으로 바뀐다. 대표 프로젝트 이름에는 실제 프로젝트와 포함 문서 번호가 표시된다. 비워진 프로젝트 세 개는 삭제하지 않고 이름에 대표 접수 번호와 `이전 등록`을 표시한다. 이름 변경은 기존 `version`을 올리고 감사에 변경 전 프로젝트 전체와 이동 매핑을 남긴다. 기존 회사 코드·접수 번호·접근 권한은 변경하지 않는다.

문서 ID·판본 ID·SHA·파일 크기·`storage_key`·제목·note와 모든 원본 바이트는 그대로다. 파일 키에 이전 프로젝트 UUID가 들어 있어도 파일 조회는 권한 확인 뒤 저장된 키로 읽으므로 이동하거나 복사하지 않는다. API는 소속 변경 후 대표 프로젝트에서 3개/2개 문서를 반환한다. 요구가 추출되면 기존 `프로젝트 전체 문서` 조회와 맥락 정리가 해당 프로젝트의 문서 전체를 대상으로 동작한다.

**현재 5개 문서에는 요구·질문·초안·맥락 결과가 없다.** 따라서 이번 정리 직후 문서 목록은 묶이지만 고객 요구나 맥락 분석이 자동으로 생기지는 않는다. 분석·맥락 정리는 별도 승인 범위다.

## 적용 전 검사

기본 명령은 READ ONLY SQL만 출력한다. 파이프라인 오류를 놓치지 않도록 파일로 만든 후 읽기 검사한다.

```bash
python3 -B scripts/local_business/group_rfp_documents.py > /tmp/kan188-grouping-check.sql
docker exec -i team4-kan159-ui-reboot-20261103-pg \
  psql -X -U postgres -d team4 -v ON_ERROR_STOP=1 < /tmp/kan188-grouping-check.sql
```

다음 중 하나라도 있으면 작업을 멈춘다. 조건을 제거해 강행하지 않는다.

- 고정 문서/판본/SHA/크기/파일 키/원래 프로젝트 이름·번호가 다르거나 추가 문서·판본이 있음.
- 원래 다섯 프로젝트의 설정·담당·검토 부서가 다르거나, 별도 manager 프로젝트 권한이 있음.
- 요구·질문·초안·검토본·맥락·협력사 등급 등 `project_id`를 가진 업무 행이 있음. 새로 생긴 테이블도 검사한다.
- 조항·단선결선도·주석 등 문서나 판본을 참조하는 파생 기록이 있음.
- 초기 `project.create` / `document.upload` 이외 명령·감사가 있음.
- 해당 프로젝트의 과거 작업이 있거나, 스택에 QUEUED/RUNNING 작업·살아 있는 lease가 있음.

## 운영자가 적용할 순서

1. 현재 실행 source·namespace·PG identity 및 runtime unlimited 6/6 설정을 대조한다. 활성 작업은 중단하지 않는다.
2. 기존 idle drain 절차로 API 쓰기 진입점과 driver를 잠깐 멈춘다. 읽기 검사 성공만으로 동시 쓰기가 차단되는 것은 아니다.
3. **현재 시점** `pg_dump -Fc`, 업로드 파일 manifest, SQLite 원장 사본, 설정·enabled marker 증거를 백업한다. 원장 논리 해시와 모든 파일 SHA를 기록한다. 예전 배포 백업만으로 대체하지 않는다.
4. 읽기 검사를 재실행하고 SQL을 검토한다. 아래 actor는 실제 승인받은 현재 등록 담당 sales ID다. 다른 계정으로 바꾸어 검사를 우회하지 않는다.

```bash
python3 -B scripts/local_business/group_rfp_documents.py \
  --write-sql-for-actor 00000000-0000-4000-8000-000000000003 \
  > /tmp/kan188-grouping-apply.sql
# SQL 검토와 위 백업 완료 후 운영자가 실행:
docker exec -i team4-kan159-ui-reboot-20261103-pg \
  psql -X -U postgres -d team4 -v ON_ERROR_STOP=1 < /tmp/kan188-grouping-apply.sql
```

쓰기 SQL은 관련 테이블을 잠근 뒤 모든 조건을 다시 검사한다. 하나라도 실패하면 전체 트랜잭션이 커밋되지 않는다. 적용은 5개 프로젝트 이름/판본 갱신, 문서3개 소속 이동, 감사5개 추가다. 재실행은 이미 바뀐 원래 이름·판본 검사에서 거부된다.

5. 원본 문서5개와 판본5개의 바이트 단위 행 비교(문서의 `project_id` 세 값만 예외), 기존 명령·감사 불변, 다른 업무 행과 파일·원장 불변을 확인한다. 대표별 문서3개/2개, 원본 다운로드 SHA, 이전 프로젝트 세 개 보존을 확인한다.
6. 기존 설정 그대로 API와 TFT driver를 재개하고 실제 GET 화면으로 문서 선택 및 프로젝트 전체 범위를 확인한다. 업무 쓰기·모델 실행을 함께 시험하지 않는다.

실패 시 SQL 커밋 전에는 롤백되므로 기존 상태를 확인하고 재개한다. 커밋 후 문제가 있으면 API/driver를 중지한 상태로 최신 백업과 감사에 기록된 변경 전 행을 바탕으로 복구한다. 서비스가 재개된 뒤 다른 작업이 쌓였다면 전체 DB를 무조건 되돌리지 않는다. 이 문서는 복원 시험 통과를 주장하지 않는다.

## 초기 등록 원장과의 관계

`register_inputs.py`와 기존 등록 원장은 문서별 독립 프로젝트였던 **최초 등록 사실**을 그대로 남긴다. 해당 원장·`rfp_commands.result`를 현재 소속에 맞춰 덮어쓰지 않는다. 이력 데이터를 고치면 당시 작업을 재현할 수 없다.

적용 뒤 옛 입력 등록 명령은 프로젝트 이름·UUID 확인에서 `PROJECT_MISMATCH` 또는 원장 불일치로 멈춘다. 이는 새 문서를 중복 업로드하거나 옛 소속으로 되돌리지 않게 하는 보호다. 새 환경 초기등록을 지원하려면 별도 그룹 등록 계약과 원장 업그레이드를 구현해야 하며, 이번 한 번의 기존 스택 정리에는 포함하지 않는다.

## 검사 범위

`tests/tft/test_rfp_document_grouping_db.py`는 별도 PostgreSQL 트랜잭션에서 소속 이동·문서 판본 불변·등록 역사 보존·원자성, 기존 업무/조항/권한/과거 및 활성 작업/lease/변경된 SHA/새 테이블의 거부를 확인한다. 테스트는 운영 UUID를 합성 테스트 행의 고정 식별자로만 쓰고 운영 DB에 연결하지 않는다. 실제 운영 DB에서는 읽기 전제조건 검사만 수행했다.
