# TFT 화면 동작 명세

KAN-58 산출물. 기준일 2026-10-23, 작성 김종하, 검토 오새결. RFP 기획서 4.8의 화면 5개와 KAN-57 결정(2026-10-21)을 기준으로 TFT 요구·후보·검증 화면의 동작을 정한다. 이 문서는 화면 명세이며 구현 완료를 뜻하지 않는다. 현재 구현된 TFT 화면은 프로젝트 목록 stub 하나다.

근거는 [AGENTS](../AGENTS.md#인증과-역할), [아키텍처](architecture.md#인증과-사람의-결정), [데이터 계약](data-contract.md#업무별-데이터와-결정), [API 규약](api-contract.md), [TFT 계약 시작점](../contracts/tft/projects.md), [의사결정](decisions.md#시연에-맞춘-tft-업무-흐름)이다. 기획서 발췌와 이 문서가 다르면 저장소 문서와 Jira 결정이 우선한다. OpenDesign 프로토타입과 기획서는 수정하지 않았고 스토리보드 Google Docs는 열람하지 못했다. 기존 C/S 초안(KAN-129 목록·상세 화면)을 공통 요소의 참고로 삼는다.

## 반영한 결정

| 항목 | 결정 | 화면 반영 |
| --- | --- | --- |
| 조직 범위 | 주관회사 한 곳의 부서 간 TFT. 계열사 간 절차 제외 | 회사 선택 UI 없음. 요청 부서는 주관회사 내부 부서만 |
| 알림 | 메일·Teams 알림은 후속. 초기 시연은 파일 등록·서비스 내 요청서 공지·후보 입력으로 완결 | 공지는 상태 전이와 부서 요청 목록 노출로 끝난다. 발송 버튼 없음 |
| 인력요청 발행 | 담당 `sales`가 검토 후 발행. 중간 승인 없음 | 요청서 화면의 "공지" 버튼은 `sales`에게만 보이고 승인 대기 상태가 없다 |
| 추천과 검증 | 같은 부서 담당자가 추천과 경험·가용성 확인을 모두 수행 가능. 기록은 구분 | 추천 기록과 검증 기록을 별도 블록으로 표시. 교차 검증으로 설명하지 않는다 |
| 프로젝트 책임자 | 프로젝트별 지정. 해당 프로젝트의 `sales`/`manager` 중에서 관리 `manager`만 지정·변경. 현재 책임자만 최종 확정. 미지정이면 확정 거부. 변경 이력 보존 | 현황 화면에 책임자 표시와 지정·변경 버튼. 구성안 화면의 확정 버튼은 책임자에게만 활성, 미지정이면 비활성과 사유 표시 |
| 후보 기준 상태 | 유사 경험·필수 역량·우대 역량·가용성 각각 확인 · 추가 확인 · 미충족. 자료 없음은 추가 확인 | 기준별 배지 4개. 미입력은 자동으로 "추가 확인" |
| 가용성 확인 완료 | 대상 기간·투입률·확인 주체·확인 시각·근거가 모두 있어야 확인 | 사용자 입력은 대상 기간·투입률·근거 3개, 확인 주체·확인 시각은 서버 기록. 불완전 입력도 저장되며 기준 상태는 "추가 확인". "확인"으로 저장하려는데 입력 3개 중 하나라도 비면 422 `EVIDENCE_REQUIRED` |
| 역할 요청 상태 | 작성 중 → 공지 → 후보 추천 접수 → 부서 검증 → 후보 비교 → 구성안 검토 → 확정 | 현황·요청서·구성안 화면의 상태 배지 |
| 출처 표기 | 원문 사실 / 기획상 도출 / 부서 확인 / 가상 시연 | 모든 값 옆의 `small` 출처 표기. 가상 후보는 목록과 상세에 "가상 시연" 표시 |

## 용어와 상태값

이 문서는 화면 라벨을 한국어로 쓴다. 코드값은 제안이며 실제 enum은 TFT API 계약(KAN-119/T04/T05/T09)에서 `backend/api/tft/` 아래 기능별 `schemas.py`로 확정한다. 공통 패키지에 업무 상태 enum을 추가하지 않는다.

| 구분 | 화면 라벨 | 코드값 제안 |
| --- | --- | --- |
| 역할 요청 상태 | 작성 중 · 공지 · 후보 추천 접수 · 부서 검증 · 후보 비교 · 구성안 검토 · 확정 | `DRAFTING`, `ANNOUNCED`, `RECOMMENDING`, `DEPT_VERIFYING`, `COMPARING`, `PROPOSAL_REVIEW`, `CONFIRMED` |
| 후보 기준 상태 | 확인 · 추가 확인 · 미충족 | `CONFIRMED`, `NEEDS_CHECK`, `NOT_MET` |
| 구성안 역할 항목 | 후보 없음 · 보강 필요 · 보완 요청 · 확정 가능 · 확정 | `NO_CANDIDATE`, `NEEDS_REINFORCEMENT`, `SUPPLEMENT_REQUESTED`, `READY`, `CONFIRMED` |
| 출처 표기 | 원문 사실 · 기획상 도출 · 부서 확인 · 가상 시연 | 데이터 계약의 `derivation_kind`(`PROVIDED`/`DERIVED`/`SYSTEM`/`ASSUMED`)와 `data_origin`(`synthetic`/`demo`/`real`), `provenance_kind`를 라벨로 바꿔 표시. 매핑은 아래 표 |

| 화면 라벨 | 필드 조합 | 예 |
| --- | --- | --- |
| 원문 사실 | `derivation_kind=PROVIDED` | RFP 조항·페이지 인용 |
| 기획상 도출 | `derivation_kind=DERIVED`, `provenance_kind=ai_draft` 또는 `system_record` | AI가 제안한 역할·필수 역량, 비교 기준 |
| 부서 확인 | `provenance_kind=human_input`이고 작성자가 부서 담당자 | 추천 이유, 가용성 확인 기록 |
| 가상 시연 | `data_origin` ≠ `real` 또는 `derivation_kind=ASSUMED` | 후보 인력, 경험, 가용성 전부 |

라벨 매핑은 UI 표시 규칙이며 저장 필드를 바꾸지 않는다. 한 값이 "원문 사실"이면서 "가상 시연"일 수 있다(합성 RFP). 그 경우 둘 다 표시한다.

역할·사용자 용어: `sales`는 담당 영업(요구 검토·요청서 발행), `dept_staff`는 요청 부서 담당자(추천·검증), `manager`는 관리 대상 프로젝트의 상세 조회·재배정·책임자 지정, 책임자는 프로젝트에 지정된 `sales` 또는 `manager`다. 책임자 여부는 현재 사용자 ID와 프로젝트 책임자 관계로 판정하며 로그인 역할과 독립이다. 책임자인 `manager`·`sales`는 확정·보완 요청을 할 수 있고, 책임자가 아닌 `manager`·`sales`는 역할의 기본 권한만 가진다. 후보 인력 ID와 로그인 사용자 ID는 별개다.

## 화면 목록과 라우트 제안

현재 라우트는 [App.tsx](../frontend/src/App.tsx)의 `/tft/projects` 하나다. KAN-129(`origin/KAN-129-common-layout`, dev 미병합)의 공통 레이아웃(`components/Layout.tsx`)과 상태 UI(`components/states.tsx`)를 전제로 하위 라우트를 제안한다. 라우트는 React Router 중첩 경로이며 기능 티켓에서 추가한다.

| 번호 | 화면 | 라우트 제안 | 주 사용자 | 기획서 4.8 | WBS |
| --- | --- | --- | --- | --- | --- |
| S0 | 프로젝트 목록 | `/tft/projects` (현재 stub) | 전원 | 프로젝트·역할 현황의 진입 | F06 |
| S1 | 프로젝트·역할 현황 | `/tft/projects/:projectId` | `sales`, 책임자, `manager` | 프로젝트·역할 현황 | F06 |
| S2 | 역할·인력 요청서 | `/tft/projects/:projectId/roles/:roleId` | `sales` | 역할·인력 요청서 | F06 |
| S3 | 부서 후보 추천 | `/tft/requests` (내 부서 요청 목록), `/tft/requests/:requestId` (요청서 열람·추천·검증) | `dept_staff` | 부서 후보 추천 | F07 |
| S4 | 후보 비교·TFT 구성안 | `/tft/projects/:projectId/proposal` (현재 구성안), `/tft/projects/:projectId/proposal/:version` (과거 판본 읽기 전용) | 책임자, `sales`, `manager` | 후보 비교·TFT 구성안 | F08 |
| S5 | 검증·변경 이력 | `/tft/projects/:projectId/history` | 전원(접근 범위 안) | 검증·변경 이력 | F08 |

규칙:

- `:projectId`, `:roleId`, `:requestId`는 서버 UUID다. 외부 ID나 이름을 URL에 쓰지 않는다.
- S3는 부서 담당자의 진입점이며 프로젝트 ID를 몰라도 열 수 있다. 요청서는 부서별로 발행되므로 `requestId` 기준이다.
- 모든 라우트는 딥링크로 열 수 있어야 한다. 권한이 없으면 403 ErrorState, 없거나 접근 범위 밖이면 404 ErrorState를 보여준다. 접근 불가 객체의 존재를 403으로 드러내지 않는다(API 규약).
- 상단 바 메뉴는 TFT 하나만 추가한다. 역할별 메뉴 분기는 하지 않고, 화면 안에서 허용되지 않는 행동을 비활성 또는 숨김 처리한다.
- `production` 빌드에서 미구현 화면은 `Preparing` 컴포넌트로 "업무 화면은 준비 중입니다"를 표시한다. 현재 S0도 같은 처리다.

C/S 초안(KAN-129의 `Tickets.tsx`, `TicketDetail.tsx`)과 같은 요소를 재사용하고 TFT에만 필요한 요소를 새로 둔다.

| 요소 | 공통 여부 | 내용 |
| --- | --- | --- |
| 상단 바와 계정 표시 | 공통 (`Layout.tsx`) | 포털 전환, 현재 계정과 역할 |
| 목록 표 `table` | 공통 | 열 머리글, 행 링크, 빈 목록 `Empty` |
| 상세 `dl` | 공통 | `dt`/`dd` 2열, 모바일 1열 |
| 상태 UI | 공통 (`states.tsx`) | `Loading`, `Empty`, `ErrorState`(401/403/404 고정, 그 외 재시도), `Preparing`, `NotFoundPage` |
| 출처 `small` 표기 | 공통 | C/S는 `data_origin`·`derivation_kind` 코드값, TFT는 위 라벨 표. 코드값을 라벨로 바꾸는 함수는 공통으로 두고 C/S에도 적용 가능하나 이 문서 범위가 아니다 |

| 상태 배지 | 공통 형식, 값은 TFT 전용 | 역할 요청 상태 7개 |
| 기준 배지 4개 | TFT 전용 | 유사 경험·필수 역량·우대 역량·가용성 각각 확인/추가 확인/미충족 |
| RFP 근거 링크 | TFT 전용 | 문서명·버전·조항·페이지와 원문 열기. 인용 위치는 데이터 계약의 `page`/`char_start`/`char_end`를 쓴다 |
| 후보 카드와 추천·검증 기록 블록 | TFT 전용 | 후보 식별자·소속·가상 시연 표시, 추천 기록, 검증 기록을 분리 |
| 가용성 확인 폼 | TFT 전용 | 사용자 입력 3개: 대상 기간, 투입률, 근거. 서버 기록 2개: 확인 주체(현재 사용자), 확인 시각 |
| 역할별 비교표와 팀 공백 | TFT 전용 | 역할 × 후보 행렬, 후보 없는 역할, 한 후보의 역할 중복 |
| 책임자 블록 | TFT 전용 | 현재 책임자, 미지정 안내, 지정·변경 버튼 |
| 판본 선택 | TFT 전용 | 구성안 판본 목록과 읽기 전용 과거 판본 |

## 화면별 동작 명세

각 화면에 (a) 목적과 주 사용자, (b) 표시 요소, (c) 행동과 결과, (d) 상태별 표시, (e) 허용되지 않는 행동, (f) 필요한 API를 적는다. 상태별 표시 중 로딩·빈값·오류·준비 중은 공통 상태 UI를 쓰므로 화면별로 다른 점만 적는다. 권한부족은 서버 403을 ErrorState로 보여주고, 화면 안의 버튼은 현재 사용자 역할과 프로젝트·부서 범위로 미리 비활성 또는 숨김 처리한다. 버튼을 숨겼다고 서버 검사를 생략하지 않는다.

### S0 프로젝트 목록 `/tft/projects`

- (a) 접근 범위 안의 프로젝트를 찾아 S1로 들어간다. 전원.
- (b) 표: 프로젝트명(링크), 주관 부서 또는 담당 `sales`, 책임자(미지정이면 "미지정"), 역할 수와 상태 요약(예: 확정 2 / 보완 요청 1 / 후보 없음 1), 최근 변경 시각, 출처 표기. 현재 stub은 이름과 `data_origin`만 있다.
- (c) 행 클릭 → S1. `sales`에게 "프로젝트 등록" 버튼(프로젝트명, RFP 파일 등록). 등록 후 S1로 이동.
- (d) 목록은 `data.items`와 `next_cursor` 커서 페이지다. 끝이면 "더 보기" 숨김. 잘못된 커서는 400이므로 첫 페이지부터 다시 조회한다. `manager`는 관리 대상 프로젝트만 보이며 전체 집계는 별도 대시보드 범위다.
- (e) `dept_staff`에게 등록 버튼 숨김. 등록 폼의 책임자 지정 항목 없음(책임자는 S1에서 관리 `manager`가 지정).
- (f) `GET /api/v1/tft/projects` (계약 있음, 실제 501). 프로젝트 등록과 RFP 파일 등록은 KAN-119/T04/T05/T09에서 정의. 파일 등록은 플랫폼 파일 API(업로드 서명·완료)를 쓰며 완료 검증 전 파일은 AI 처리에 쓰지 않는다.

### S1 프로젝트·역할 현황 `/tft/projects/:projectId`

- (a) 다음으로 요청하거나 검토할 역할을 찾는다. `sales`, 책임자, `manager`.
- (b) 머리글: 프로젝트명, RFP 문서명·버전(원문 열기 링크), 담당 `sales`, 책임자 블록(현재 책임자 표시명, 지정 시각, "미지정"일 때 안내문), 현재 구성안 판본과 확정 여부, 출처 표기. 요구·과업 요약: RFP에서 정리한 요구 항목과 근거 조항(기획상 도출 표기, 원문 사실 링크). 역할 표: 역할명, 수행 과업 요약, 요청 부서, 인원(확정/미정), 역할 요청 상태 배지, 추천 접수 수, 검증 완료 수, 회신 기한, 다음 행동(예: "요청서 공지 필요", "부서 검증 대기", "보완 요청 중"). RFP 처리 작업이 진행 중이면 작업 상태 표시(`QUEUED`/`RUNNING`/`PARTIAL` 등)와 진행률(없으면 표시 안 함).
- (c) 역할 행 클릭 → S2. "구성안 보기" → S4. "이력" → S5. `sales`: "역할 추가"(역할명·과업·요청 부서 입력 → 작성 중 상태로 생성), "RFP 분석 요청"(202 작업 생성, 상태 URL로 폴링 또는 SSE). 관리 `manager`: "책임자 지정" 또는 "책임자 변경"(후보 목록은 이 프로젝트의 `sales`·`manager` 사용자만, 사유 필수) → 저장 후 책임자 블록 갱신과 S5에 이력 추가.
- (d) 책임자 미지정: 책임자 블록에 "책임자 미지정 — 구성안 확정 불가. 관리 manager가 지정합니다" 안내. 역할 없음: 역할 표 자리에 `Empty`("아직 정리된 역할이 없습니다")와 `sales`에게 분석 요청·역할 추가 안내. 분석 작업 실패: 작업 오류와 "다시 요청" 버튼, 기존 역할은 유지. `manager`가 관리 대상이 아닌 프로젝트: 404.
- (e) 책임자 지정 버튼은 관리 `manager`에게만 보인다. 프로젝트 생성자·담당 `sales`·전역 `manager`라는 이유로 보이지 않는다. 자기 자신 지정 가능 여부 등 추가 제약은 결정 전이므로 UI에서 막지 않는다. 역할 삭제는 확정 후 불가(409 `INVALID_TRANSITION` 안내).
- (f) 프로젝트 상세, 요구·역할 목록, 역할 생성, RFP 분석 작업(202 + `/api/v1/tft/jobs/{job_id}`), 책임자 지정·변경: KAN-119/T04/T05/T09에서 정의. 현재 사용자: `GET /api/v1/platform/me`(계약 있음).

### S2 역할·인력 요청서 `/tft/projects/:projectId/roles/:roleId`

- (a) 역할의 필요성과 조건을 수정하고 부서 인력 요청서를 공지한다. `sales`. 책임자·`manager`는 읽기 전용.
- (b) 역할 요청 상태 배지와 전이 이력 요약. 기획서 4.3 항목을 `dl`로 표시: RFP 근거(문서명·버전·조항·페이지·원문 링크·이유 한 문장, 원문 사실 표기), 필요 역할과 수행 과업(요청 인원 확정/미정, 핵심/보강, 기대 산출물), 필수 역량과 우대 역량(분리된 두 목록, 기획상 도출 표기, 사용자가 고치면 부서 확인이 아니라 "담당 검토" 작성자 표시), 유사 프로젝트 경험 조건(제품·전압·환경·고객·과업 유사성, 요청할 근거 자료), 요청 부서와 투입 조건(주관/협업 부서, 예상 시작일·기간·투입량, 회신 기한. 미정은 "미정"으로 표시하고 빈칸으로 두지 않는다), 후보 추천 회신 항목 안내. 공지 후에는 접수된 추천 수와 S3 링크.
- (c) `sales`, 작성 중 상태: 각 항목 편집 폼과 "저장"(`If-Match` 판본 포함). "공지" → 확인 대화(요청 부서·회신 기한 재확인) → 상태 공지로 전이, 요청서가 해당 부서의 S3 목록에 나타난다. 공지 후: "조건 수정" → 수정 저장 시 새 판본과 S5 이력, 상태는 유지. "회수"는 이번 범위에 없다. "구성안에서 보기" → S4의 해당 역할로 스크롤.
- (d) 필수 항목(역할명·과업·요청 부서·필수 역량 1개 이상·회신 기한) 중 빈 항목이 있으면 공지 버튼 비활성과 누락 항목 목록. 저장 중 412 `VERSION_CONFLICT`: "다른 사용자가 수정했습니다. 최신 내용을 불러온 뒤 다시 확인하세요"와 "다시 불러오기". 428 `VERSION_REQUIRED`는 클라이언트 오류이므로 요청 ID와 함께 표시. RFP 근거가 없는 역할(사람이 추가): 근거 항목에 "근거 없음 — 추가 확인" 표시, 공지는 가능.
- (e) 책임자·`manager`·`dept_staff`에게 편집 폼과 공지 버튼 숨김. 승인 대기 상태나 승인자 선택 UI 없음. 공지는 메일을 보내지 않으며 "발송" 문구를 쓰지 않는다. 확정 상태의 역할은 편집 불가.
- (f) 역할 상세·수정, 요청서 공지 전이: KAN-119/T04/T05/T09에서 정의. 판본은 `ETag`/`If-Match`, 상태를 만드는 POST는 `Idempotency-Key`를 따른다.

### S3 부서 후보 추천 `/tft/requests`, `/tft/requests/:requestId`

- (a) 부서에 배정된 요청서를 읽고 후보를 추천하며 경험·가용성 근거를 입력·보완한다. 주 사용자는 `dept_staff`다. 요청서 접근 범위는 아래 표를 따르며, 이 문서의 딥링크 규칙과 S2·S4의 요청서 링크도 이 표를 참조한다.

| 사용자 | 접근 범위 | 허용 행동 |
| --- | --- | --- |
| `dept_staff` | 소속 부서가 수신 부서인 요청서 | 읽기, 후보 추천·철회, 검증·가용성 기록, 보완 회신 |
| `sales` | 담당 프로젝트의 요청서 | 읽기 전용 |
| 프로젝트 책임자 (역할 무관, 사용자 ID로 판정) | 해당 프로젝트의 요청서 | 읽기 전용 |
| `manager` | 관리 대상 프로젝트의 요청서 | 읽기 전용 |

범위 밖 요청서는 목록에 없고 딥링크는 404 `NOT_FOUND`다(존재를 드러내지 않는다). 범위 안이지만 허용되지 않는 행동은 403 `FORBIDDEN`이며 화면에서는 해당 버튼을 미리 숨긴다. 목록 `/tft/requests`는 현재 사용자의 접근 범위 안 요청서를 보여주고 쓰기 버튼은 `dept_staff`에게만 보인다.

- (b) 목록: 프로젝트명, 역할명, 요청 부서, 요청 상태, 회신 기한, 추천 수, 보완 요청 여부. 상세: 요청서 읽기 전용 `dl`(S2와 같은 항목, 필수·우대 역량 분리 표시), 보완 요청 블록(책임자·`sales`가 남긴 요청 내용과 기한, 있을 때만), 후보 목록. 후보 카드: 후보 식별자·소속·"가상 시연" 표시, 추천 기록 블록(추천자, 추천 시각, 추천 이유, 유사 프로젝트·기간·실제 과업·근거 자료), 검증 기록 블록(검증자, 확인 시각, 기준별 배지 4개, 항목별 근거, 추가 확인사항), 가용성 상세(대상 기간, 투입률, 확인 주체, 확인 시각, 근거, 업무 제약).
- (c) "후보 추가": 후보 식별자 선택(부서 인력 목록, 가상 시연 표시) 또는 신규 입력, 추천 이유와 경험 근거 입력 → 추천 기록 생성. 첫 추천이 저장되면 역할 상태가 후보 추천 접수로 전이. "경험·역량 확인": 유사 경험·필수 역량·우대 역량 각각 확인/추가 확인/미충족과 근거 입력 → 검증 기록 생성·갱신. "가용성 확인": 사용자는 대상 기간·투입률·근거 3개를 입력하고 저장할 기준 상태(확인·추가 확인·미충족)를 고른다. 확인 주체는 현재 사용자, 확인 시각은 서버가 기록한다. 불완전 입력도 저장되며 그때 기준 상태는 "추가 확인"으로 기록한다. "확인"을 골랐는데 입력 3개 중 하나라도 비면 서버가 422 `EVIDENCE_REQUIRED`를 반환하고 기존 기록은 바뀌지 않는다. 검증 기록이 하나라도 저장되면 상태가 부서 검증으로 전이. "추천 변경": 기존 추천을 철회하고 다른 후보를 추천하면 이전 추천은 S5 이력에 남고 카드에 "철회됨" 표시. "보완 회신": 보완 요청에 답(자료 보완 또는 다른 후보 추천) → 구성안의 해당 역할 상태가 보완 요청에서 벗어나는 것은 책임자가 S4에서 다시 판단한다.
- (d) 목록 빈값: "배정된 요청서가 없습니다". 추천 전 상세: 후보 목록 자리에 `Empty`("아직 추천한 후보가 없습니다")와 "후보 추가". 가용성 입력 3개 중 누락: "추가 확인"으로 저장되고 카드에 누락 항목 안내. "확인"을 고른 채 저장하면 폼에서 누락 항목을 먼저 안내하고, 서버 422 `EVIDENCE_REQUIRED`도 같은 문구로 표시하며 기준 상태는 바뀌지 않는다. 추천자와 검증자가 같은 사람: 두 블록에 각각 이름을 표시하고 "같은 담당자가 추천과 확인을 수행"이라고 적는다. 역할이 확정된 뒤: 폼 비활성과 "확정된 역할입니다" 안내.
- (e) 접근 범위 밖 요청서는 위 표대로 404, 읽기 전용 사용자의 쓰기 행동은 403이며 버튼을 숨긴다. 추천 이유 없이 후보만 추가할 수 없다. 후보 기준 배지를 "확인"으로 바꾸려면 근거 필수. 소속·프로젝트명만으로 "유사 경험 확인"을 자동 표시하지 않는다. 후보에게 로그인 계정을 만들지 않으며 후보 ID를 사용자 ID 자리에 쓰지 않는다. 가용성 확인 주체는 현재 사용자로 서버가 기록하고 화면에서 바꿀 수 없다.
- (f) 내 부서 요청 목록, 요청서 상세, 후보 추천 생성·철회, 경험·역량 검증 기록, 가용성 확인 기록, 보완 회신: KAN-119/T04/T05/T09에서 정의. 부서 인력 목록은 조직 자료 어댑터(가상 시연)에서 제공하며 공개 자료를 개인 경험 근거로 쓰지 않는다.

### S4 후보 비교·TFT 구성안 `/tft/projects/:projectId/proposal`

- (a) 역할별 후보를 비교하고 팀 공백을 확인한 뒤 책임자가 확정하거나 보완을 요청한다. 책임자(확정·보완 요청. 역할 무관, 현재 사용자 ID와 프로젝트 책임자 관계로 판정), 책임자가 아닌 `sales`(비교·보완 요청·구성안 초안 정리), 책임자가 아닌 `manager`(읽기). 책임자인 `manager`·`sales`는 확정·보완 요청을 할 수 있다.
- (b) 머리글: 현재 판본 번호, 작성자·시각, 책임자 블록(S1과 동일), 확정 상태 요약("필수 역할 4개 중 확정 2, 보완 요청 1, 후보 없음 1 — 구성 완료 아님"). 역할별 비교 구간: 역할명·요청 부서·상태 배지, 후보 행(후보 식별자·소속·가상 시연, 기준 배지 4개, 유사 과업 경험 요약, 가용성 요약, 추천자·검증자, 근거 링크 → S3 카드), 한 후보가 다른 역할에도 올라 있으면 "다른 역할 제안 중: 역할명 (기간 겹침)" 표시. 역할마다 제안 후보 선택, 추천 이유, 남은 조건, 보강 필요 사유, 다음 담당자. 팀 공백 구간: 후보 없는 역할, 필수 역량 미확인 역할, 가용성 미확인 역할, 중복 투입 후보. 보완 요청 목록: 대상 역할·부서, 요청 내용, 기한, 상태.
- (c) `sales`·책임자: "제안 후보 선택"(역할당 1명 이상), "보강 필요 표시"(사유 선택: 필수 역량 추가 확인, 가용성 미확인, 후보 없음, 중복 투입), "보완 요청"(대상 부서·내용·기한 → S3에 노출, 역할 항목 상태 보완 요청), "구성안 저장"(새 판본 생성, 이전 판본 보존). 책임자만: "역할 확정"(기준 4개가 모두 확인인 후보가 선택된 역할만 활성, 역할 단위), "구성안 확정"(확정자 ID·대상 판본 기록. 남은 공백은 보완 요청 또는 다음 담당자가 기록돼 있어야 함). 판본 선택 → `/proposal/:version` 읽기 전용.
- (d) 구성안 없음: "아직 구성안이 없습니다"와 `sales`·책임자에게 "구성안 시작"(현재 추천·검증 기록으로 초안 생성). 책임자 미지정: 확정 버튼 비활성, 옆에 "책임자가 지정되지 않아 확정할 수 없습니다" 사유. 현재 사용자가 책임자가 아님: 확정 버튼 비활성과 "현재 책임자 홍길동만 확정할 수 있습니다". 필수 역량 추가 확인 또는 가용성 미확인 후보: 역할 확정 비활성과 "보강 필요" 배지, 사유 표시. 후보 없는 역할: "후보 없음" 배지와 다음 행동(담당 부서·회신 기한) 입력. 일부 역할만 확정: 요약에 "구성 완료 아님"을 유지하고 전체 완료로 표시하지 않는다. RFP 범위·가용성이 바뀐 뒤: 영향 역할에 "재검토 필요" 표시, 이전 판본은 그대로 둔다. 412: S2와 같은 안내.
- (e) 책임자가 아닌 `manager`·`sales`에게 확정 버튼은 보이되 비활성(사유를 알 수 있게). `dept_staff`는 S4 접근 불가(403). 추가 확인 상태의 후보를 확정으로 바꾸는 우회 없음. 구성안 판본을 덮어쓰는 저장 없음. 확정 후 후보 교체는 새 판본과 책임자 재확정이 필요하다.
- (f) 비교 데이터 조회, 구성안 판본 생성·조회, 역할 확정, 구성안 확정, 보완 요청 생성: KAN-119/T04/T05/T09에서 정의. 확정은 `If-Match` 필수이며 서버가 현재 책임자 여부를 검사한다(브라우저의 책임자 표시는 근거가 아니다). 허용되지 않는 전이는 409 `INVALID_TRANSITION`, 책임자 아님은 403 `FORBIDDEN`.

### S5 검증·변경 이력 `/tft/projects/:projectId/history`

- (a) 결정 근거와 재확인 대상을 확인한다. 접근 범위 안의 전원.
- (b) 판본 순 표(공통 변경 이력 형식): 시각, 변경자(사용자 표시명, 후보 ID 아님), 대상(요구·역할·요청서·후보 추천·검증·가용성·구성안·책임자), 이전 값, 이후 값, 사유. 필터: 대상 종류, 역할. 책임자 변경 행은 이전·신규 책임자와 사유를 함께 표시. 구성안 확정 행은 확정자와 대상 판본. 추천 철회·변경 행은 이전 후보와 새 후보. 각 행에서 관련 화면 딥링크(S2 역할, S3 카드, S4 판본).
- (c) 행 클릭 → 해당 객체 화면. "재확인 대상만 보기" 필터: RFP 범위·가용성 변경 이후 재검토 표시가 붙은 역할·후보.
- (d) 이력 없음: "기록된 변경이 없습니다". 커서 페이지.
- (e) 이력 수정·삭제 UI 없음. 원문 본문은 이력에 복제하지 않는다(C/S 감사 이력과 같은 원칙).
- (f) 프로젝트 이력 목록: KAN-119/T04/T05/T09에서 정의. C/S의 `GET /api/v1/cs/tickets/{ticket_id}/audit` 형식을 참고한다.

## 흐름과 화면 연결

```text
요구 → 역할 → 요청서 → 후보 → 비교 → 구성안 → 확정
S0/S1  S1/S2   S2 공지   S3     S4     S4 저장   S4 책임자
```

| 단계 | 화면 | 행위자 | 결과와 다음 화면 |
| --- | --- | --- | --- |
| 프로젝트·RFP 등록 | S0 → S1 | `sales` | 프로젝트 생성, 파일 등록, 분석 작업 202. S1에서 작업 상태 확인 |
| 요구·역할 검토 | S1 | `sales` | 기획상 도출 역할 확인, 역할 추가·수정. 역할 행 → S2 |
| 요청서 작성·공지 | S2 | `sales` | 작성 중 → 공지. 요청 부서의 S3 목록에 노출 |
| 후보 추천 | S3 | `dept_staff` | 추천 기록 생성. 공지 → 후보 추천 접수 |
| 경험·가용성 확인 | S3 | `dept_staff` | 검증 기록 생성. 후보 추천 접수 → 부서 검증 |
| 비교·공백 확인 | S4 | `sales`, 책임자 | 부서 검증 → 후보 비교. 보강 필요·보완 요청 → S3에 보완 요청 노출 |
| 구성안 정리 | S4 | `sales`, 책임자 | 판본 저장. 후보 비교 → 구성안 검토 |
| 확정 | S4 | 책임자 | 역할 확정·구성안 확정. 구성안 검토 → 확정. S5에 기록 |
| 변경 추적 | S5 | 전원 | 책임자 변경, 추천 변경, 재검토 대상 확인 |

상태 전이는 역할 단위다. 한 프로젝트 안에서 역할마다 다른 상태가 공존하며 S1 역할 표와 S4 요약이 이를 보여준다. 전이는 사용자의 행동(공지, 추천 저장, 검증 저장, 보완 요청, 판본 저장, 확정)으로만 일어나고 AI 작업 `SUCCEEDED`가 역할 상태를 바꾸지 않는다.

딥링크 규칙:

- S1 역할 행 → `/tft/projects/:projectId/roles/:roleId`
- S2 "접수된 추천 n건" → `/tft/requests/:requestId` (S3 접근 범위 표에 따라 `sales`는 읽기 전용)
- S3 상단 "프로젝트 현황" → `/tft/projects/:projectId` (`dept_staff`는 S1을 읽기 전용으로 보되, 요청 부서 외 역할의 후보 상세는 보이지 않는다. 범위는 KAN-78 권한 구현에서 확정)
- S4 후보 행의 근거 링크 → `/tft/requests/:requestId#candidate-:candidateId` (S3 접근 범위 표에 따라 책임자·`sales`·`manager`는 읽기 전용, 범위 밖은 404)
- S4 역할 블록 "요청서" → S2
- S5 행 → 대상 객체 화면과 판본
- 보완 요청 생성 시 S3 목록의 해당 요청서에 "보완 요청" 표시. 알림은 보내지 않는다.

## 시연 시나리오 체크리스트

두 시나리오 모두 가상 시연 데이터다. 후보·경험·가용성 전부에 "가상 시연" 표기가 보여야 한다. 체크 항목은 각 단계에서 화면에 보여야 하는 것이다.

### 대표: 해저케이블 RFP (기획서 4.6, 후보 A~D)

1. S0 — `sales` 계정. "프로젝트 등록"으로 해저케이블 프로젝트 생성, RFP 파일 등록. 목록에 프로젝트 행, 책임자 "미지정", 출처 "가상 시연".
2. S1 — RFP 분석 작업 상태가 `RUNNING`에서 `SUCCEEDED`로. 역할 표에 설계·생산계획·품질시험·시공 4개, 모두 작성 중, 출처 "기획상 도출", 각 역할의 근거 조항 링크. 책임자 블록에 "책임자 미지정 — 구성안 확정 불가" 안내.
3. S1 — 관리 `manager` 계정으로 전환. "책임자 지정"에서 이 프로젝트의 `sales` 1명 선택, 사유 입력. 책임자 블록 갱신, S5에 지정 행.
4. S2 (시공) — `sales` 계정. 요청 부서 시공, 필수 역량 "해상 설치 조건·시공 위험 검토 역량", 우대 역량 "유사 해저 시공 참여 경험", RFP 근거 조항·페이지·원문 링크, 투입 조건과 회신 기한. 미정 항목은 "미정" 표시. **핵심 시점 1(부서 요청 전)**: 역할·요청 부서·우대 경험·RFP 근거가 한 화면에 보인다. "공지" → 상태 공지.
5. S2 (설계·생산계획·품질시험) — 같은 방식으로 공지. S1 역할 표 4개 모두 공지.
6. S3 목록 — 각 부서 `dept_staff` 계정. 자기 부서 요청서만 보인다. 다른 부서 요청서 딥링크는 404.
7. S3 상세 — 설계 부서: 후보 A 추천, 유사 경험 확인(해저 설계 프로젝트·기간·실제 과업·근거), 필수·우대 역량 확인, 가용성 대상 기간·투입률·근거 입력 후 "확인"으로 저장 → 확인 주체·확인 시각이 서버 기록으로 표시. 추천자와 검증자가 같은 사람으로 각각 표시. 상태 후보 추천 접수 → 부서 검증.
8. S3 상세 — 품질 부서: 후보 B, 생산 부서: 후보 C 같은 방식. C는 가용성 근거를 비운 채 "추가 확인"으로 저장 → 저장되고 가용성 "추가 확인" 배지와 누락 항목 안내. 같은 상태에서 "확인"으로 저장을 시도하면 422 `EVIDENCE_REQUIRED` 안내와 함께 기준 상태 유지.
9. S3 상세 — 시공 부서: 후보 D 추천. 경험 근거는 육상 설치뿐 → 유사 경험 "추가 확인", 필수 역량(해상 설치 조건·시공 위험 검토) "추가 확인". "미충족"이 아니라 "추가 확인"으로 표시된다.
10. S4 — `sales` 계정. **핵심 시점 2(후보 추천 후)**: 역할 4개 × 후보 A~D 비교표. A·B 확인, C 가용성 추가 확인, D 필수 역량·유사 경험 추가 확인. 팀 공백 구간에 "시공: 필수 역량 미확인", "생산계획: 가용성 미확인". D에 "보강 필요 — 필수 역량 추가 확인" 표시.
11. S4 — "보완 요청": 시공 부서에 "해상 시공 경험 자료 보완 또는 다른 후보 추천, 외부 보강 가능성 표시" 요청, 기한 입력. 생산 부서에 가용성 근거 요청. 시공·생산계획 역할 항목 상태 보완 요청. 구성안 저장 → 판본 1.
12. S3 (시공) — `dept_staff` 계정. 보완 요청 블록이 보인다. 자료 보완 또는 다른 후보 추천 회신. 이 시연에서는 "외부 보강 필요"로 회신하고 D의 필수 역량은 추가 확인 유지.
13. S3 (생산) — C의 가용성 근거 입력 후 "확인"으로 저장 → 확인 배지, 확인 주체·확인 시각 표시.
14. S4 — 책임자(`sales`) 계정. **핵심 시점 3(책임자 검토 후)**: 설계 A·품질 B·생산계획 C 역할 확정(기준 4개 모두 확인). 시공은 역할 확정 버튼 비활성, "보강 필요" 사유와 다음 담당자(시공 부서)·후속 요청 기록. 구성안 확정 → 판본 2, 요약 "필수 역할 4개 중 확정 3, 보완 요청 1 — 구성 완료 아님".
15. S4 — 책임자가 아닌 `manager` 계정으로 전환. 확정 버튼 비활성, "현재 책임자 ○○○만 확정할 수 있습니다" 표시. 판본 1을 열면 읽기 전용.
16. S5 — 책임자 지정, 4개 요청서 공지, 추천·검증, 보완 요청, 판본 1·2 저장과 확정 행이 시각 순으로 보이고 변경자는 사용자 표시명이다.

### 보조: GIS RFP §3.5.19 (기획서 4.7, 후보 E·F)

1. S0 → S1 — GIS 프로젝트. 요구 요약에 "본체 공급 제외, 단말 키트 공급, 설치 포함"과 근거 조항. 역할 표에 설계·설치(시공) 2개.
2. S1 — 책임자 지정(관리 `manager`).
3. S2 — 설계·설치 요청서 공지. 설치 역할 필수 역량에 설치 경험 조건.
4. S3 (설계) — 후보 E 추천. 설계 경험 확인, 설치 경험은 입력하지 않음 → 설치 관련 항목은 설계 역할 기준이 아니므로 표시 없음. 가용성 확인.
5. S4 — 설계 E 확인. 설치 역할 "후보 없음" 배지와 팀 공백 구간에 "설치: 후보 없음, 다음 담당자 시공 부서, 회신 기한". 요약 "필수 역할 2개 중 확정 가능 1, 후보 없음 1 — 구성 완료 아님". 설계 접수만으로 전체 완료로 표시되지 않는다. E를 설치 역할에 올리면 설치 역할 기준에서 유사 경험 "추가 확인"으로 따로 표시된다.
6. S3 (시공) — 후보 F 추천. 경험 확인, 가용성은 근거 없이 "추가 확인"으로 저장 → 저장되고 "추가 확인" 배지.
7. S4 — 책임자. 설계 E 역할 확정. 설치 F는 가용성 추가 확인이므로 역할 확정 비활성 → "보완 요청"(시공 부서, 가용성 확인 요청). 구성안 확정 시 설치 역할은 보완 요청 상태 유지, 요약 "구성 완료 아님".
8. S3 (시공) — F의 가용성 근거 입력 후 "확인"으로 저장 → 확인 배지. S4에서 책임자가 설치 역할 확정 → 새 판본, 요약 "필수 역할 2개 중 확정 2". 이전 판본 보존.
9. S5 — 두 판본과 보완 요청, 가용성 확인 행 확인.

가상 후보 시험 사례(기획서 4.7 목록)와 화면 표시 대응: 유사 경험 충분(A·B) → 확인, 다른 과업 경험만(D) → 추가 확인, 경력 근거 부족 → 추가 확인과 근거 요청, 가용성 미확인(C·F) → 가용성 추가 확인과 확정 비활성, 같은 시기 중복 투입 → S4 "다른 역할 제안 중 (기간 겹침)" 표시와 병행 가능 여부 확인 요청, 후보 없는 역할(GIS 설치) → 후보 없음 배지와 다음 담당자, 부서 추천 변경 → S3 철회 표시와 S5 행.
