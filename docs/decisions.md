# 프로젝트 의사결정 정리

기준일: 2026년 10월 22일. 이 문서는 팀원이 현재의 기획, 기술 선택과 배포 방향을 읽고 이해하기 위한 결정 요약이다. 확정된 방향과 실제 구현 상태를 구분한다.

아래에는 확정한 선택, 선택 이유와 감수하는 제약을 기록한다. 기술적 적합성 설명은 성능 실측 결과와 구분하며 품질·지연·비용은 평가로 확인한다.

개발 기준은 [최종 C/S DOCX](https://drive.google.com/file/d/12lSqCl6DiYLkstFWcZno5MqNKv_kJ2AC/view)와 [최종 RFP DOCX](https://drive.google.com/file/d/1zolHAa_hHtQeNyc1dIV7btO0HK3pRmcR/view)다. 기획서를 다시 수정하지 않고 모호한 출력·평가·출처 정의만 개발 계약으로 구체화한다. 담당 및 개발 범위는 이 보완으로 변경하지 않는다.

## 선택의 기준

우선순위는 11월 3일까지 두 업무를 통합 배포하고, 11월 10일에 사람이 확인하고 결정하는 전체 흐름을 시연하는 것이다. 팀원이 AI를 잘 활용한다는 전제는 개발 속도를 높이는 근거지만 인증, 권한과 근거 추적을 생략하는 근거는 아니다.

교육장 GCP와 Gemini를 활용해 초기 계정 및 비용 부담을 줄인다. 다만 모델 선택은 제공 여부만으로 끝내지 않고 평가 결과로 검증한다. 개발 분업을 위해 업무와 배포 경계를 나누되, 발표 후 상시 운영하지 않는 범위에 맞춰 환경 수와 중간 승인 절차는 줄인다.

이 기준에 따라 어떤 선택은 개발 독립성을, 어떤 선택은 구현 및 운영 부담 감소를 우선한다. 모든 구성 요소를 최대한 분리하는 것이 일관된 목표는 아니다.

## 목표와 일정

전력기기 제조사의 해외 C/S 문의 대응과 RFP 자사 대응·협력사 보완을 지원한다. AI는 분석, 근거와 초안을 준비하고 사람이 발송 및 업무 결정을 확정한다.

| 항목 | 결정 |
| --- | --- |
| 개발 및 통합 배포 완료 | 2026년 11월 3일 |
| 발표 | 2026년 11월 10일 |
| 최종 목표 | 배포 환경에서 두 업무와 평가 화면을 시연 |
| 완성도 | 실제 운영할 서비스에 필요한 인증, 권한, 이력과 실패 처리를 갖추는 방향 |
| 발표 후 | 계속 운영할 계획은 없음 |
| 제출물 | 소스코드, 기획서, 발표자료 등을 분리해 제출하고 같은 최종 버전을 연결 |
| 일정 운영 | AI 활용을 전제로 개발하되 실제 진행 속도와 막힌 작업에 따라 조정 |

스프린트는 10/21~10/27 공통 기반과 평가 실행, 10/28~11/3 기능 완성과 통합 배포, 11/4~11/10 안정화와 발표 준비로 나눈다. 기존 작업의 완료 예정일과 선후관계를 유지해 앞 단계의 결과를 다음 단계에서 사용하도록 구성했다. 평가 기반을 먼저 만들고 발표 주에 새 기능을 추가하지 않기 위한 분할이다. 작업별 배정과 Jira 적용 상태는 [Jira 백로그](https://lsteam4.atlassian.net/jira/software/projects/KAN/boards/1/backlog)에서 관리한다.

## 서비스 범위

| 구분 | 포함하는 업무 |
| --- | --- |
| C/S 문의 대응 | 원문 문의 분석, 규칙 기반 우선순위 및 부서 배정, 근거 검색, 답변과 정보 요청 초안, 담당자 확인 후 메일 발송 |
| C/S 개선요청 | 반복 고장, 확인된 펌웨어 문제와 문서 문제 검토, 부서 요청 및 회신, 조치와 추가 발생 추적 |
| RFP 대응 | RFP 문서·판본 등록과 조항 추출(취소선 등 편집 흔적 반영), 요구별 자사 대응 판정(근거 있음·조건부·사양 차이·판단 근거 부족), 보완 경로와 가상 협력사 후보 등급, 고객 질문, 변경 제안 승인, 제안 초안·검토본·내보내기 |
| 공통 기능 | Microsoft 로그인, 실제 메일 읽기 및 발송, 파일과 원문 관리, 평가 실행 요청과 결과 조회 |

RFP 시연은 14번 유닛 변전소 규격서 한 건을 대표로 쓰고 협력사는 가상 프로필이다. 외부 메일 발송, 실제 업체 접촉, 자동 가격, 도면 설계, 외부 에이전트 연동은 이번 범위에 포함하지 않는다.

C/S 문의 종결과 개선요청 완료는 별도로 관리한다. RFP 대응도 산출물 상태와 판단 상태를 구분하며 승인된 변경 제안만 요구에 반영한다. 검토본 작성은 입찰 통과·수주와 별개다.

C/S 개선 검토의 초기 기준은 최종 기획서에 따라 일반 고장에 최근 90일 내 서로 다른 고객 3곳, 해당 고장에 적용 가능한 수정 펌웨어가 이미 배포된 경우 고객 1곳, 문서 문제에 확인된 오류 근거 1건이다. 이는 시연용 초기 정책이며 실제 도입 시 회사 데이터와 처리 여력으로 조정한다. RFP 관련 메일의 AI 분류는 후보 제시이며 프로젝트 연결과 등록은 사람이 확인한다.

| 선택 | 선택 근거 | 감수하는 제약 |
| --- | --- | --- |
| 실제 메일은 포함, 회사 시스템 연동은 제외 | 요구: 메일 가져오기와 발송까지 포함하도록 지정했다. 설계 이유: 외부 시스템 접근을 기다리지 않고 문의 접수부터 사람의 확인 및 회신까지 시연할 수 있다. | ERP나 CRM과의 실제 업무 연결 및 데이터 동기화는 검증하지 못한다. |
| 프로젝트 2를 RFP 자사 대응·협력사 보완으로 변경 | 요구: 2026-10-28 사용자가 TFT 팀 구성을 RFP 자사 대응·협력사 보완(KAN-7)으로 바꿨다. 설계 이유: 실제 RFP 조항을 읽어 자사 제품 근거·사양 차이·보완 경로를 판단하는 흐름이 제공 데이터로 검증 가능하다. | TFT 인력 구성 코드는 제거했고(KAN-181, 복원 기준 `1d17f84`) 협력사는 가상 프로필이라 실제 업체 조건을 증명하지 않는다. |
| C/S에 개선요청까지 포함 | 요구: 사용자가 개선요청 포함 여부를 확인하고 확정했다. 설계 이유: 한 문의에 회신하는 업무와 반복 문제를 개선하는 업무를 모두 보여준다. | 문의 종결과 개선 완료를 별도로 추적해야 하므로 상태 관리가 늘어난다. |
| AI는 근거와 초안, 사람은 발송과 최종 결정 | 요구: 두 프로젝트의 공통 기획 원칙이다. 설계 이유: 생성 결과의 불확실성을 업무 확정 권한과 분리한다. | 완전 자동 처리율보다 검토 가능한 근거와 승인 이력이 우선이다. |

개선 검토의 수치 기준은 실무 통계로 최적화한 결과가 아니다. 일반 고장은 반복성을, 펌웨어 및 문서 문제는 확인된 오류 근거를 중심으로 검토한다는 정책을 시연용 값으로 구체화한 것이다.

## 서비스 실행 구조

C/S 업무 백엔드와 TFT 업무 백엔드에 더해 공통 플랫폼 API를 독립 서비스로 배포한다. 총 세 서비스는 각각 빌드하고 배포하며, 순수 공통 코드와 데이터 계약은 패키지로 공유한다.

```mermaid
flowchart TD
    W[통합 웹] --> P[공통 플랫폼 API]
    P --> C[C/S 백엔드]
    P --> T[TFT 백엔드]
    P --> D[공유 PostgreSQL DB]
    C --> D
    T --> D
    P --> M[Microsoft 로그인과 메일]
    P --> F[Cloud Storage]
    T --> Q[Cloud Tasks 문서 처리]
    P --> J[Cloud Run Jobs 평가 실행]
    Q --> D
    J --> D
```

공통 플랫폼은 로그인과 메일, 파일, 평가 관리 API 및 브라우저의 업무 API 요청 중계를 맡는다. 실제 평가는 Cloud Run Jobs에서 실행한다. React 정적 파일은 별도 공개 Cloud Run 웹 서비스가 제공한다.

서비스 배포는 독립적이지만 플랫폼 장애는 두 업무의 웹 접근에 영향을 준다. DB도 공유하므로 DB 장애와 자원 경합은 공통으로 영향을 준다.

| 결정 | 선택 근거 및 비교한 안 | 감수하는 제약 |
| --- | --- | --- |
| C/S와 TFT 업무 백엔드 분리 | 요구: 사용자가 모듈화와 개발 분업을 이유로 업무 백엔드 두 개를 선택했다. 설계 이유: 서로 다른 업무 상태와 API 변경을 각 앱에서 다룰 수 있다. | 앱 사이의 데이터 계약과 통합 테스트가 필요하다. |
| 공통 API를 독립 서비스로 배포 | 요구: 공통 기능을 C/S 앱에 함께 실행하는 초기 제안에 대해 사용자가 개발 과정의 독립성을 이유로 별도 서비스를 선택했다. 인증, 메일, 파일과 평가 API를 업무 앱의 배포 일정과 분리한다. | 세 번째 앱의 배포 및 설정, 내부 호출 인증이 추가된다. 플랫폼을 거치는 요청은 플랫폼 가용성에도 의존한다. |
| DB 인스턴스 1개와 DB 1개, 스키마 및 계정 분리 | 요구: 같은 인스턴스에서 논리 DB를 나누는 안과 비교한 뒤 한 DB 구성을 선택했다. 설계 이유: 공통 사용자와 업무 자료의 연결 및 마이그레이션 관리를 단순하게 하면서 쓰기 소유권은 나눈다. | 물리적 격리가 아니므로 장애와 자원 경합을 공유한다. 스키마 이름만 나누지 말고 DB 접속 권한도 제한해야 한다. |

독립 서비스 선택과 공유 DB 선택은 서로 다른 문제를 해결한다. 전자는 개발 및 배포 경계를, 후자는 현재 규모에서 데이터 관리 부담을 조정한 결정이다. 서비스가 분리됐다는 이유로 DB까지 독립됐다고 설명하지 않는다.

## 기술 스택

| 영역 | 선택 | 설계 해석과 확인할 제약 |
| --- | --- | --- |
| 백엔드 | Python 3.11 이상, FastAPI | 규칙, 데이터 처리와 AI 호출을 같은 언어로 개발하고 API 계약으로 프론트와 분업한다. 처리량 우위를 실측해 고른 것은 아니다. |
| 프론트 | React, Vite, TypeScript, TanStack Query | 업무 및 평가 화면의 API 데이터, 로딩과 오류 상태를 일관되게 다루는 구성이다. UI 키트 없음은 확정 사항이며 특정 키트보다 우수하다는 비교 기록은 없다. |
| 실행 환경 | GCP Cloud Run, 서울 리전 | 세 FastAPI 앱을 컨테이너 단위로 독립 배포하는 요구에 맞춘다. 최소 인스턴스 1은 시연 응답성을 우선한 설정이며 유휴 비용을 감수한다. 초기값은 CPU 1, 메모리 512MiB, 최소 1·최대 2 인스턴스이며 부하 평가로 조정한다. |
| LLM | Gemini | 교육장 키로 시작하는 진입 부담이 낮다. 가장 정확하거나 저렴하다는 결론은 아니며 지원 목록, 품질, 지연과 비용 평가로 모델 ID를 고른다. |
| 임베딩 | Gemini 다국어 임베딩 | 다국어 원문을 직접 검색 대상으로 삼아 번역 단계를 추가하지 않는다. 언어별 검색 품질은 평가가 필요하며 모델 ID와 차원은 미정이다. |
| 검색 | PostgreSQL FTS와 pgvector | 제품 코드 및 규격 같은 키워드와 의미가 유사한 표현을 함께 찾기 위한 구성이다. 권한 필터 후 후보를 RRF로 결합하고 재정렬한다. 결합과 재정렬의 품질 이득 및 지연은 실측해야 한다. |
| DB | Cloud SQL PostgreSQL | 업무 데이터, 검색과 실행 상태를 PostgreSQL 중심으로 관리해 별도 저장소 수를 줄인다. 한 DB 안에서 서비스별 스키마와 접속 계정을 분리하며 실제 부하에서 경합을 확인해야 한다. |
| 파일 | Cloud Storage | 원문 및 첨부를 DB 행과 분리해 보관하고 인용 위치와 연결한다. 원문 판본과 파생 파일의 연결 및 변경 정책은 앱에서 구현해야 한다. |
| 인증 | Microsoft OAuth, MSAL, PKCE | 실제 메일 연동에 쓰는 Microsoft 로그인과 서비스 접근을 연결한다. 조직의 로그인 성공과 앱의 업무 권한은 별개로 검사한다. |
| 에이전트 | LangChain, LangGraph | 분류, 근거 검색, 초안과 사람의 확인을 단계 및 상태로 표현한다. 모든 단계를 별도 에이전트로 늘리는 근거는 아니며 상태 전이 검증이 필요하다. |
| 실행 상태 | langgraph-checkpoint-postgres | 실행 상태를 서비스 프로세스 밖에 보관하고 PostgreSQL 운영 구성을 재사용한다. 중단 후 재개 시 외부 작업이 중복되지 않도록 별도 검증해야 한다. |
| 추적 | LangSmith | 단계별 입력과 출력 및 실패 위치를 평가 결과와 연결하기 위한 선택이다. 요금제, 기록 범위와 민감정보 처리 정책은 미정이다. |
| 문서 비동기 처리 | Cloud Tasks | RFP OCR 및 임베딩을 API 요청 수명과 분리하고 작업 단위로 재시도하도록 설계한다. 중복 실행에도 결과가 중복 반영되지 않게 구현해야 한다. |
| 평가 및 초기화 | Cloud Run Jobs | 끝이 있는 평가 및 초기화 실행을 업무 API 프로세스와 분리한다. 실행 시작 지연과 자원 상한은 확인이 필요하다. |
| 주기 작업 | Cloud Scheduler | 메일 동기화의 주기 호출을 웹 앱 내부 타이머와 분리한다. 중복 호출과 동기화 체크포인트를 처리해야 한다. |
| CI/CD | GitHub Actions, Cloud Build, Artifact Registry | 변경 서비스의 CI와 이미지·배포를 분리한다. main의 동일 커밋 CI 성공 뒤 OIDC로 배포하며 빌드·배포 계정을 분리한다. |
| 비밀값 | Secret Manager | 키와 접속 비밀값을 코드 및 문서에 넣지 않고 실행 계정별로 제공한다. 접근 권한과 키 교체 절차는 별도 설정해야 한다. |
| 화면 진행 상황 | SSE | 서버에서 브라우저로 작업 진행 상태를 보내는 요구에 맞춘다. 재연결, 누락 이벤트 조회와 플랫폼 중계 경로의 타임아웃은 검증해야 한다. |

위 표는 [AGENTS.md](../AGENTS.md)와 현재 합의된 스택의 적용 이유를 풀어 쓴 것이다. 제품별 벤치마크나 모든 대안에 대한 비교 평가를 수행했다는 의미는 아니다.

Redis, Kubernetes, BigQuery, FAISS는 프로젝트 스택에서 사용하지 않는다. 모델 이름과 라이브러리 세부 버전은 확인 없이 임의로 고정하지 않는다.

설계 이유: 현재 요구는 PostgreSQL 중심의 업무 및 검색, 관리형 앱 배포와 유한한 비동기 작업으로 구성한다. 추가 저장소나 클러스터를 먼저 도입할 구체적인 부하 근거가 없으므로 운영 대상을 늘리지 않는다. App Engine, Cloud Functions와 Agent Platform 사용 여부도 논의했으나 현재 실행 구조에는 추가하지 않는다. 해당 제품들이 요구를 지원하지 못한다는 판단이나 성능 비교 결과를 뜻하지 않는다.

GCP와 Gemini는 교육장 제공 자원을 활용한다. 다른 분류 모델이나 임베딩 등이 필요해지면 사용자가 추가 비용을 검토한다. 제공된 모델을 기준선으로 시작하되 선택은 품질과 지연, 토큰 및 비용 평가로 검증한다. 반복 문서의 Gemini 명시적 캐시도 지원 모델 및 조건을 확인해 적용한다.

### Gemini API 호출 방식

기본 경로는 Gemini Developer API와 API 키다. 팀이 사용하는 키와 공통 Google Gen AI SDK를 재사용해 로컬 설정과 모델 비교의 부담을 줄인다. 로컬은 GEMINI_API_KEY, 배포 설정의 C/S와 TFT는 Secret Manager의 gemini-api-key:1을 사용한다. 웹과 플랫폼에는 모델 키를 주지 않는다. 키의 접근 권한, 유출 방지와 회전은 서버에서 관리한다.

초기 연결 모델은 gemini-3.6-flash다. 최종 업무 모델과 임베딩 차원은 같은 입력·정책에서 품질·지연·토큰·비용을 비교해 결정한다. API 호출 성공과 업무 품질 합격을 구분한다. 실행 방법은 [외부 연동 점검](integration-checks.md)을 따른다.

## 로그인과 사용자 권한

Microsoft 토큰은 서버에 보관하고 브라우저에는 세션 쿠키를 전달한다. 사용자 식별은 tid와 oid의 조합을 사용하며 이메일은 표시용이다. 로그인에 성공했다고 역할을 자동으로 부여하지 않는다. 한 사용자에게 여러 역할과 부서 및 프로젝트 범위를 지정할 수 있다.

| 역할 | 주요 업무와 범위 |
| --- | --- |
| cs_agent | 권한이 있는 C/S 문의와 개선요청 처리 |
| dept_staff | 소속 부서에 배정된 요청 회신. RFP 검토 부서면 조회·변경 제안·고객 질문 작성. 부서 지정 필수 |
| sales | 담당 프로젝트의 RFP 접수·문서·처리, 요구·대응표 검토, 보완 경로·후보 선택, 질문·회신·제안·승인, 초안 수정·검토본 저장 |
| manager | 주관회사 전체 운영 집계 조회, 지정된 C/S 관리 부서와 RFP 관리 프로젝트의 상세 조회, 담당 sales·책임자 지정 |

관리자의 집계 조회 권한은 개인 메일함 전체나 전체 직원 자료 열람 권한으로 확대하지 않는다. 메일과 첨부, RFP 원문·내보낸 파일은 접근 가능한 업무에 연결된 범위만 조회한다.

프로젝트 책임자(`responsible_user_id`)는 새 로그인 역할이 아니다. 관리 권한이 있는 manager가 `assignment` 경로로 담당 sales와 함께 지정 및 변경하며 변경자, 이전 및 신규 담당, 사유와 시각을 남긴다. 책임자는 sales 범위에 더해 변경 제안 승인·기각과 검토본 저장을 한다.

| 결정 | 선택 근거 | 감수하는 제약 |
| --- | --- | --- |
| 서버 로그인과 세션 쿠키 | 요구: 브라우저가 토큰을 받아 업무 API를 직접 호출하는 안과 비교해 서버 방식을 선택했다. 설계 이유: Microsoft 토큰과 메일 접근을 플랫폼에서 관리하고 브라우저의 호출 및 인증 경로를 통일한다. | 플랫폼 중계와 세션 저장, CSRF 방어 및 내부 사용자 맥락 전달을 구현해야 한다. |
| tid와 oid로 식별, DB에서 권한 관리 | 설계 이유: 표시용 이메일과 사용자 식별자를 분리하고, 로그인 여부와 회사의 업무 배정을 구분한다. 부서 및 프로젝트 범위가 다른 권한을 표현할 수 있다. | 사용자 등록과 권한 변경의 관리 주체 및 절차가 필요하다. |
| manager의 집계와 상세 조회 범위 구분 | 요구: 전체 운영 현황은 보되 상세 조회 및 재배정은 지정된 관리 범위로 확정했다. 설계 이유: 업무 조정에 필요한 가시성과 원문 자료의 접근 제한을 함께 유지한다. | 전체 집계를 볼 수 있어도 개별 상세는 열 수 없는 경우를 UI와 API에서 일관되게 처리해야 한다. |
| 프로젝트 책임자는 지정 관계로 관리 | 요구: 새 역할을 추가하지 않고 프로젝트별 책임자를 두기로 했다. 설계 이유: 같은 사용자가 프로젝트마다 다른 책임을 맡을 수 있고 승인 주체를 명확히 남긴다. | 전역 manager라는 이유만으로 승인할 수 없다. 시연은 자기 제안 자기 승인을 허용하므로 책임자 없이도 흐름이 돌고, 실제 도입 시 제안자·승인자를 분리한다. |

## 시연에 맞춘 RFP 대응 업무 흐름 (2026-10-28 범위 변경)

```text
RFP 접수와 문서(DOCX·PDF) 판본 등록
→ 처리 작업(조항 추출·요구 추출·자사 자료 검색·비교·보완 경로·후보 등급·초안)
→ 담당 sales의 요구·대응표 검토, 보완 경로·협력사 후보 선택
→ 고객 질문 작성과 회신 기록
→ 변경 제안(웹 수정·고객 회신·PDF 메모) 승인·기각
→ 초안 문장 수정, 검토본 저장, DOCX·PDF 내보내기
```

요구의 상태·성격·조건을 바꾸는 입력은 전부 변경 제안으로 들어오고 승인된 제안만 반영한다(승인 전 반영 금지). 재실행은 담당자가 손댄 요구를 덮어쓰지 않고 차이를 제안으로 남긴다. 자사 제품이 없다고 참여 불가로 끝내지 않고, 외부 보완 경로와 가상 협력사 후보를 등급과 근거로 비교한다. 상세 흐름과 경로는 [RFP API 명세](https://docs.google.com/document/d/1lh6blP9IqACKvr3nyPp7NuU07jOmliIvIH_h87HDu9g/edit)가 원본이다.

**선택 근거:** 제공 데이터에 협력사 자료가 없어 후보는 팀이 설계한 가상 프로필을 쓴다. 등급은 프로필에 적지 않고 후보×요구마다 계산해, 후보를 외워 답하는 것이 아니라 요구를 읽고 판단하는지 평가한다. 시연에서는 자기 제안 자기 승인을 허용해 계정·대기 단계를 줄이되, 감사 행에 제안자·승인자를 모두 남겨 실제 도입 시 분리할 수 있게 한다.

개발용 시연 사용자와 실제 Microsoft 로그인 사용자는 구분한다. 로컬 계정 선택은 개발을 앞당기는 수단이며 실제 Microsoft 로그인과 Graph 메일 연동이 된다는 증거는 아니다.

## 조직 자료와 실데이터 교체

공개 자료에 나온 회사 및 조직, RFP의 업무 분야, 프로젝트에서 필요한 역할과 서비스 로그인 권한을 분리한다. 설계, 토목/구조, 시공/운송, 품질/시험, 사업관리는 업무 분류이며 실제 부서명이나 로그인 역할을 대신하지 않는다.

공개 조직 자료는 관련 부서 후보를 찾는 근거로 활용한다. 개인의 경험과 가용성은 시연용 가상 자료 및 담당자 확인으로 준비한다. 자료에서 확인하지 못한 내부 조직과 경력을 AI가 만들어 채우지 않는다.

원천 데이터 어댑터가 CSV, 업로드와 메일을 공통 업무 모델로 변환한다. 실제 회사 데이터를 받으면 어댑터와 정책, 권한, 평가 사례를 교체 및 검증하는 구조로 설명한다. 가상 자료와 실제 자료의 출처 및 확인 시점도 구분한다.

**선택 근거:** 대화에서 사용자가 가정한 데이터를 쓰더라도 실제 현업 데이터를 받으면 인터페이스로 교체할 수 있음을 설명하고 싶다고 요청했다. 따라서 원본 필드와 형식에 업무 코드를 직접 묶지 않고 공통 모델로 변환하는 경계를 둔다. 공개 조직명, 업무 분류와 로그인 권한도 분리해 자료 교체가 곧 권한 변경이 되지 않게 한다.

이는 교체할 위치를 정한 설계이며 실제 회사 데이터의 무수정 적용을 검증한 결과는 아니다. 필드 의미, 식별자, 권한, 정책과 평가 사례를 맞추는 도입 작업은 남는다.

## 평가와 품질

모델을 먼저 고정하기보다 비교 가능한 평가 파이프라인을 먼저 구축한다. 화면에서 실행 설정, 진행 상태, 모델별 비교와 사례별 결과를 확인할 수 있게 한다. LLM, 임베딩, OCR과 재정렬 구현을 교체할 수 있는 인터페이스를 둔다.

품질뿐 아니라 토큰, 비용, 지연, 재시도, 오류와 캐시 사용을 실행별로 기록한다. 데이터셋과 설정, 프롬프트 및 모델 판본을 보존해 비교 조건을 맞춘다.

**선택 근거:** 사용자는 모델을 바꾸며 성능과 토큰 비용을 비교해 의사결정하고, 그 과정을 화면에서도 확인하고 싶다고 요청했다. 평가를 마지막 검수에만 두지 않고 모델 선택의 선행 조건으로 삼은 이유다. 화면은 실행과 실패 사례를 함께 검토하기 위한 도구이며 점수만 높게 표시하는 발표용 결과판이 아니다.

대신 평가 데이터 정리, 실행 기록과 비교 화면을 먼저 만드는 비용을 감수한다. 같은 모델이라도 프롬프트, 데이터와 재시도 조건이 다르면 결과를 단순 비교하지 않는다. 아직 측정하지 않은 품질 개선이나 비용 절감 수치를 선택 근거로 사용하지 않는다.

| --- | --- |
| 문의 유형 macro-F1 | 0.90 이상 |
| CRITICAL 누락 | SAFETY 및 SITE_DOWN 누락 0건 |
| 우선순위 | adjusted=N 부분집합에서 1.0000 |
| 긴급도 | macro-F1 0.70 이상, 비NONE 재현율 0.85 이상 |
| 담당부서 | 0.93 이상 |
| 출력 스키마 위반율 | 0 |

위 수치는 목표 기준이며 이번 세션에서 달성한 측정 결과가 아니다. TFT, OCR, 검색과 생성 초안의 합격선 및 부하 조건은 별도 확정이 필요하다. 최종 시험 자료를 반복 튜닝에 사용하지 않으며 사용 및 노출 이력을 확인한다.

기획서의 평균 정확도·규칙 일치율은 [평가 명세](evaluation.md)에서 macro-F1, 규칙 단독 재현 및 전체 파이프라인 지표로 구체화한다. 계산식·대상·제외 조건을 고정하고 규칙 단독 100%를 전체 AI 성능으로 표시하지 않는다. 보조 분류와 반품 하위유형의 정답 매핑 및 추가 합격선은 KAN-82·95에서 본실험 전에 잠근다.

규칙으로 결정되는 priority, assigned_dept와 product_family는 LLM에 맡기지 않는다. 설계 근거는 같은 입력의 결과를 재현하고 정책 변경과 모델 오류를 분리하기 위해서다. 문의 분류 LLM 출력은 category_code, secondary_category, urgency_flag, provided_info와 return_subtype 다섯 개이며 입력 화이트리스트는 build_input() 한 곳에서 관리한다. 보조 유형은 복합 의도 기록이며 규칙의 주분류를 자동 대체하지 않는다. 상세 허용값과 null 처리는 [C/S 계약](../contracts/cs/tickets.md)을 따른다.

안전 관련 CRITICAL 누락 0건과 FLT-042 인용 차단은 평균 점수로 상쇄하지 않는 기준이다. PHONE 채널의 긴급도 정답 누설과 SAFETY 표본 부족을 분리해 보고하고, test 597건은 2회 이상 사용하지 않는다. 합격선만 넘었다고 실제 현업 전체에서의 안전성과 성능이 입증됐다고 표현하지 않는다.

## 결정을 다시 검토할 조건

아래는 현재 범위를 늘리는 요구사항이 아니라, 이후 선택을 바꿀 때 확인할 근거다.

| 현재 선택 | 재검토할 조건 |
| --- | --- |
| 독립 플랫폼과 공유 DB | 공통 배포가 반복적으로 업무 개발을 막거나 DB 자원 경합 및 권한 격리 요구가 현재 구조로 해결되지 않을 때 |
| 로컬 개발과 공용 환경 한 세트 | 공용 배포와 데이터 변경이 검증을 반복해서 방해하거나 실제 운영에서 별도 검증 및 복구 환경이 필요해질 때 |
| Cloud Run 및 최소 인스턴스 1 | 실측 지연, 동시 처리량과 유휴 비용이 목표에 맞지 않을 때. 먼저 자원 및 상한 조정으로 해결되는지 확인 |
| Gemini 및 현재 검색 구성 | 합격선을 충족하지 못하거나 대안이 같은 조건에서 품질, 지연 및 비용 면에서 더 적합하다는 평가 결과가 있을 때 |
| 단일 회사 및 간소화한 승인 흐름 | 회사 간 자료 공유를 포함하거나 실제 조직 정책이 독립 검증 및 추가 승인 단계를 요구할 때 |
| 시연용 데이터와 초기 정책 | 실제 데이터의 필드 의미, 분포와 처리 여력이 현재 가정과 달라 재평가가 필요할 때 |

결정을 바꿀 때는 바뀐 요구나 측정 결과, 선택한 대안, 영향받는 API 및 데이터 계약과 일정까지 함께 기록한다.

남은 주요 결정은 시연 주관회사, 최종 생성·임베딩 모델과 차원, 평가·계정 관리 권한, LangSmith 요금제다. 구현된 기반과 업무 기능 완료를 구분한다.

## 개발 통합과 배포 방식

기능 브랜치에서 개발하고 dev 대상 PR을 검사·검토 후 Squash merge한다. 배포 담당자는 dev → main PR을 Create a merge commit으로 병합한다. main의 동일 SHA CI가 성공하면 변경된 서비스만 이미지 생성과 별도 CD를 수행한다. 배포 후 main → dev도 merge commit으로 동기화한다.

이 구성은 팀 개발 버전과 공용 시연 버전을 구분하기 위한 선택이다. 대신 장기 브랜치 동기화와 배포 판단을 담당자가 관리한다. 자세한 화면 순서는 [서비스별 배포 안내](service-delivery.md#오새결의-평소-배포-dev에서-main으로)를 따른다.

API 원본은 서비스별 Pydantic 모델·라우터이고 OpenAPI·TypeScript 타입·모의 예시를 생성한다. 공용 DTO 동시 수정을 줄이고 제공자·소비자가 작은 계약을 먼저 합의하기 위한 구성이다.

새 기능은 필요한 범위만 구현하고 pytest·Ruff·mypy·계약 및 소비자 검사를 실제 실행한다. CI와 검토자 확인 뒤 병합하며 필수 검증을 남긴 채 티켓을 완료 처리하지 않는다.
