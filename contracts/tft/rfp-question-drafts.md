# RFP 고객 질문 초안 엔진 (KAN-189)

`backend.engine.rfp.questions.generate_question_drafts(tree, requirements)`는
`ClauseTree`와 `Sequence[ExtractedRequirement]`를 받아 `list[QuestionDraft]`를 반환하는
순수 함수다. DB·모델·worker·HTTP 연결과 고객 발송은 포함하지 않는다.

각 초안은 `kind`, `sources: [{clause_no, quote}]`, `question`, `pre_reply_note`로 구성한다.
`quote`는 조항의 현행 제목·본문·표 칸 또는 그 안의 추출 인용을 그대로 보존한다.
복수 조항 불일치에는 양쪽 출처를 함께 싣는다. 출력은 입력 조항/요구 순서로 결정되며
자리표시자 → 불일치 후보 → 승인 절차 순서다. 동일 출처 쌍의 불일치 질문과 동일 `(clause_no, quote)`의 승인 질문은 한 번만 낸다.

## 유형과 판정 범위

| kind | 조건 | 회신 전 처리 |
| --- | --- | --- |
| `PLACEHOLDER` | 현행 제목·본문·표 칸에 `<Insert …>`, `TBD`, 빈 대괄호 `[ ]`, 밑줄 3개 이상, 또는 인용 전체가 한글 미정 표시(`미정`, `용량: 미정`, `납기: 별도 협의`). `납기는 별도 협의`처럼 문장 속에 든 한글은 미정이 아니다. 영문 표지는 문장 어디에 있어도 질문을 낸다(`has_placeholder`) | 미정 항목의 확정 값·단위 질문. 회신 전 해당 항목을 적합·부적합 판정에서 제외한다는 메모 |
| `INCONSISTENCY` | 서로 다른 조항에서 같은 상위 항목·장비·조건·항목 문구·값 제외 인용 구조가 확인되고 같은 `equipment_family`·`attribute_key`에 값·연산자·허용오차 차이 | 같은 장비인지와 적용 값·우선 조항 확인. 불일치 후보이며 부적합을 확정하지 않음 |
| `APPROVAL_PROCESS` | 현행 인용이 확인된 요구의 `approval_procedure_missing=true` | 승인 요청 방법·담당자·시점과 제출 자료 목록 질문. 대체 허용을 승인 완료로 취급하지 않음 |

삭제 값(`deleted_values`, 제목·표의 삭제 이력 포함)은 읽거나 복원하지 않는다.
현행 값으로 질문하며, 없는 조항·현행 원문에 없는 인용·인용에 없는 값은 비교에서 제외한다.
숫자 일부만 일치하는 오래된 값도 제외한다(현행 125의 25, 1,125의 125, 1.25의 25 등).
숫자와 연결되지 않은 문장 끝 마침표·쉼표는 정상 경계로 인정하고, 공백뿐인 값은 제외한다.
원문에 값이 없는 문장형 요구는 추측해서 비교하지 않는다.

## 불일치 비교 경계

- `kind=SPEC`만 비교한다. family가 `OTHER`/`None`, attribute_key가 `OTHER`, 값 없음,
  인용 내 자리표시자, 같은 조항의 복수 요구는 비교 대상이 아니다.
- 2026-10-31 사용자 정책 변경: 장비 동일성이 애매해도 일단 질문하던 이전 방침을 폐기한다.
  같은 속성 키만으로 충돌을 만들지 않는다. 다른 장비 형식/IP 표기·다른 인터페이스 주제는 동일 항목을 입증하지 못하면 생략한다.
- 실제 존재하는 서로 다른 직계 부모 조항(`parent_no`, 없으면 구조화 조항 번호의 바로 위 prefix)이 있어야 한다.
  상위 조항 레코드가 없거나 PART 수준이면 비교하지 않는다. 없는 문맥을 만들어 채우지 않는다.
  2026-10-31 사용자 추가 정책: 같은 부모의 형제는 택일 의미를 추론하지 않고 모두 생략한다.
  따라서 형제 안의 실제 모순도 놓칠 수 있다. 명시적 선택문 정규식이나 문서별 예외는 추가하지 않는다.
  서로 다른 부모라는 사실만으로 동일 항목을 인정하지 않으며 아래 장비·항목·조건·프레임 증거를 모두 요구한다.
- 장비 문구는 공백·대소문자 등 기존 표기 정규화 뒤 같아야 한다. 명시 식별자가 있으면 양쪽 ID 집합과
  ID를 제외한 장비 문구까지 같아야 한다. 같은 ID가 있어도 주/보조 장비 같은 장비 문구 상충을 덮지 않는다.
  `unit A`, `tag …`, `equipment/transformer/switchgear no./id/# …`만 명시 식별자다.
  `units/tagged/tags`나 `IP-54/IP-65`, 단독 `SWG-1`은 식별자로 추론하지 않는다.
- 비어 있지 않은 `attribute` 문구도 정규화 뒤 같아야 한다. 인용에서 값 한 곳·인접 단위·명시 연산자·기록된 허용오차를 비교값의 일부로 가린 나머지
  문장 구조가 같을 때만 동일 항목의 차이로 본다. 값이 여러 곳에 반복되거나 항목/문장 구조가 다르면 생략한다.
  값에 바로 붙은 `at least/at most`, `not/no less/more/greater than`, `greater/less than`,
  `minimum/maximum`, `>=/<=/≥/≤/>/</=`와 뒤쪽 `minimum/maximum/or greater/less/more/lower`만 가린다.
  허용오차는 입력 `tolerance`에 기록된 표현이 값/단위에 인접한 경우(괄호 또는 tolerance 표지 포함)에만 가린다.
  실제 `operator`·`tolerance` 필드는 바꾸지 않으며 그 차이는 기존 충돌 판정에 그대로 남긴다.
  다른 주제/일반 문구/떨어진 조건은 제거하지 않는다. 장비명 동의어·의미 모델·자유 문장 유사도로 다른 항목을 합치지 않는다.
- `conditions` 이름·값·단위를 정규화한 목록이 같을 때만 비교한다. 조건 순서는 무관하다.
  조건이 다르거나 한쪽에만 있는 경우 정당한 차이일 수 있으므로 불일치로 만들지 않는다.
  조건 이름의 동의어 및 상하위 조건의 논리적 포함 관계는 추론하지 않는다.
- 숫자는 Decimal로 비교하며 천 단위 쉼표·소수·과학 표기, Unicode 호환 문자,
  공백·일부 대시 표기의 동등성을 처리한다. 일반 텍스트는 대소문자를 정규화하지만
  단위는 원래 대소문자를 보존하며, 별도 필드 또는 단순 숫자 뒤 접미사에서 읽는다.
  `A/a`, `V/v` 등 명시적으로 등록한 안전한 표기만 공유한다. `MW/MVA`의 대문자 M을
  소문자 m으로 바꾸지 않는다. `mW`·`mw`·`mVA` 등 미지원·모호한 표기는 환산 없이
  숫자 표기와 단위를 문자열로 비교하며, `MW`와 동등 처리하지 않는다.
- 지원 환산: V/kV, A/kA, VA/kVA/MVA, W/kW/MW, s/ms, Hz/kHz, m/cm/mm,
  percent/%, °C/degC. 조건 값에도 같은 규칙을 적용한다. 기존 엔진에 재사용할 순수 환산 함수가
  없어 이 모듈의 작은 목록만 사용한다. API 모듈의 비공개 함수를 역참조하지 않는다.
- 미지원 단위·복합 단위·RMS/ASYM 수식어·범위·복합 수치·허용오차는 문자열로 보존한다.
  Decimal 표현·환산·비교 예외도 문자열 비교로 보호한다.
  동등성을 입증하지 못한 차이는 확인 후보다. 연산자가 다르거나 허용오차 표기가 다르면
  충돌을 확정하지 않고 우선 적용 기준을 질문한다. 텍스트의 의미 동등성은 추론하지 않는다.

## 승인 절차 질문의 입력 경계

요구 추출에서 제공한 `approval_procedure_missing`이 true일 때만 승인 질문을 만든다.
존재하는 조항의 현행 본문·제목·표 칸에 해당 요구의 비어 있지 않은 `quote`가 포함되어야 한다.
근거는 그 요구의 `clause_no`와 `quote`를 그대로 보존한다. 없는 조항·삭제된 인용·공백 인용은 제외한다.
승인 질문에는 `SPEC`, 장비 계열·속성 또는 수치 `value` 조건을 강제하지 않는다.
false일 때는 원문 표현과 관계없이 생성하지 않는다. 영어 정규식·주변 문맥으로 승인 의미나
절차의 충분성을 다시 추론하지 않으며, 추출 필드가 true이면 원문에서 승인 절차를 찾아 억제하지도 않는다.
요구 추출은 긴 절을 부분별로 처리하므로 다른 부분의 절차를 놓치면 질문이 더 생길 수 있다.
이 초안은 사람이 확인할 질문이며 승인 여부를 확정하지 않는다.

## 검증과 연결

`tests/tft/test_rfp_question_drafts.py`는 일반 합성 문장으로 현행/삭제 구분, 자리표시자,
다른 부모 분기의 동일 항목 양성·형제/다른 장비/항목/인터페이스의 억제, 명시 식별자와 하이픈/키워드 경계, 조건·단위 동등성,
단위 대소문자, Decimal 예외, 오래된 숫자 조각 배제, 승인 추출 필드와 현행 인용 경계를 검증한다. 실제 문서·정답·외부 API는 사용하지 않는다.
기존 `scripts/check_backend.py tft`는 `tests/tft`를 재귀 수집하므로 새 테스트도 CI 대상이다.
이 계약은 엔진 반환 형식이며 API 스키마·상태 전이·후속 판정 엔진은 변경하지 않는다.
