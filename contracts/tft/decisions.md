# KAN-127 구성안 판본과 책임자 결정 API

선행: KAN-122/#31, KAN-123/#37, KAN-125/#38. 모든 경로는 `/api/v1/tft/projects/{project_id}` 아래에 있다. 현재 업무 API partial 구현이며 운영 중계/화면 연결은 후속이다.

| 경로 | 동작 |
|---|---|
| POST `/compositions` | 담당 sales 또는 현재 책임자가 모든 역할을 후보/공백으로 기록. 항상 새 판본 생성. CONFIRMED 항목은 현재 책임자만 가능 |
| POST `/confirm` | 현재 책임자가 지정한 최신 구성안 판본 전체 확정. 미확인·미충족·중복 제안·인원 부족·이후 검증 변경이 있으면 422 |
| POST `/reject` | 현재 책임자가 현재 구성안 반려 사유를 추가 이력으로 기록. 반려된 판본을 재확정할 수 없고 새 판본 필요 |
| POST `/reopen` | 담당 sales 또는 현재 책임자가 확정된 프로젝트를 COMPOSING으로 재검토. 이전 확정 기록/판본 보존 |
| GET `/compositions/{version}` | 접근 범위 내 과거 판본 조회. 부서 담당자에게 다른 부서 구성안 공개하지 않음 |
| GET `/decisions` | after_version/limit으로 결정 이력 조회 |

POST는 프로젝트 판본 If-Match와 Idempotency-Key가 필수다. 요청서 판본과 다르다. 현재 권한 확인 후 동일 키/본문은 최초 응답을 반환한다. 다른 본문은409, 오래된 판본412, 누락428. 구성원/검증 주체·서버 시각을 입력으로 받지 않는다. 새 구성안은 현재 프로젝트와 선택 추천 중 synthetic/demo 출처를 보수적으로 보존한다.

프로젝트 행을 먼저 잠그고 해당 요청서 행을 잠근 뒤 현재 검증 근거를 읽는다. 추천 기록도 같은 프로젝트→요청서 잠금 순서를 사용해 확정과 동시에 가용성 변경이 통과하는 경쟁을 막는다. 업무 기록·프로젝트 판본·결정 이력·멱등 응답은 한 transaction이며 실패 시 전체 롤백된다. 확정 뒤 검증 기록 추가는 재검토를 먼저 열어야 한다.

구성안과 구성원은 추가 전용이며 과거 판본을 수정하지 않는다. 일부 역할 확정은 프로젝트 COMPOSING에 남는다. 전체 확정은 모든 역할 인원과 현재 검증이 충족되어야 하며 현재 책임자만 가능하다. 우대 역량도 화면 계약의 기준 4개 확인 조건에 맞춰 확인된 상태만 확정한다. 새 검증이 과거 판본 이후 발생하면 새 판본과 재확정이 필요하다. 반려 사유는 결정 이력으로 읽으며 KAN-125의 읽기 전용 검토 준비 상태 자체가 승인 가능 여부를 뜻하지 않는다.

## 차단된 범위

책임자 지정/변경 API는 아직 구현하지 않았다. `tft_app`은 identity 스키마를 읽을 수 없고 전달된 Principal은 현재 호출자 한 명뿐이다. 다른 후보 사용자의 활성 상태·sales 역할·관리 프로젝트를 검증하는 플랫폼 계약/조회 인터페이스가 없어 임의 사용자 ID를 승인하지 않는다. 새 DB 권한이나 다른 담당자의 인증 기능을 추가하지 않았다. 사용자/업무 권한 담당의 검증된 대상 사용자 조회 계약이 필요하다. 기존 프로젝트의 지정 책임자에 대한 결정 경로는 독립적으로 구현/검증했다.

역량 재검증 저장, 역할/요구사항 편집 이력 및 다른 프로젝트의 실제 투입 자료는 후속 통합이 필요하다. AI 구성안 초안 생성(KAN-126)은 다른 담당 범위이며 이 API는 사람이 제출한 구성안을 저장한다. 자동 생성/메일 발송/배포 없음.
