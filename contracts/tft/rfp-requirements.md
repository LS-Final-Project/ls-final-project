# RFP 자사 대응 요구 추출 (KAN-185, A04)

원본: [RFP API 명세 v1.3](https://docs.google.com/document/d/1lh6blP9IqACKvr3nyPp7NuU07jOmliIvIH_h87HDu9g) §4.3(extract 단계)·§4.4(요구 응답), 기획서 최종본 3.2(평가 기준)·4.2·5.2. 입력은 [조항 트리](rfp-clauses.md)이고 저장 구조는 [RFP 데이터 계약](rfp-data.md)의 `requirements`·`requirement_versions`·`requirement_conditions`다.

| 원본 | 파일 |
| --- | --- |
| 입력 구성·지시문·출력 검사·빠진 문장 보완 | `backend/engine/rfp/requirements.py` |
| 채점(재현율·정밀도, 건수 병기) | `backend/engine/rfp/scoring.py` |
| 로컬 평가 실행 | `scripts/rfp_requirements_eval.py` |

엔진은 순수 함수이고 모델 호출은 주입한 함수(`provider`)가 한다. 실제 연결은 `generate(client, settings, prompt, response_schema=ResponseSchema)`다. DB 저장과 처리 작업(rfp.process의 extract 단계) 연결은 A07(KAN-188)이다.

## 흐름

1. **입력** `build_inputs(tree, ["2.4", "2.5"])`: 절마다 하위 조항의 **현행 텍스트**와 상위 조항 문맥(`path`)을 모은다. 취소선으로 지운 값은 보내지 않는다. 반환 타입은 평탄한 `list[ExtractionInput]`이며 요청 절 순서와 절 안 원문 조항 순서를 유지한다. 길이에 관계없이 요청 절마다 입력 하나를 반환한다. 새 한글 장·조·독립 숫자 leaf 절에 하위 본문이 없으면 머리 조항의 본문·표를 한 번만 입력으로 사용한다. 기존 영문 절 선정·하위 조항 입력은 유지한다. 나눔과 부분 결과 합산은 `extract_section`이 맡는다. 모든 부분은 원래 `section_no`·`section_title`·`clause_no`·`path`를 유지한다.
2. **모델**: Gemini 구조화 출력으로 요구를 낸다. 요구 하나는 장비 하나의 속성 하나 또는 과업 하나다.
   - 출력 항목: `clause_no`, 근거 `quote`, `kind`, `equipment`, `task`, `attribute`, `value`, `unit`, `operator`
   - 값에 붙은 `conditions`(2차 전압별, 115℃ 상승 등), `standard_system`, `necessity`, `designated_model`, `designated_manufacturer`
   - 연산자 기준(v6): 최소 요구는 `GTE`(문구가 '이상'이거나, 내전류·차단 용량·연속 전류처럼 더 높은 정격이 요구를 만족하는 양), 최대 제한은 `LTE`, 고정된 지정값(계통 전압, 고정값으로 적힌 절연 수준·공칭 정격)은 `EQ`, 범위는 `RANGE`다.
   - 조건 이름(v6): `conditions.name`은 어휘(`vocabulary.ConditionName`) 안의 값 또는 `OTHER`다. 자사·협력사 사양 근거의 조건 이름도 이 어휘 안에 있어야 한다(검사가 확인). `OTHER`면 `value`에 원문 문구를 그대로 둔다. 응답 스키마는 enum 하나다.
   - v3 의미 칸(같은 호출 안, 추가 호출 없음). `value`·`unit`·`conditions`·`quote`는 원문 그대로다.
     - `attribute_key`: 같은 물리량인 내부 사양 항목 하나 또는 `OTHER`. 장비 자체의 형식을 적은 문장(개폐 기기, 설치 방식, 절연 방식)은 측정값과 따로 `form` 요구 1건으로 낸다. 부품, 부속, 재질, 체결, 연동, 표시, 배선, 접근, 기능은 형식이 아니라 `OTHER`다(v10). 그 문장의 극수는 `number_of_poles`로 따로 낸다. 헷갈리기 쉬운 키(정격 전류·프레임 AF, 저압 Icu·Ics·고압 정격 단락 차단 전류·단시간 내전류, Ue·정격 최대전압·변압기 1·2차 전압, 극수, 정격 용량, 권선 재질, 보호 기능)의 공학 의미는 `vocabulary.ATTRIBUTE_HINTS` 한 곳에 두고 지시문에 넣는다. 값이 도면·별도 지정이라 없어도 그 물리량의 키를 단다(값 null). 부품·부속·보조 회로(제어 전원, 보조 접점, 배선, 퓨즈, 커패시터, 저항, 피뢰기, 계기용 변성기)의 정격과 계통 조건(공칭 전압, 상·선 수, 주파수, 접지)은 장비 정격 키가 아니다(계통 조건은 함께 적힌 정격의 `conditions`, 없으면 `OTHER`)(v11)
     - `equipment_family`: 제품 계열 하나 또는 `OTHER`. 과업·문서 요구는 null. `LV_SWITCHGEAR`(v8)는 저압 배전반·스위치기어 조립품과 그 구획이고 그 안의 차단기는 `LV_BREAKER`다. 자사 제품이 없는 계열이라 자사 비교는 후보 없음이고, 협력사 저압 후보(`PROFILE_FAMILIES`)가 조립품·차단기 요구를 함께 받는다
     - `tolerance`: 원문 허용 오차 표기 그대로 또는 null. 범위 계산은 코드가 한다
     - `certification_listed`: 원문이 Listed·labeled 등록을 요구할 때만 true
     - `assembly_clause`(v4): 여러 장비를 한 조립품·단일 공급 책임으로 납품하라는 요구일 때만 true, 장비가 나열되기만 하면 false. 통합 책임 판별(`rfp/integration.py`)의 입력이다. 처리 흐름 연결은 후속이다
     - `approval_procedure_missing`(v5): 대체품·동등품·목록 밖 제조사를 승인 조건부로 허용하는데 받은 본문 안에 승인 절차·제출 자료가 없을 때만 true. 대체 불허이거나 절차가 적혀 있으면 false. 고객 질문 판별의 입력이다(영어 정규식 대신 의미 판단). 한계: 긴 절은 부분별로 추출되므로 절차가 다른 부분에 있으면 true가 될 수 있다. 오탐은 질문이 하나 더 생기는 안전한 방향이다
     - `basis_of_design`(v7): 특정 제품을 대체 불가 지정이 아니라 설계 기준으로 들고 동등 이상을 허용할 때만 true다. 이때 제품명은 `value`(연산자 `TEXT`)에 두고 `designated_model`·`designated_manufacturer`는 null이다. 함께 보내면 `validate_output`이 지정 칸을 비운다.
     - `canonical_value`(v7): 문장으로 적힌 값의 비교용 표기 또는 null. `value`·`quote`는 원문 그대로다. 탭은 `±NxS%` 또는 `+Nx-MxS%`(곱하기는 영문 소문자 x), 보호 기능은 L·S·I·G 순서의 문자 집합이다(예 `LSI`). 표기는 `vocabulary.CANONICAL_FORMS` 한 곳에 있다. 그 속성의 표기가 아니면 `validate_output`이 지우고 `needs_review`로 둔다. 형식만 검사하고 의미 대조는 하지 않는다. 판정 사용은 후속 PR이다.
     - 어휘·계열은 `backend/engine/rfp/vocabulary.py` 단일 원본이다. 사양 사실 형식(`partners.schemas.Attribute`)도 같은 목록이고, 자사 사양 파일은 그 부분집합이다(검사가 확인)
     - 지시문은 목록과 '모르면 OTHER, 비슷한 말로 추측하지 않음'을 싣는다. 예시는 14번 문구를 쓰지 않는다
   - 명령문("Provide…", "Comply with…")도 요구로 읽는다.
   - `<Insert value>` 같은 빈 값은 값 그대로 남겨 고객 질문으로 보낸다.
   - 가격·표준 납기는 뽑지 않는다.
3. **검사** `validate_output`: 근거가 원문에 없으면 버리고 이유를 남긴다(`rejected`).
   - `UNKNOWN_CLAUSE`: 없는 조항
   - `QUOTE_NOT_IN_CLAUSE`: 인용이 그 조항 현행 텍스트에 없음(지운 값을 쓰면 여기서 걸린다)
   - `VALUE_NOT_IN_QUOTE`: 수치 값이 인용에 없음
   - 문장형 요구(`operator=TEXT`)의 값이 인용에 없으면 모델이 바꿔 쓴 말이므로 **값만 비우고 요구는 남긴다**(`value_dropped`).
   - 의미 칸 검사(v3). 요구를 버리지 않고 `needs_review`로 표시한다. `needs_review`는 코드만 정하며 응답 스키마에 없다.
     - 목록 밖 `attribute_key`·`equipment_family`·조건 이름은 엄격 검사 전에 `OTHER`로 바꾸고 검토로 둔다. 응답 전체를 스키마 위반으로 버리지 않는다
     - `tolerance`가 인용 안에 그대로 없으면 지우고 검토로 둔다
     - 값이 숫자인데 인용에 허용 오차 표기(±, +/-, +0/-5, tolerance, plus or minus)가 있고 `tolerance`가 비었으면 검토로 둔다
   - 지정 모델·제조사는 그 조항 현행 텍스트에 토큰으로 있을 때만 남긴다(앞뒤가 ASCII 영숫자면 다른 낱말이다). 모델명은 영숫자 2자 이상이고 숫자만이면 안 된다. 없으면 **그 칸만 비우고 요구는 남긴다**(`designated_dropped`). 모델명에서 제조사를 짐작한 값(SEL-751A → Schweitzer), 취소선으로 지운 옛 모델, 원문에 없는 모델이 여기서 걸린다. 모델이 비면 제조사도 비운다.
   - 필수 여부 규칙(KAN-161). 모델이 `necessity=UNDETERMINED`로 냈는데 인용, 없으면 그 조항 입력의 상위 조항 문맥(`path`, 가까운 상위부터)에서 처음 만난 표현이 의무(shall·must·is/are required to·Provide 등 명령문 첫머리, 한글 '-야 한다'·'-야 하며'·'할 것')면 `MANDATORY`로 올리고 코드 전용 칸 `necessity_by_rule=true`로 남긴다(저장하지 않는다). 처음 만난 표현이 선호·허용(should·may·preferred·optional·is recommended, 권장·바람직·문장 끝 '수 있다')이면 올리지 않는다. `PREFERRED`·`CONDITION_BOUND`·`MANDATORY`는 바꾸지 않는다. 처리 worker와 평가 스크립트가 같은 `validate_output`을 지난다.
4. **빠진 문장 보완** `coverage`: 조항을 문장으로 나눠, 요구 문장마다 채택한 요구의 인용이 겹치는지 본다. `:`로 끝나는 머리글은 요구 문장에서 뺀다. 빠진 문장이 있으면 **그 문장만** 모아 한 번 더 부른다. 보완 결과도 원 조항 기준으로 같은 검사를 받는다. 그 밖의 자동 재시도는 없다.
5. **같은 조항 일반 의무 합치기** `merge_general`: 보완까지 끝난 뒤, 같은 조항에서 어휘 키가 없는(`OTHER`) 줄 가운데 종류·필수 여부·대상·과업·연산자·단위·규격 체계·계열이 같고 지정품·조건·허용 오차가 없으며 값이 서로 다르지 않은 줄을 한 줄로 합친다. 인용은 첫 인용부터 끝 인용까지의 원문 연속 구간, 속성은 원래 속성을 ` · `로 잇는다. 인증(`COMPLIANCE`)은 규격마다 따로 비교하므로 합치지 않는다. 합친 인용이 4000자, 속성이 200자를 넘으면 합치지 않는다. 문장마다 일반 의무 한 줄씩 나와 검토 화면 줄이 늘어나는 것을 막는다(KAN-188).
6. **차단 방식 붙이기**: 장비 이름에 차단 방식(MCCB·ACB·VCB)이 없으면, 상위 조항 첫머리가 한 방식만 말할 때(`_switching_from_path`) 또는 같은 첫 단계 조항 묶음의 인증 요구가 차단기 규격 하나만 말할 때(UL 1066·ANSI C37.13 → ACB, UL 489 → MCCB, `switching_from_standards`) 장비 이름 뒤에 `(방식)`을 붙인다. 자사 비교가 다른 방식 차단기 정격으로 충족 처리하지 않게 한다(`comparison._switching`).

모델에 주는 스키마(`ResponseSchema`)는 엄격 모델(`ExtractionOutput`)과 필드가 같다(코드만 정하는 `needs_review`·`necessity_by_rule` 제외). 다른 점은 `extra=forbid`가 없다는 것이다. Gemini가 `additionalProperties`를 받지 않아서(400 INVALID_ARGUMENT) 이렇게 둔다. 받은 응답은 엄격 모델로 다시 검사한다.

## 지정품 (명세 v1.3 §5.1·§11, 판본 `rfp-requirements-v2`)

`designated_item(requirement)`이 `{manufacturer, model, clause_no}`를 돌려준다. `designated_model`이 null이면 null이다(API `designated_item`도 null).

- `manufacturer`는 원문에 제조사 이름이 적혀 있을 때만 채운다. 14번 2.6.E.5 `SEL-751A`, 2.7.B `PowerLogic ION 9000`은 조항에 제조사 이름이 없어 null이다.
- 응답의 `clause_id`는 저장(A07 KAN-188)이 `clause_no`로 `tft.clauses`에서 찾아 `requirement_versions.designated_clause_id`에 넣는다. `procurement`는 저장 기본값 `SPECIFIED_PROCUREMENT`이고 추출은 정하지 않는다.
- 허용 제조사 목록(2.1 MANUFACTURERS)은 지정품이 아니다.
- v2는 지시문과 출력 칸이 바뀌었다. 아래 측정치는 v1 결과다.
- 14번 실측(v2, gemini-3.6-flash, 1회, 2026-10-30): 2.6 지정품 1건 `SEL-751A`(2.6.E.5), 2.7 지정품 1건 `PowerLogic ION 9000`(2.7.B), 둘 다 제조사 null, 원문 대조로 비운 칸 0건. 2.6 채택 74·버림 16(모두 `VALUE_NOT_IN_QUOTE`), 요구 문장 포괄 65/69. 2.7 채택 39·버림 0, 포괄 35/36. 2.6·2.7은 정답을 만들지 않아 재현율·정밀도는 없다.

## 긴 절 나눠 부르기 (`split_input`)

`build_inputs`는 절 전체 길이와 관계없이 절마다 입력 하나를 반환한다. `extract_section`이 `split_input`으로 나눠 부르고 요구와 결과를 합산한다. `split_input`은 본문(표 행 포함)이 `PART_CHARS`(4000자)를 넘으면 첫 단계 하위 조항 묶음 단위로 순서대로 나눈다. 절 전체가 목표 길이 이하면 입력을 그대로 반환한다. 첫 단계 묶음이 목표 길이(`limit`, 기본 4000자)를 넘으면 그 묶음만 개별 하위 조항 경계로 같은 목표 길이에 맞춰 재묶는다. 개별 조항은 자르지 않으므로 목표 길이를 넘는 조항은 단독 부분이 된다. 조항 순서·번호·문맥을 보존하며 중복 호출하지 않는다. `split_input`은 `build_inputs`의 개별 조항 길이·부분 수 사전 검사를 거친 입력을 전제한다.

- 기존 절 전체 12000자 제한은 **개별 조항** 제한으로 이동한다. 개별 조항 본문(표 행 포함)이 12000자를 초과하면 문장·표를 강제로 자르지 않고 `RFP_SECTION_TOO_LONG`으로 호출 전에 거부한다.
- 절별 재분할 결과는 `MAX_SECTION_PARTS`(12부분)까지 허용하며 초과하면 `RFP_SECTION_TOO_MANY_PARTS`로 호출 전에 거부한다. `build_inputs`에서 `split_input(item)`의 실제 추출 부분 수를 검사한다. 최초 호출 최대 12회 + 부분별 빠진 문장 보완 최대 12회 = 절별 논리 호출 최대 24회다. 공급자 전송 재시도는 이 수와 별개로 공급자 정책을 따른다.

- `extract_section`은 원래 절의 모든 부분이 `VALID`일 때만 `VALID`다. 실패한 부분이 있으면 그 결과 코드이고, 성공한 부분의 요구는 남기며 `parts_failed`로 드러난다. 문장 포괄 분모는 실패한 부분까지 포함한 원래 절 전체 요구 문장 수다. 부분별 요구·실패·포괄 집계도 `extract_section`이 담당한다.
- 입력 생성의 `RFP_SECTION_TOO_LONG`·`RFP_SECTION_TOO_MANY_PARTS`는 `ValueError`다. worker는 해당 절을 건너뛰고 `needs_review`로 남기는 흐름을 유지한다.
- v1 측정 절(2.4 2510자, 2.5 3972자)은 상한 아래라 나뉘지 않는다. 2.6의 기존 실측은 2부분, 실패 0이며 목표 길이 초과 묶음 재분할 변경 후 실측은 미실행이다.

부분 응답이 출력 상한에 닿으면(`MAX_TOKENS`) 잘린 응답은 버리고 그 부분을 조항 경계로 둘로 나눠 한 번만 다시 부른다. 조항이 하나면 나눌 수 없어 실패로 드러난다. 반쪽이 또 잘려도 더 나누지 않는다. 재시도는 절 호출 상한 `MAX_SECTION_CALLS`(24) 안에서만 하고, 남은 부분마다 2회와 반쪽의 4회를 남길 수 없으면 하지 않는다. 그래서 부분이 많은 절의 앞쪽 부분은 재시도되지 않을 수 있다. 잘린 호출의 사용량은 합계에 든다.

## 번호 빈자리 표시와 모델 경계 보정 (KAN-188, `rfp-structure-repair-v1`)

조항 트리는 계속 코드가 만든다. 모델은 코드가 표시한 자리에서 **경계만** 낸다(문서 파싱 업계 방식: 결정 파싱 먼저, 어려운 곳만 모델).

- 표시(`clauses.detect_structure_gaps`, 모델 없음): `build_clause_tree`가 끝에 `numbering_issues`에 `STRUCTURE_GAP`(detail `이유: 번호들`)을 더한다. 기존 `GAP`·`DUPLICATE` 등은 그대로다.
  - `LATE_START`: 첫 하위가 `.b`·`.2`처럼 시작 번호가 아니다. `SKIP`: 형제가 `.c` 다음 `.e`처럼 건너뛴다. 둘 다 빠진 번호가 3개 이하일 때만이고, 고칠 조항은 문서 순서상 바로 앞 조항이다.

## 설비 검토묶음·병렬 추출·이미지 전사 (KAN-188)

- 요구는 여전히 속성·과업 단위다. 화면은 동일 문서의 원문 절(숫자절 상위 두 단계)과 정확한 장비/과업 표기를 기준으로 **검토묶음**을 만든다. 같은 실물 장비라는 확정이나 장비 전체 충족 판정이 아니다. 공통/미분류 요구는 별도로 남기고, 자사 근거·사양 차이·조건·부족을 합산해 보여 준다. 협력사 근거는 해당 요구 판본과 프로필 판본이 일치하는 실제 저장 등급만 사용한다.
- worker의 `extraction_concurrency` 기본값은 6이며 허용 범위는 1~6이다(2026-11-06, 로컬 원장 동시 호출 상한 6과 같다). 서로 다른 절을 최대 6개까지 병렬 추출하되, 절 안의 입력 분할·누락 문장 보완은 기존 순서를 유지한다. 결과는 원문 절 순서로 결합하고 모든 추출 후 기존 단일 업무 트랜잭션에 저장한다. 취소·lease 상실·정산 불명 시 새 호출을 중단하고 이미 시작한 호출의 종료·정산을 기다린다. 호출 수·비용 감소나 처리 시간 단축 배수를 보장하지 않는다. 추출 호출의 thinking 수준은 `TFT_EXTRACTION_THINKING_LEVEL`(기본 `LOW`, 2026-11-06. 비우면 모델 기본)이고, 평가 실행기는 `--thinking-level`로 같은 값을 준다(실행기 기본은 미설정이라 운영과 같게 재려면 `--thinking-level LOW --structure-repair`를 준다). 맥락 정리는 `TFT_CONTEXT_THINKING_LEVEL`(기본 미설정)이며 LOW는 묶음 품질이 크게 떨어져 쓰지 않는다.
- 로컬 TFT 원장은 같은 token/job의 실행 중 예약만 최대 6개(`MAX_PARALLEL_TFT_CALLS`) 허용한다. 프로세스 메모리의 예약 ID와 DB의 RESERVED 집합이 정확히 일치해야 다음 예약을 만들 수 있다. 이전 실행의 예약, 다른 job의 예약, UNKNOWN은 계속 차단한다. CS는 순차 호출을 유지한다. 알려진 사용량은 호출별로 정산하며 중단 시 이미 발생한 호출 비용을 취소하지 않는다.
- 이미지 처리는 `backend/engine/documents/vision.py`의 별도 단계다. DOCX 본문 내장 이미지와 PDF의 이미지·벡터 도형이 있는 페이지에서 **눈에 보이는 글자·표**를 전사하고, 아래 단선도 계약에 따라 별도 연결 후보를 만든다. 누락 정격이나 설계 적합성을 추론하지 않는다. DOCX 페이지 번호는 생성하지 않으며 후보 위치는 원문 측정값이 아닌 정규화된 AI 관측 좌표다. PDF는 실제 페이지 번호, DOCX는 본문 이미지 순번을 출처로 남긴다.
- 문서별 최대 16개, 개별 8 MiB, 합계 32 MiB다. 지원하지 않는 형식·한도 초과·빈 전사·불완전 전사는 누락 경고로 남긴다. native PDF 본문과 정확히 같은 줄은 제거하지만 유사 문장의 중복까지 보장하지 않는다. 모든 문서의 native 입력을 OCR 호출 전에 검사하며, 이미지 전용 문서는 OCR 이후 최종 입력을 검사한다. 사용 가능한 요구 입력이 전혀 없으면 0건 성공으로 저장하지 않는다. 단, `DRAWING`에서 유효한 단선도 노드가 확인되면 요구 0건과 도면 후보를 구분해 저장할 수 있다.
- OCR 조항은 `OCR-DOCX-0001.*` 또는 `OCR-PDF-P0001.*`로 원문 위치를 추적한다. 추출 요구는 항상 `needs_review=true`이고 자사 확정 근거는 조건부로, 협력사 확정 등급은 검토필요로 제한한다. 화면에서도 원문 확인을 요구하며 OCR 문장을 native 원문 좌표로 밑줄치지 않는다. OCR 검토 완료를 별도로 확정하는 자동 기능은 없다.
- `DocumentDetail.extraction_warnings`는 기본값 `[]`인 추가 응답 필드다. 문서 접근 권한 확인 후 정확한 최신 판본의 `OCR-REVIEW-*` 안내 조항을 조회한다. 이 안내 필드 자체는 조항 저장을 사용한다. 별도 도면 후보 저장은 아래 신규 테이블을 사용한다. 기존 처리 완료 판본은 자동으로 OCR하거나 재분석하지 않는다. 새 원문 판본 처리부터 적용한다.


## 단선결선도 연결 후보 (KAN-188)

- 대상은 새로 처리하는 `RFP_SPEC`, `ADDENDUM`, `DRAWING`의 이미지·벡터 도형이다. 기존 처리 결과를 자동 재분석하지 않는다. 이미지 OCR과 같은 한 번의 호출에서 `diagram`을 추가 수신한다. 장비 태그·종류·인쇄 정격·근거·위치와 연결선 후보를 별도 보존하며, 이를 요구사항이나 자사/협력사 적합성 판정에 자동 삽입하지 않는다.
- 원문 파일은 변경하지 않는다. DOCX 내장 이미지의 원 bytes, PDF는 모델에 전달한 단일 페이지 PDF bytes를 별도로 보존한다. 후자는 전체 원본 PDF의 해당 byte 구간과 동일하다는 뜻이 아니며 벡터를 래스터로 바꾸지 않는다. 개별 SHA-256·MIME·크기·문서 판본·원문 SHA와 결속한다. 지원하지 않는 형식/한도 밖 이미지는 원문에 남으며 경고한다. 직접 crop·회전·뒤집기·숨김 표시가 있는 DOCX 이미지는 원 asset을 보존하지만 표시범위 밖 내용을 해석하지 않도록 호출을 생략한다. 모든 Word 스타일 상속/렌더러 지원은 보장하지 않는다.
- 그래프는 최대 노드 80개·연결 160개, 위치는 전체 제공 이미지/페이지 기준 0~1000이다. 선 교차만으로 접속을 확정하지 않는다. 불명확하면 `UNRESOLVED`와 근거·불확실성을 남기며, 다른 페이지의 인쇄 참조는 `CROSS_PAGE`로 보존하고 목표 장비를 자동 연결하지 않는다. 모든 그래프는 `review_required=true`이고 전기적 설계 승인·보호협조·실제 전류 방향 판정이 아니다. 잘못된 그래프는 경고로 분리하며 정상 OCR까지 버리지 않는다.
- `tft.document_diagrams`는 정확한 문서 판본당 불변 manifest 1개다. 원문 SHA 일치와 단일 업무 트랜잭션을 적용한다. `tft_app`은 SELECT, `tft_worker`는 SELECT/INSERT만 갖는다. 동일 manifest는 skip, 상이한 덮어쓰기는 거부한다. 업무 트랜잭션 실패 시 미참조 asset이 남을 수 있으며 사용자 원문을 삭제하지 않는다.
- `GET /api/v1/tft/documents/{document_id}/diagrams?document_version_id=UUID`는 해당 프로젝트 접근 권한과 문서/판본 일치를 검사한다. `NOT_ANALYZED`는 기록 없음, `ANALYZED`는 기록 있음, `PARTIAL`은 경고를 포함한다. 후보가 없다는 것과 도면이 없다는 확정은 다르다. 반환되는 `requirement_links`는 같은 프로젝트 최신 요구의 equipment에서 인쇄 태그가 정확히 일치한 후보이며, 중복 태그를 단일 실물로 합치지 않는다.
- `GET /api/v1/tft/documents/{document_id}/diagrams/{source_id}/image?document_version_id=UUID`는 같은 권한 검사를 거쳐 저장 bytes의 SHA·크기를 검증한다. PDF/PNG/JPEG/WebP만 attachment/nosniff로 전달하고 저장 경로를 노출하지 않는다. 웹·플랫폼 중계는 이 정확한 경로에 한해서 이미지 MIME을 허용한다.
- 화면은 원본 확대/내려받기와 점선 후보 표시, 장비·연결 선택, 관측 근거·미확정 영역·같은 태그의 요구 링크를 제공한다. 위치는 AI 추정이며 실제 치수 측정이 아니다. 업무 완료 후 같은 판본 조회를 갱신하고, 이전 판본의 늦은 응답을 새 판본 화면에 섞지 않는다.
