# RFP 제안 검토 초안 엔진 (KAN-188)

`backend.engine.rfp.draft.build_draft`는 공개 업무 스냅샷에서 결정적 템플릿으로
`backend.api.tft.rfp.schemas.Draft`를 반환하는 순수 함수다. 모델·DB·파일·worker·라우트·발송·
검토본 저장·내보내기 연결은 포함하지 않는다. 기존 snapshot/출력 계약을 재사용하기 위해
이 엔진에서 API 스키마 타입을 참조하는 경계는 이번 작업의 승인된 설계다.

## 입력과 책임 경계

키워드 인자:

- `project_id`, `version`, `data_origin`, `known_at`: 호출자가 제공하는 프로젝트·초안 메타데이터.
- `requirements: Sequence[RequirementDetail]`: 최신 요구 전체와 현행 인용·판정·재검토 표시.
- `integration: IntegrationResponsibility`: 공개 API의 서버 계산 근거 조항과 사람의 책임자 지정.
- `comparisons: Sequence[Comparison]`, `options: Sequence[SupplementOptions]`: 요구에 대응하는 자사 비교·보완 선택지.
- `selections: Sequence[SupplementSelected]`, `partners: Sequence[PartnerCandidate]`,
  `questions: Sequence[Question]`: 최신 사람 선택·가상 협력사 후보/요구별 등급·고객/내부 질문.
  이들 목록과 비교·선택지는 생략하면 빈 목록이다.

시계나 난수를 호출하지 않는다. 문장 ID는 프로젝트 ID를 namespace로 하여 초안 판본·절·문장·
근거 참조로 계산하는 UUID5다. 같은 협력사가 복수 보완 경로에 있으면 경로를 문장에 표시하고
서로 다른 ID와 조건을 유지한다. 입력은 변경하지 않는다. 요구/질문/후보는 식별자 순,
선택지는 rank·path 순, 절은 `DraftSection` 순으로 출력한다.

호출자는 접근 권한, 동일 프로젝트 소속, 최신 스냅샷 선택 및 인용이 **현행 원문**임을 검증한다.
이 함수는 원문 전체나 DB를 받지 않으므로 인용의 진위·프로젝트 소속·최신 원격 판본을 다시 조회하지 않는다.
내부의 공개 참조·비교 판본·보완 선택지 판본은 다음과 같이 검증한다.

- 중복 요구 ID, 요구당 중복 비교/선택지/사람 선택, 중복 질문/후보 ID, 중복 경로/요구별 후보 등급을 거부한다.
- 비교 `requirement_version`과 선택지 `version`은 해당 요구 `version`과 같아야 한다.
  비교 행 자체 `version`, 사람 선택 `version`, 질문 `version`은 독립 판본이므로 요구 판본과 비교하지 않는다.
- 비교/선택지/사람 선택/질문/후보 등급의 요구 참조와 요구 links의 질문/협력사 참조를 확인한다.
  허용/통합 근거 조항 및 질문의 조항 참조는 제공 요구의 origin 조항에서 찾는다.
  요구와 조항이 함께 있는 질문은 그 요구의 조항과 같아야 한다.
- 파트너 경로의 후보는 제공 협력사와 해당 요구의 등급이 있어야 한다. 다른 경로의 후보 코드는
  제공 비교 결과의 자사 제품 코드에서 찾는다. 단독 제품 코드로 제품을 새로 만들지 않는다.
- 사람 선택은 존재하는 허용 경로와 그 경로 후보에 한정한다. 차단 경로·금지된 외부 경로·
  제외된 협력사를 사람 선택으로 제공해도 추천으로 바꾸지 않고 오류로 거부한다.
- 통합 필요 여부와 근거 조항 목록, 번호·ID 대응을 확인한다. 근거 없는 통합 책임 문장을 만들지 않는다.
- 비어 있는 요구 원문/코드, 비어 있는 질문, 스냅샷 간 data_origin 불일치,
  비교 불가인데 MEETS/DIFFERS라는 모순도 거부한다.

검증 실패는 `RFP_DRAFT_*`의 `ValueError`다. 빈 초안으로 실패를 숨기지 않는다.
이 함수가 소비하지 않는 변경 제안 ID·과거 초안 문장 ID는 여기서 조회하거나 검증하지 않는다.

## 절과 표현

| 절 | 근거에 따른 내용 |
| --- | --- |
| `CUSTOMER_GOAL_SCOPE` | 고객 요구의 현행 인용의 건수/대표로 제안 검토 범위를 표시. 별도 근거 없는 고객 목표를 만들지 않음 |
| `OUR_RESPONSE` | 문서 근거가 있는 자사 후보의 대표 속성·요구값·후보값·비교 결과의 집계. 적용 범위·조건·제한을 보존 |
| `DEVIATIONS` | 사양 차이 판정 기록, 자사/대체 사양 보완 경로의 검토안 |
| `PARTNER_SUPPLEMENT` | 허용된 협력사 경로·후보의 가상 프로필과 요구별 등급, 미확인 조건 |
| `ASSUMPTIONS_EXCLUSIONS` | 조건부/근거 부족·보류·내부 가정, 통합 책임의 확보 여부와 미확보 조건 |
| `QUESTIONS_NEXT_ACTIONS` | 요구의 다음 확인 담당, 고객 질문 또는 내부 부서의 다음 행동 |

항상 여섯 절을 반환하고 근거 자료가 없는 절은 빈 문장 목록으로 둔다. 고객 목표 자유문장과
일반 가정을 발명하지 않는다. 선택지는 검토안/미선택으로 표시하며 사람 선택도 이행 확약으로 바꾸지 않는다.
`CONDITIONAL`·`INSUFFICIENT_EVIDENCE`·`SPEC_GAP`, 조건부 필수와 미정 항목·판정 미확인,
후보의 적용 조건과 자료 제한, R&D `PENDING`/`WAIVED`, 재검토 표시는 조건/미확인으로 남긴다.
제공된 `spec.tolerance`는 원문 그대로 조건에 보존하며 null을 허용 오차 없음으로 확정하지 않는다.
`needs_review`(시스템 추출 검토 표시)와 `needs_rereview` 중 하나라도 true이면 관련 문장의
`needs_rereview`·`unconfirmed`에 반영한다. 두 입력 필드 자체를 수정하거나 같은 의미로 저장하지 않는다.
모든 문장은 `provenance_kind=system_record`이며, 사람 입력의 내용을 인용해도 코드 생성 문장 자체를
사람이 승인한 문장으로 표시하지 않는다. 근거 있음은 해당 요구의 기록이며 전체 공급 가능 판단이 아니다.

자사 후보의 문서 근거가 비어 있으면 그 후보 문장은 만들지 않는다. 차단 경로와 EXCLUDED 후보는
추천하지 않는다. 공급·납기·보증·수주를 확약하지 않으며 가상 프로필의 납기/보증을 실제 계약으로 복사하지 않는다.
통합 책임이 미확보이면 조립·공장 시험·연동·보증 확인 조건과 제공 fallback 경로를 보존하고 유닛 공급을 확정하지 않는다.
책임자가 지정되어 있어도 입력의 책임자 기록일 뿐 공급 확약이 아니다.

분류는 `target`만으로 결정한다. CUSTOMER는 고객 확인 질문, INTERNAL은 내부 다음 행동으로 표시한다.
엔진 입력인 읽기 `Question` DTO는 `target_dept=None` 또는 자유 문자열을 허용한다. 부서가 없거나 공백이면
`담당 부서 미정`, 알려지지 않은 부서 코드면 `담당 부서 지정됨`으로 보수 표시하며 고객 질문으로 바꾸지 않는다.
쓰기 `QuestionCreate`의 INTERNAL 부서 필수 검증은 유지하며 엔진에서 새 질문 생성 권한/검증을 대신하지 않는다. DRAFT는 초안·미발송,
OPEN은 확인된 질문이지만 발송 여부는 별도 확인, REPLIED는 회신 수신 기록이며 판정 반영은 별도 확인이다.
회신을 받았다는 사실만으로 요구의 조건/상태를 해소하지 않는다. `shown_in_draft=true`인 내부 가정은
질문 근거와 함께 표시하고 충족 판정에 사용하지 않는다는 문구를 유지한다.

## 그룹 요약과 문장 상한 (2026-10-31 시연 품질 보완)

요구마다 문장을 반복하지 않고 장비 문구·판정 상태·보완 경로·사람 선택 여부별로 요약한다.
과업은 공개 입력 `spec.task`가 있을 때만 과업으로 구분한다. 근거 부족/과업은 건수와 대표 항목으로 표시한다.
자사 비교는 같은 장비/상태/비교 결과, 보완은 같은 장비/상태/경로/선택 여부,
질문은 고객/내부 담당 부서/질문 상태로 묶는다. 대표 문구는 근거 있는 요구 인용·입력 제품코드와 그 후보의 비교 값·질문에서만 가져온다.

- 여섯 절 각각 최대 **8문장**, 전체 최대 **48문장**이다. 통합 책임이 필요한 경우 가정/제외 절의 첫 한 칸을 예약한다.
- 그룹 정렬은 재검토 필요를 먼저 두고 사양 차이→조건부→근거 부족→근거 있음 순서 및 그룹 키로 결정한다.
  남은 슬롯을 넘는 그룹은 마지막 `혼합 항목 추가 검토` 요약으로 합친다. 서로 다른 장비·조건·선택 여부를
  동일 항목/충족/공급 가능으로 주장하지 않는다. 조건·정적 검토/미확약 flags는 합집합/OR로 유지한다.
- 대표는 조항 번호의 숫자 순서→장비/항목→요구 UUID(질문 단독이면 질문 UUID)의 고정 순서에서
  중복 없이 최대 **3개**다. 일반 인용 대표는 표시용 최대 **120자**, 자사 비교 대표는 최대 **1000자**다.
  고객 `req.origin.quote`는 알려진 코드/enum과 한글 조사가 들어 있어도 표시 mapping을 절대 적용하지 않는다.
  탭·연속 공백·줄바꿈도 재작성하지 않으며, 길이 초과 때만 원문 접두부+명시 줄임표를 표시한다.
  장비 제목은 최대 80자, 그룹 키는 축약 전 장비 문구를 사용한다. 긴 본문이 같은 접두사를 가졌다고 그룹을 합치지 않는다.
- 대표에 뽑히지 않았거나 초과 그룹에 들어간 요구·조항·제품·후보·질문의 **전체 evidence**는 유지한다.
  전체 조건도 유지하며 대표 생략을 조건 해소로 취급하지 않는다. 본문은 문장당 4000자 이내다.
- 자사 비교는 요구값/후보값 쌍→제품 식별명→속성명 순서로 예산을 배정한다. 값 쌍은 900자까지 완전 보존한다.
  쌍이 이 예산을 넘으면 더 긴 값은 `긴 요구값/후보값: 조건 원문 확인`으로 명시한다. 짧은 값도 남은 예산에
  완전히 들어가지 않으면 같은 방식으로 참조하며, 비교 숫자를 중간에서 잘라 다른 값처럼 보이지 않게 한다.
  제품명/속성명이 남은 예산을 넘는 경우에도 부분 식별명 대신 `긴 제품 식별명/속성명: 조건 원문 확인`으로 표시한다.
  이런 생략이 하나라도 있으면 제품·속성·요구값/단위·후보값/단위를 연결한 `자사 비교 원문` 조건을 추가한다.
  이 원문 조건은 `literal_conditions` 경계를 사용하여 후속 `_display` 치환을 거치지 않는다.
  제품명이 속성 키와 같은 경우까지 원형을 보존하며 전체 evidence와 기존 조건도 유지한다.
- 요구 코드/UUID는 본문에 삽입하지 않고 evidence에서 추적한다. 자사 후보 제품코드는 내부 enum이 아닌 제품 식별명이므로
  대표 문구에 해당 코드와 요구값/그 후보값을 함께 표시한다. 제품 식별명은 속성키 mapping에서 제외하며 evidence 원형도 보존한다. 상태·경로·등급·부서·R&D 상태는 표시용 문구로 쓴다.
  생성한 설명/질문 표시의 알려진 속성·조건 키만 표시용 mapping으로 바꾼다. 고객 원문 인용과 자사 비교 원문 기록은 예외로 보호한다.
  키 경계는 ASCII 영숫자/밑줄 기준으로, `rated_current가`처럼 한글 조사가 붙어도 표시하며
  영문 식별자 `prerated_current`·`rated_current_suffix` 내부는 부분 치환하지 않는다.
  임의 숫자·규격·실제 장비명을 지우거나 의미를 추론하지 않는다. 근거 ID 원형은 바꾸지 않는다.

## 근거 집계와 고정 고지

각 문장의 `evidence`는 입력에서 확인된 `requirement`·`clause`·`product`·`partner`·`question` 참조다.
제품 비교 문장에는 요구/제품, 협력사 문장에는 요구/협력사, 질문에는 질문 및 연관 요구/조항 근거를 붙인다.
입력에 없는 참조나 근거가 없는 문장을 생성하려 하면 오류다. 제목/고지는 제안 문장이 아니다.

`evidence_missing_count = sum(sentence.evidence_missing for 모든 출력 문장)`이며 고지/제목을 제외한다.
근거 없는 제안 문장을 만들지 않으므로 정상 생성은 각 flag가 false이고 합은 0이다. 자료가 부족한 경우
자료 부족 자체를 **근거 있는 요구의 판정 기록**으로 표시할 수 있지만 제품 사실을 만들어 채우지는 않는다.
빈 입력도 문장 0개이므로 count는 0이다. 이것이 업무 정확도나 추적률 100%를 증명하지 않는다.

`disclaimer`는 다음 문자열을 그대로 유지한다.

> 시연용 검토본이며 실제 제안서가 아니다.

## 검증 범위와 남은 연결

`tests/tft/test_rfp_draft.py`는 일반 합성 데이터로 스키마·여섯 절·결정성·입력 불변성·참조/판본,
추적 불변식과 count, 조건/미확인/재검토, 복수 경로의 후보 ID 유일성, 통합 책임과 질문 상태를 확인한다.
실제 기획 사례 문구·제품 코드를 하드코딩하지 않는다. `scripts/check_backend.py tft`가 새 테스트를 수집한다.

공식 `rfp_draft_trace_rate`는 `eval.rfp_metrics.summarize_draft_trace`가 처리된 프로젝트의 최신 초안으로 잰다.
입력은 `scripts/rfp_draft_trace_input.py`가 만들고 `rfp_candidate_run --drafts`로 넘긴다. 분모는 자사 대응·차이·
협력사 보완·가정 절의 문장이다. 분자는 프로젝트에 실제로 있는 요구·제품·협력사 근거가 있거나 가정 표시(`unconfirmed`)가
있는 문장이다. 생성기의 `evidence_missing` 표시는 쓰지 않는다. 조항·질문만 달린 문장은 분자에 들지 않는다.
분모가 0인 빈 초안의 추적률도 1.0으로 보고하지 않는다. 여러 문서 중 하나라도 초안이 비어 있으면 전체 값이 없다.
기획서 4.10 원문과 Jira 전체 완료조건은 이 구현에 별도로 제공되지 않았으므로 이 계약은
supervisor가 승인한 순수 엔진 범위다. 기획 원문 전체 구현·HTTP/저장/배포·실제 업무 성능 완료를 뜻하지 않는다.

## 처리 흐름·저장·HTTP 연결 (KAN-188 후속)

순수 엔진의 공개 입력/출력 형식은 그대로이며 `drafts.py`가 같은 DB 연결의 공개 snapshot 변환을 조합한다.
처리 흐름은 compare~draft를 한 트랜잭션으로 묶고, 초안 작업 ID당 한 판본만 저장한다.
같은 `source_job_id` 재시도는 원래 생성 판본을 읽으며 그 사이 사람 편집으로 바뀐 head를 덮어쓰지 않는다.
다른 작업 ID로 명시적으로 재처리하면 새 초안 판본을 만든다. 생성/편집/검토본 저장/내보내기는
동일 프로젝트 advisory transaction lock으로 직렬화한다.

T17은 기존 표에 `draft_sentences.needs_rereview`(생성 당시 검토 표시), `draft_versions.source_job_id`
(부분 unique index) 두 열만 추가하고 필요한 표의 worker 조회·초안 추가·head/내보내기 결과 열 갱신 권한만 준다.
기존 `rereview_marks`는 `cause_proposal_id`가 필수이므로 시스템 추출 검토 표시 저장을 대신할 수 없다.
표는 새로 만들지 않는다. 로컬·배포 DB에는 운영자가 T14 이후 T17을 적용해야 한다.

- **25 GET draft**: 최신 또는 `?version=N`. 고지·여섯 절·문장 근거·조건·미확약·검토 표시를 반환한다.
  공개 `sentence_id`는 `sentence_key`, 물리 판본 행 ID는 내부 전용이다. 요구 상세 링크도 최신 공개 키를 반환한다.
- **26 PATCH draft**: 담당 sales·책임자만 가능. `DraftEdit.version` CAS, 문장별 사유와 audit,
  불변 이전 판본을 유지한다. 기존 문장 수정/절 이동에서도 조건·미확약·검토 표시·공개 ID를 보존한다.
  새 문장은 section이 필수다. 원문 없는 자유문장 또는 프로젝트 안에서 확인 못한 evidence는
  `evidence_missing=true`로 표시·합산하고 검토본 저장을 막는다. 변경 DTO로 고지나 검토 표시를 지울 수 없다.
- **27 POST review-versions**: 담당 sales·책임자, Idempotency-Key 필수. 최신 초안 version 일치,
  근거 누락/문장 재검토 0, 필수 요구 해결 또는 `unresolved+next_owner_field`, 통합 책임 필요 시 확보,
  빈 초안 아님을 확인한다. 실패는 422 `TFT_DRAFT_INCOMPLETE`(대상 ID를 details에 표시), stale은 409.
  성공 시 `REVIEW_DRAFT`가 되고 미해결 필수가 있으면 `CONDITION_CHECK`, 없으면 `OWNER_CONFIRMED`다.
  이는 담당자의 저장 행위이며 공급·수주 승인이 아니다. 같은 키 재전송은 원래 검토본을 반환한다.
- **28 POST exports**: 담당 sales·책임자, Idempotency-Key 필수. 지정된 불변 review_version 예약과 플랫폼
  `rfp.export` 접수. `ExportAccepted(JobAccepted)`에 `export_id`를 추가하여 파일 GET과 연결하며,
  같은 요청 재전송은 같은 export_id다. process/annotate는 기존 JobAccepted를 유지한다.
- **29 GET exports/{export_id}/file**: 기존 프로젝트 조회 범위, 다른 프로젝트/없는 자원은 404,
  미완료는 409 `TFT_EXPORT_NOT_READY`. 완료 파일은 sha256/size 확인 후 DOCX MIME·attachment·no-store·nosniff로 반환한다.
  파일 누락/손상은 안전한 503이며 내부 storage_key는 응답에 포함하지 않는다.

### 내보내기 포맷과 파일

ExportFormat의 `DOCX`·`PDF` enum은 바꾸지 않는다. **이번 구현은 DOCX만**이며 PDF는 예약/DB 쓰기/
플랫폼 접수 전에 422 `TFT_EXPORT_FORMAT_UNAVAILABLE`다. PDF 생성은 별도 후속 작업이다.
reportlab·글꼴·의존성·이미지를 추가하지 않는다.

DOCX는 stdlib ZIP/XML의 실제 OOXML 패키지로, 고정 고지·모든 절/문장·공개 ID·조건·근거·미확약/검토 표시를 싣는다.
XML escaping 및 `w:br`·`w:tab`으로 한글/특수문자/줄바꿈을 보존하고 유효하지 않은 XML 문자는 삭제하지 않고 실패한다.
검토본 판본에 대해 바이트가 결정적이다. 내보내기는 `draft_repository.load_snapshot`으로 해당 판본의 저장된
본문·근거·조건·flags만 읽는다. 이후 요구의 `needs_review`나 `rereview_marks`는 파일에 합산하지 않는다.
일반 `load`를 쓰는 GET·PATCH 응답과 검토본 저장 검사는 현재 재검토 표시를 계속 합산한다.
편집 저장 입력은 `load_snapshot`의 정적 flags를 보존하며, 일시적인 live 검토 표시를 새 판본에 저장하지 않는다. 기존 원문 DocumentStore(private GCS 또는 `TFT_DOCUMENT_ROOT`)에
`rfp/{project}/exports/{export}.docx`로 저장하며 25 MiB 상한·해시·크기를 기록한다.
객체 생성 후 DB commit 전에 실패하면 private 객체만 남을 수 있다(기존 업로드와 동일).
재시도는 같은 바이트일 때만 기존 객체를 인정하며 다른 바이트를 덮어쓰지 않는다.

서버/플랫폼 웹 중계는 이 다섯 경로와 정확한 export 파일 경로의 DOCX 응답을 허용한다.
본체 JSON 경로에 바이너리를 허용하지 않는다. 실제 모델·외부 발송·공식 추적률 평가 연결은 포함하지 않는다.
로컬 일반 합성/파일/HTTP 검증과 전용 PostgreSQL CI 검증을 분리하며 DB 미실행을 통과로 보고하지 않는다.


## 재생성과 사람 편집 보존 (KAN-188 보완 범위)

새 처리 작업은 프로젝트 초안 잠금 안에서 최신 불변 snapshot을 읽고 `human_input` 문장의
ID·절·본문·근거·조건·정적 flags·마지막 편집 이유를 새 초안으로 이관한다. 직접 추가한 문장도 포함한다.
자동 문장을 고친 이력이 있는 문장만 원래 자동 문장의 제목으로 식별되는 같은 절의 포함 근거/조건 영역을 대체한다.
원래 제목으로 개별 영역을 특정할 수 없는 혼합 초과 요약은 자동 기여를 추측해 제거하지 않는다. 요약 전 개별 기여를
제외하므로 일부 요구만 겹친다는 이유로 전체 자동 요약을 지우지 않는다. 다른 요구·새 후보·새 조건은
자동 생성에 남는다. 근거가 없는 직접 추가문장은 자동 영역을 대체하지 않는다. 통합 책임 고지는 자동 유지한다.
자동 생성은 절별 8문장/총 48문장 상한을 유지하며 사람이 고친/추가한 문장은 이 상한의 예외다.
사라진 근거는 원래 문장과 근거 ID를 유지하고 evidence_missing/needs_rereview로 표시한다.
기존 sentence_key를 보존하여 미해소 mark는 live 조회에서 계속 반영한다. live flags는 이관 snapshot에
저장하지 않으며, 기존 정적 flags를 유지한다. 같은 source_job_id 재시도는 앞서 만든 판본을 반환하고
그 뒤 사람 편집을 덮어쓰지 않는다. 동시 사람 편집은 프로젝트 잠금과 기존 판본 CAS를 따른다.

**범위 한계:** 근거 링크에는 요구 판본 baseline이 없다. 이번은 기존 mark 기반 보존이며 요구의
실제 판본/값/인용 변경만을 정확히 판별하는 기능은 구현하지 않는다. `needs_review`를 요구 변경의
증거로 간주하지 않는다. 현재 요구의 검토 표시는 기존 live 조회 정책을 유지한다. 새 migration/DTO는 없다.
초안 다시 만들기 버튼은 보류한다. 공개 API로 명시 문서 판본의 처리 완료를 보장할 수 없어 새 연결을
추가하지 않으며 기존 접수 화면의 사유 입력 후 처리 재실행을 사용한다. 이미 처리된 문서만 재실행하면
worker가 parse/extract를 건너뛰므로 모델 재호출 없이 승인·보완 선택으로 초안을 재생성한다.


## 모델 문장 작성의 양식 기원 (KAN-188)

`Sentence.template_text`는 nullable 읽기 필드이며 원래 양식 문장이다. 문장 ID는 양식 문장으로
계산하며 모델이 text를 바꿔도 유지한다. 사람 편집/이관은 template_text를 유지하고 자동 재생성의
대체 지문은 실제 자동 기원의 template_text·evidence·conditions를 읽는다. 직접 추가한 사람 문장은
양식 기원이 없으므로 null이고 모델 입력에서 제외한다. 이전 데이터의 human_input 본문을 양식으로
backfill하지 않으며 같은 sentence_key의 실제 자동 기원을 찾는다. 새 T19 migration은 양식 기원과
rewrite 접수·사용량/실패대체 사유 기록을 저장한다. 기존 고지 문구는 변경하지 않는다.

## 경로32: 모델 문장 작성

`POST /api/v1/tft/projects/{id}/draft/rewrite`의 입력은 `{version:N}`뿐이다. 초안 생성과 동일한
담당 sales·책임자 인가/프로젝트 범위·CSRF·Idempotency-Key를 적용한다. 새 키의 N은 최신 초안이어야
하며 다르면 409다. 같은 키·본문은 같은 플랫폼 `JobAccepted`를 반환하고 다른 본문은 409다.
프로젝트 안의 활성 작업은 하나다. `rfp.process` 뒤 자동 연쇄하지 않고 사람이 판단 후 명시적으로
비용 작업을 접수한다. 화면은 비용이 드는 작업과 실패 시 양식 유지 사실을 알리며 금액은 확정 표시하지 않는다.

별도 작업 `rfp.draft_rewrite`가 불변 N을 읽고 트랜잭션을 끝낸 뒤 모델을 부른다. 절은 순차 처리하며
자동 문장만 절별 최대8/전체48개, 대표 최대3개를 입력한다. 화이트리스트는 절 이름·임시 no·제목·대표·
조건·미확정 여부다. UUID/근거ID/협력사코드/금액/남은 내부코드가 있는 문장은 모델에 보내지 않고
INPUT_BLOCKED로 양식을 유지한다. human_input은 입력에 포함하지 않고 글자/근거/조건/flags 그대로 복사한다.

응답은 JSON `[{no,text}]`다. 구조/번호/공백/4000자, 숫자(천단위 쉼표 동등)/숫자-단위 대응,
규격·모델·조항 표기, 조건값, 상태 고정 문구, 부정 문구 보존을 검사한다. UUID·SYN-/DS-/KAN-/
내부 enum/속성/조건 키·밑줄 식별자·금액·확약 표현을 차단한다. 의미가 같은 번역인지까지 이 검사가
보증하지 않으므로 사람 검토가 최종 경계다. 금지정보를 일반 문구로 추론해 치환하지 않는다.

- 내용/구조 실패: 그 문장만 실패 코드와 함께 절별1회 재작성. 성공한 다른 문장은 재작성하지 않는다.
- 호출 오류/시간초과/출력 잘림: 해당 절 전체를 양식으로 두며 운송 재시도는 하지 않는다.
- 두 번째도 검사 실패한 문장은 양식 유지. N은 삭제/수정하지 않으며 호출 실패를 작업 전체 실패로 만들지 않는다.
- 공급자 실패는 안전 코드만 저장하고 원문 예외/프롬프트/응답을 기록하지 않는다.
- 반환 후 프로젝트 잠금 안에서 최신 초안이 여전히 N인지 CAS 확인. 사람이 먼저 저장했으면 모델 결과를
  버리며 기존 사람 판본은 바꾸지 않는다. 같으면 N+1을 source_job_id로 멱등 저장한다.
- 모델 적용은 text/provenance_kind(ai_draft)만 바꾼다. 양식은 system_record다. ID/절/순서/evidence/
  conditions/unconfirmed/needs_rereview/evidence_missing와 추적률 입력은 동일하다. template_text는 유지한다.
- tft.draft_rewrite_calls는 절/시도/검사코드/프롬프트 판본/요청·응답 모델/토큰/가격표 판본·비용/시간을
  저장한다. attempt0·skipped는 미호출(0토큰·0비용·provider_attempts0)이며 성공 호출로 계산하지 않는다.
  실패에서 공급자가 미보고한 토큰·비용은 null로 두며 0비용 성공으로 꾸미지 않는다.
- 기존 검토본 저장/내보내기 인가·완전성 검사·불변 snapshot·PDF422는 그대로다.

설정은 TFT_DRAFT_REWRITE_PROVIDER(gemini/fake, 미설정 시 추출 provider), TFT_DRAFT_REWRITE_MODEL
(기본 gemini-3.6-flash), TFT_DRAFT_REWRITE_MAX_OUTPUT_TOKENS(8192), TFT_DRAFT_REWRITE_TIMEOUT_MS(120000)다.
worker 생성 시 실제 rewrite용 클라이언트는 만들지 않고 해당 작업 호출 시만 준비한다. 실제 모델 호출은
승인 후 별도 합성 문서 시험으로 검증하며, 현재 구현 검증은 fake 공급자/합성 snapshot이다. 실제 번역 품질·
대체율·토큰·비용·지연과 운영 migration 적용은 미확인이다. 고정 고지 변경도 승인 범위에 포함하지 않는다.
