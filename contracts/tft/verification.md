# KAN-125 부서 검증·팀 공백 규칙

`GET /api/v1/tft/projects/{project_id}/verification`은 현재 프로젝트와 구성안의 검증 보고서를 반환한다. 담당 sales, 현재 책임자, 프로젝트 관리 범위 manager만 전체 보고서를 읽는다. 부서 담당자는 다른 부서의 비교/공백을 볼 수 없다(범위 밖 404). 외부 모델·자동 선발·상태 변경·최종 승인 없음.

- 후보가 없는 역할, 미정 인원, 인원 대비 추천 부족을 구분한다. 철회 추천과 미발행/종료 요청의 추천은 제외한다.
- 경험은 실제 수행 요약과 검증자·시각·근거, 필수/우대 역량은 역할에 연결된 확인 기록, 가용성은 기간·투입률·검증자·시각·근거를 각각 판정한다.
- 최신 시각의 검증 기록을 사용하며 동률은 UUID 순서로 결정한다. 과거 기록은 수정하지 않는다. 확인 주장에 주체/근거가 없으면 추가 확인으로 처리한다. 미기재·미확인·미충족은 서로 다르다.
- 가용성이 요청 기간 전체와 투입률을 충족해야 확인이다. 요청 기간/투입률 자체가 미정이면 추가 확인이다.
- 동일 후보의 서로 다른 역할 제안 기간이 하루라도 겹치면 `OVERLAPPING_ROLE_PROPOSALS`로 표시한다. 이는 이 프로젝트 내 제안 충돌 경고이며 실제 투입 확정이나 전사 일정 충돌을 의미하지 않는다. 기간 미정은 가용성 추가 확인에 남는다. 다른 프로젝트 투입 자료는 아직 연결하지 않았다.
- 우대 역량 상태는 별도로 반환하며 필수 역량 부족으로 바꾸지 않는다. `ready_for_review`는 검토 준비 여부일 뿐 최종 승인 가능 여부가 아니다. 최종 결정 규칙은 KAN-127에서 추가한다.
- 공백에는 요청 부서/역할 다음 부서/구성안 다음 부서를 돌려준다. 검증 준비가 되면 현재 책임자에게, 책임자가 없으면 책임자 지정 단계로 안내한다. 후보 인력 ID를 사용자 ID로 사용하지 않는다.
- 구성안의 CONFIRMED 항목도 현재 검증이 준비됐을 때만 집계한다. 구성안 작성 이후 검증 기록이 바뀌면 재검토 대상이다. 동일 후보가 여러 요청으로 들어와도 인원은 한 명으로 센다.
- 일부 역할만 확정은 `PARTIALLY_CONFIRMED`, 역할이 모두 확정돼도 최종 결정 전이면 `READY_FOR_FINAL_REVIEW`다. 최신 구성안과 현재 책임자가 일치하는 최종 확인, 프로젝트 CONFIRMED 상태까지 있어야 전체 완료다. 빈 프로젝트는 완료가 아니다.

이 API는 읽기 전용 partial 계약이며 운영 중계 allowlist/화면 연결은 KAN-140 및 후속 화면 작업에서 한다. KAN-123/#37과 KAN-122/#31을 선행으로 사용한다. 역량 재검증 저장 방식과 책임자 결정/구성안 판본 생성은 후속 API에서 연결해야 한다. 기존 규칙을 통과했다는 이유로 자동 확정하지 않는다.
