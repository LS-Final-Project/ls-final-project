# 화면·업무 상태 전이·권한 행렬 (KAN-57)

기준일 2026-10-23. 담당 김종하, 검토 오새결. 이 문서는 KAN-57 "[D05] 화면, 업무 상태 전이, 권한 행렬 정리"의 설계 산출물이다. 역할·범위 모델, C/S와 RFP 대응의 업무 상태 전이, 권한 행렬과 화면별 행동을 정리한다. 2026-10-28 프로젝트 2 범위 변경으로 3절·4.2·5.5~5.7은 RFP 자사 대응·협력사 보완 기준으로 바꿨다. **설계 합의이며 구현·검증 완료를 뜻하지 않는다.** 실제 검사 코드, 마이그레이션, OpenAPI는 각 기능 티켓(KAN-78·79 사용자·업무 권한, KAN-108 C/S 업무 상태, RFP 대응 A 티켓 KAN-182~192)에서 구현한다.

원본 우선순위는 Jira KAN-57 결정(2026-10-21 댓글) → [AGENTS](../../AGENTS.md#인증과-역할) → [아키텍처](../../docs/architecture.md#인증과-사람의-결정) → [데이터 계약](../../docs/data-contract.md) → [API 계약](../../docs/api-contract.md) → 최종 기획서 순이다. 기획서 발췌는 참고이며 저장소 문서와 어긋나면 저장소 문서를 따른다. 역할 이름은 AGENTS의 `cs_agent`, `dept_staff`, `manager`, `sales`를 그대로 사용한다.

이 문서의 상태 이름(영문 enum)은 **제안**이다. 실제 enum은 해당 서비스의 `schemas.py`에 두고 공통 패키지에 넣지 않는다([계약 수정 안내](../README.md)). 표에서 **확정**은 Jira·기존 문서에 결정된 것, **기본값(제안)**은 시연 흐름에 맞춰 이 문서가 제안한 값, **미확정(주체)**은 아직 결정하지 않은 것이다. 미확정 항목은 구현에서 기본 거부한다.

## 1. 역할·범위 모델

권한은 **역할 × 범위(dept/project) × 객체 상태**로 결정한다. 역할만으로 허용하지 않고, 범위만으로 행동을 허용하지 않으며, 범위 안이라도 객체 상태가 허용하지 않는 전이는 거부한다.

### 1.1 로그인 역할 (확정)

| 역할 | 설명 | 필수 속성 |
| --- | --- | --- |
| `cs_agent` | C/S 문의 처리와 개선요청 주관 | 없음 |
| `dept_staff` | 전문부서 담당자. 이관 문의 처리, 개선요청 회신·조치, RFP 검토 부서의 조회·변경 제안·고객 질문 | 소속 부서 `dept` 필수. 없으면 로그인 거부(401) |
| `manager` | 주관회사 전체 집계 조회. 관리 대상 부서·프로젝트 안에서 상세 조회와 재배정 | 관리 대상 C/S 부서 목록, 관리 대상 RFP 프로젝트 목록(명시 부여, 기본 없음) |
| `sales` | RFP 접수·문서·처리, 요구·대응표 검토, 보완 경로·후보 선택, 질문·회신·제안·승인, 초안 수정·검토본 저장 | 담당 프로젝트 목록 |

- 사용자 식별은 `tid + oid`다. 이메일은 표시용이다. 등록되지 않은 사용자에게 역할을 자동 부여하지 않는다.
- 한 사용자에게 여러 역할을 줄 수 있다(`identity.user_roles`). 행동 허용은 역할별 조건 중 하나라도 만족하면 되지만 범위 조건은 해당 역할의 범위로 검사한다.
- `manager`라는 이유만으로 상세 조회, 원문·파일 다운로드, 개인 메일함 열람, RFP 제안 승인·검토본 저장을 허용하지 않는다. 집계 조회권은 상세 API를 우회하는 근거가 아니다.

### 1.2 범위 (scope)

| 범위 | 정의 | 부여 주체 | 상태 |
| --- | --- | --- | --- |
| 자기 부서 | `dept_staff`의 `users.dept` | 사용자 등록 시 | 확정(필드 존재) |
| 관리 대상 부서 | `manager`에게 명시 부여한 C/S 부서 집합 | 사용자 등록 스크립트(서버 밖) | 확정, 저장 구조 미구현(KAN-78) |
| 관리 대상 프로젝트 | `manager`에게 명시 부여한 RFP 프로젝트 집합 | 사용자 등록 스크립트(서버 밖) | 확정, 저장 구조 미구현(KAN-78) |
| 담당 프로젝트 | `sales`가 담당하는 RFP 프로젝트(`projects.sales_user_id`) | 접수한 `sales`가 담당. 변경은 관리 대상 `manager`의 `assignment` | 확정(명세 §4.1) |
| 검토 부서 | RFP 프로젝트의 `review_departments`에 있는 부서. `dept_staff.dept`와 비교 | 담당 `sales`·책임자가 프로젝트 PATCH로 지정 | 확정(명세 §2.2, 옛 '요청 부서' 행 대체) |
| 수신 부서 | C/S 개선요청의 전달 대상 부서(`proposed_depts`). 여러 부서 가능 | 전달 시 `cs_agent`가 확정 | 확정 |
| 프로젝트 책임자 | `projects.responsible_user_id`. 프로젝트별 속성이며 로그인 역할이 아님. `sales` 범위 + 제안 승인·기각·검토본 저장 | 관리 대상 `manager`가 `assignment`로 지정 | 확정 |

C/S 범위 판정: 문의와 개선요청의 담당 `cs_agent`(문의 담당자, `cs_owner`)는 **C/S 부서** 소속이다. C/S 소속은 `cs_agent` 역할로 판정하며 `users.dept`는 쓰지 않는다(`cs_agent`는 부서 없음 유지). 부서 코드는 C/S 라우팅·이관·`manager` 관리 범위가 모두 `identity.departments`의 한 값 집합을 쓰며, C/S 부서의 코드는 `GCS_L1`(글로벌 C/S 센터)이다. 따라서 담당 `cs_agent` 재배정은 이관 여부와 관계없이 C/S 부서를 관리 대상 부서로 가진 `manager`만 할 수 있다. 조회 범위에서는 이관된 문의가 C/S 부서와 이관 부서 모두에 속하므로, 이관 부서만 관리하는 `manager`는 그 문의를 상세 조회할 수 있지만 재배정할 수는 없다.

계정 등록·역할 지정·`manager` 관리 범위 부여는 **서버 밖 등록 스크립트(로컬은 seed)로만** 한다(확정 2026-10-23). 등록 값은 사내 관리자가 정한 것으로 가정하며, 실제 도입 시에는 사내 계정 시스템 연동으로 대체한다. 이를 위한 API·화면은 만들지 않으며 어떤 로그인 역할도 다른 사용자의 로그인 역할·소속 부서·관리 대상 부서·관리 대상 프로젝트를 바꿀 수 없다. 프로젝트별 업무 배정(담당 `sales`, 프로젝트 책임자, 요청 부서)은 계정 부여가 아니라 업무 데이터이므로 이 규칙의 예외이며, 위 표와 4.2를 따른다.

프로젝트 책임자는 사용자 속성이 아니라 **프로젝트 속성**이다. 같은 사용자가 프로젝트 A의 책임자이면서 프로젝트 B에서는 일반 `sales`일 수 있다. 생성자, 다른 `manager`, 담당 `sales`에게 자동 부여하지 않는다.

### 1.3 검사 순서와 오류 (확정 코드는 [API 계약](../../docs/api-contract.md#오류와-동시-수정) 사용)

| 순서 | 검사 | 실패 응답 |
| --- | --- | --- |
| 1 | 세션 유효성(활성 사용자, 유효 역할, 부서 조건) | 401 `AUTH_REQUIRED` 또는 `SESSION_EXPIRED` |
| 2 | 객체가 사용자의 **조회 범위** 안에 있는가 | 404 `NOT_FOUND` (범위 밖 객체의 존재를 숨김) |
| 3 | 역할·범위가 해당 **행동**을 허용하는가 | 403 `FORBIDDEN`. 승인권자 확인이 더 필요하면 403 `APPROVAL_REQUIRED` |
| 4 | 객체 **상태**가 전이를 허용하는가 | 409 `INVALID_TRANSITION` |
| 5 | 판본 일치(`If-Match`) | 428 `VERSION_REQUIRED` / 412 `VERSION_CONFLICT` (확인 필요 1 참고) |
| 6 | 필수 근거·입력 | 422 `VALIDATION_ERROR`, `EVIDENCE_REQUIRED` |

플랫폼이 세션을 검증하고 사용자 맥락을 내부 요청으로 중계하며, C/S·TFT 서비스는 호출자 인증과 함께 2~6을 **다시** 검사한다. 브라우저가 보낸 역할·사용자 헤더와 `approved=true` 같은 값은 근거로 쓰지 않는다. 조회 가능 범위 안에서는 404 대신 403을 내서 "보이지만 할 수 없음"을 구분한다.

### 1.4 업무 서비스가 받는 사용자 정보 (KAN-78, 형식 제안)

C/S·TFT 서비스는 DB 권한상 `identity` 스키마를 읽지 못한다. 플랫폼이 세션에서 읽은 사용자를 아래 형식으로 넘기고, 서비스는 이 값으로 2~3단계를 검사한다(`backend/shared/access.py`).

| 필드 | 내용 |
| --- | --- |
| `user_id` | `identity.users.id` |
| `roles` | `identity.user_roles`의 역할 목록(1개 이상) |
| `dept` | `users.dept`. `dept_staff`는 필수 |
| `managed_departments` | manager의 관리 대상 부서 코드(`identity.manager_departments`) |
| `managed_projects` | manager의 관리 대상 RFP 프로젝트 ID(`identity.manager_projects`) |

- 전달: 요청 헤더 `X-Team4-Principal`에 위 필드의 JSON. 알 수 없는 필드, 역할 없음, 부서 없는 dept_staff, manager가 아닌 사용자의 관리 범위는 401로 거부한다.
- 신뢰 범위: KAN-178은 이 공통 모델을 운영 세션에서 만들고 브라우저의 같은 헤더를 제거한다. 업무 중계는 기본 비활성이며 production은 DB 조회 전 404 잠금을 유지한다. 명시 활성화 시에는 Google 서명·수신 서비스 audience·플랫폼 실행 계정을 검증한 `X-Team4-Caller-Token`이 있어야 이 JSON을 읽는다. 호출자 인증 뒤에도 업무 역할·객체 검사를 수행한다. 설정·허용 경로·거부 조건·실제 공용 검증의 구분은 [인증 계약](auth.md#업무-json-중계와-호출자-검증-kan-178)을 따른다. 비활성 local/test의 unsigned fake는 독립 개발에만 사용한다.
- 플랫폼 `/me`와 세션 조회는 같은 값(`managed_departments`, `managed_projects`)을 이미 돌려준다.

## 2. C/S 업무 상태 전이

C/S에는 **문의(ticket) 상태**와 **개선요청(improvement request) 상태**가 있고 둘은 독립이다. 고객 문의 종결이 개선요청 완료가 아니며, 부서 회신이나 개선요청 완료가 문의 종결을 만들지 않는다(확정). AI 작업 상태(`SUCCEEDED` 등)와 메일 발송 상태(`ACCEPTED`, `UNKNOWN` 등)도 두 업무 상태와 별개이며 자동 전이를 일으키지 않는다.

### 2.1 문의 상태 (확정 2026-10-27, KAN-108)

워크플로우 ①~⑪(기획서 4.1)의 담당자 확인 게이트 ⑥을 중심으로 정리한다. 제공 데이터의 `status`는 `cs.ticket_source_records`의 사후 기록이며 운영 상태와 같은 칸을 쓰지 않는다([C/S 계약](../cs/tickets.md)).

| 상태 | 의미 |
| --- | --- |
| `RECEIVED` | 접수. AI 분석 작업 미완료 또는 미실행 |
| `IN_REVIEW` | 분석 결과·규칙 결과·초안이 있고 담당자 확인 대기(게이트 ⑥). 고객 회신 재투입 후에도 이 상태로 돌아옴 |
| `WAITING_CUSTOMER` | 추가 정보 요청을 발송하고 고객 회신 대기 |
| `ANSWERED` | 답변을 발송하고 고객 회신 또는 종결 판단 대기 |
| `TRANSFERRED` | 전문부서로 이관 확정. 부서 처리 중 |
| `CLOSED` | 종결. 사례 적재 가능 |

| 전이 | 트리거 | 허용 역할 | 범위 조건 | 거부 시 |
| --- | --- | --- | --- | --- |
| `RECEIVED` → `IN_REVIEW` | 분석 작업 완료(시스템) 또는 수동 접수 후 분석 건너뜀 | 시스템 / `cs_agent` | — | — |
| `IN_REVIEW` → `WAITING_CUSTOMER` | 추가 정보 요청 발송 승인 | `cs_agent` | 문의 조회 범위 | 403 / 409 |
| `IN_REVIEW` → `ANSWERED` | 답변 발송 승인(초안 수정 포함) | `cs_agent` | 문의 조회 범위 | 403 / 409 |
| `IN_REVIEW` → `TRANSFERRED` | 이관 확정(대상 부서는 규칙 제안을 사람이 확정) | `cs_agent` | 문의 조회 범위 | 403 / 409 |
| `WAITING_CUSTOMER`, `ANSWERED` → `IN_REVIEW` | 고객 회신 재투입(같은 문의에 연결, 재분석) | 시스템(메일 수신) / `cs_agent`(수동 연결) | — | — |
| `TRANSFERRED` → `IN_REVIEW` | 부서 처리 결과·회신 내용 등록(`SUBMITTED`). 문의는 `IN_REVIEW`로 돌아가고 `cs_agent`가 결과를 채택하거나 보완을 요청한 뒤 고객 발송 또는 종결을 판단 | `dept_staff` | **현재 자기 부서로 이관된 문의** | 403 / 409 |
| `TRANSFERRED` → `IN_REVIEW` | 부서 반송: 자기 부서 일이 아님(사유 필수) | `dept_staff` | 현재 자기 부서로 이관된 문의 | 403 / 409 / 422 |
| `TRANSFERRED` → `IN_REVIEW` | C/S 회수(사유 필수). 다른 부서로 다시 보내려면 일반 이관을 한다 | `cs_agent` | 문의 조회 범위 | 403 / 409 / 422 |
| `IN_REVIEW` → `TRANSFERRED` | 부서 결과 보완 요청(사유 필수): 결과는 `REWORK_REQUESTED`, 같은 부서로 새 이관 회차 | `cs_agent` | 문의 조회 범위 | 403 / 409 / 422 |
| `ANSWERED` → `CLOSED` | 종결 확정 | `cs_agent` | 문의 조회 범위 | 403 / 409 |
| `IN_REVIEW` → `CLOSED` | 종결 확정. **cs_agent가 채택한 부서 처리 결과가 있거나 이 문의에 고객 발송 완료 이력이 있을 때만** 허용. 둘 다 없거나 검토 전 결과가 있으면 409 | `cs_agent` | 문의 조회 범위 | 403 / 409 |
| `CLOSED` → `IN_REVIEW` | 고객 회신 재투입으로 재개 | 시스템 / `cs_agent` | — | — |
| 담당자 재배정(상태 변경 없음) | 문의의 담당 `cs_agent` 변경 | `manager` | C/S 부서를 관리 대상으로 가진 `manager`(1.2). 이관 여부와 무관 | 403 |

종결 조건(확정): 종결은 `ANSWERED`에서, 또는 `IN_REVIEW`에서 채택된 부서 처리 결과나 고객 발송 완료 이력이 있을 때만 허용한다(`TRANSFERRED`에서는 부서 결과 등록으로 `IN_REVIEW`를 거친 뒤 종결한다). 추가로 발송 결과가 `UNKNOWN`인 발송 의도가 없어야 하며, `cs_agent`가 명시적으로 종결을 확정한다. AI 작업 완료, SLA 만료, 부서 회신만으로 자동 종결하지 않는다. 사례 적재(⑧)와 고객 이력 확정값 저장(⑨)은 `CLOSED` 상태에서만 허용하며 종결 후 개선요청은 계속 진행할 수 있다.

고객 발송 주체는 `cs_agent`로 통일한다(기본값 제안). `dept_staff`는 처리 결과와 회신 내용을 등록하고 고객 발송은 `cs_agent`가 확인한다. RMA 번호·방문일·보증 승인은 AI가 생성하지 않으며 사람이 입력한 값만 발송 본문에 들어간다(확정).

### 2.2 개선요청 상태 (기획서 4.4 기반, 확정)

| 상태 | 의미 |
| --- | --- |
| `DRAFT` | 초안. 후보 기준(90일 내 서로 다른 고객 3곳 등) 충족으로 시스템이 생성하거나 `cs_agent`가 수동 생성 |
| `REVIEWED` | `cs_agent` 검토 완료. 전달 대상 부서 확정 |
| `SENT` | 부서에 전달(메일 발송 승인 완료). 부서별 상태로는 다시 전달된 부서도 이 상태로 돌아온다. 요청 상태로는 2.2.1 요약 결과 |
| `ACKNOWLEDGED` | 수신 부서가 수신 확인 |
| `ADOPTED` | 채택 |
| `INFO_REQUESTED` | 추가 정보 대기. `cs_agent`가 자료 취합·재검토 주관. 문의가 종결돼도 유지 |
| `REJECTED` | 반려. 사유 필수. 요청 상태로는 현재 회차의 모든 부서가 반려한 경우(2.2.1) |
| `ACTION_TAKEN` | 실제 조치 등록(조치 내용·적용 대상·실제 적용일·근거) |
| `FOLLOW_UP` | 사전에 정한 후속 확인(대상·방법·기간) 진행 |
| `COMPLETED` | 사람의 완료 판단. 완료 후에도 추가 발생 감시 |

**요청** = 요청 단위 동작(회차를 열거나 요청 상태를 바꿈), **부서** = 한 수신 부서의 상태만 바꾸는 부서 단위 동작. 출발 상태가 같아도 둘은 다른 동작이다(2.2.1). 부서 단위 동작은 요청이 `FOLLOW_UP`·`COMPLETED`·반려 종료일 때 모두 409다.

| 단위 | 전이 | 트리거 | 허용 역할 | 범위 조건 | 거부 시 |
| --- | --- | --- | --- | --- | --- |
| 요청 | (생성) → `DRAFT` | 후보 기준 충족(시스템) / 수동 생성 | 시스템 / `cs_agent` | — | — |
| 요청 | `DRAFT` → `REVIEWED` | 검토 완료, `cs_owner`·`reviewed_by` 기록, 제안 부서 수정 | `cs_agent` | — | 403 / 409 |
| 요청 | `REVIEWED` → 첫 회차 | 전달(메일 발송 승인, `sent_at`). 대상 부서가 모두 `SENT`로 시작 | `cs_agent` | — | 403 / 409 |
| 부서 | `SENT` → `ACKNOWLEDGED` | 수신 확인 | `dept_staff` | **수신 부서** | 403 / 409 |
| 부서 | `ACKNOWLEDGED` → `ADOPTED` / `INFO_REQUESTED` / `REJECTED` | 부서 회신(`dept_replies.reply_type`). 반려는 사유 필수 | `dept_staff` | 수신 부서 | 403 / 409 / 422 |
| 부서 | `ADOPTED` → `ACTION_TAKEN` | 조치 등록(`action`, `action_scope`, `action_date`, `action_evidence`). 그 부서가 `ADOPTED`이면 다른 부서의 회신을 기다리지 않는다 | `dept_staff` | 수신 부서 | 403 / 409 / 422 |
| 부서 | `INFO_REQUESTED` → `SENT` | 자료 보완 후 그 부서에 재전달(새 판본) | `cs_agent` | — | 403 / 409 |
| 부서 | `REJECTED` → `SENT` | 반려 사유와 다른 새 근거로 그 부서에 재요청(새 판본). 다시 반려하면 반려 확인도 다시 한다 | `cs_agent` | — | 403 / 409 / 422 `EVIDENCE_REQUIRED` |
| 부서 | `SENT`, `ACKNOWLEDGED` → `SENT` | 회신 기한이 지난 부서에 회신 재촉 | `cs_agent` | — | 403 / 409 |
| 부서 | 반려 확인(상태 변경 없음) | 반려 사유를 확인하고 재요청하지 않음(`rejection_reviewed_by`·`_at` 기록). 현재 회차의 `REJECTED` 부서만 | `cs_agent` | — | 403 / 409 |
| 요청 | `SENT`, `ACKNOWLEDGED`, `ADOPTED`, `INFO_REQUESTED`, 반려 종료 → 새 회차 | 재요청(조치 전): 직전 요청 단위 전달 이후 새 해결 기록 3건마다 후보 → `cs_agent` 검토 후 전달. 반려 종료 요청은 이 후보 또는 반려 사유와 다른 새 근거 중 하나가 있어야 하며, 둘 다 없으면 422 | 시스템(후보) / `cs_agent`(전달) | — | 403 / 409 / 422 `EVIDENCE_REQUIRED` |
| 요청 | `ACTION_TAKEN` → `FOLLOW_UP` | 후속 확인 계획(`followup_plan`) 확정. 현재 회차의 모든 부서가 `ACTION_TAKEN`이거나 반려 확인된 `REJECTED`이고 `ACTION_TAKEN`이 1개 이상일 때만. 아니면 409 | `cs_agent` (부서와 협의) | — | 403 / 409 / 422 |
| 요청 | `FOLLOW_UP` → `COMPLETED` | `followup_result` 기록 후 완료 판단(`completed_by`, `completed_at`) | `cs_agent` | — | 403 / 409 |
| 요청 | `ACTION_TAKEN`, `FOLLOW_UP`, `COMPLETED` → 새 회차 | 재발 재개: 조치 적용 장비에서 1건이라도 재발이 확인되면 재발 후보 → `cs_agent` 검토 후 같은 요청을 다시 열어 전달(새 판본). 조치 전 장비의 발생은 재발이 아니며 재요청 집계로 간다 | 시스템(후보) / `cs_agent`(재개) | — | 403 / 409 |
| 요청 | 담당자 재배정(`cs_owner` 변경, 상태 변경 없음) | — | `manager` | C/S 부서를 관리 대상으로 가진 `manager`(1.2) | 403 |

- 완료 판단은 `cs_agent`(C/S 주관)가 한다(기본값 제안). 부서 회신·조치 등록만으로 `COMPLETED`가 되지 않는다. 재발 재개는 조치 이후 상태(`ACTION_TAKEN`, `FOLLOW_UP`, `COMPLETED`) 어디서든 가능하며 이전 회차의 후속 확인 기록은 보존한다. 조치 전 장비의 발생은 재발과 구분해 따로 집계한다.
- 여러 부서에 전달한 요청은 부서마다 상태를 따로 두고, 요청 상태는 시스템이 요약한다(2.2.1, 확정 2026-10-23). `cs_agent`가 요청 상태를 직접 고르지 않는다.
- `manager`는 개선요청 진행 현황을 집계로 보고, 관리 대상 부서가 수신·제안 부서인 요청만 상세 조회한다. C/S 부서를 관리 대상으로 가지면 전체 요청을 상세 조회한다(1.2). 상태 전이는 하지 않는다.

### 2.2.1 여러 수신 부서: 부서별 상태와 요청 상태 요약 (확정 2026-10-23)

수신 부서마다 `SENT → ACKNOWLEDGED → ADOPTED / INFO_REQUESTED / REJECTED → (ADOPTED이면) ACTION_TAKEN`을 독립적으로 진행한다. 부서별 현재 상태는 요청-부서 단위 행에 두고(이름은 C/S 개선요청 구현에서 정함), 회신 이력은 `dept_replies`에 남긴다. 반려는 "이 부서가 맡을 일이 아님"을 뜻하며 그 부서만 진행에서 빠진다. 부서 질문(`QA:`, `SCM:` 등)은 해당 부서에 묶는다.

**전달 회차**

- 요청 단위 전달(첫 전달, 재요청, 재발 재개)은 새 회차를 연다. `cs_agent`가 고른 **대상 부서**는 `SENT`에서 시작한다. 기본 대상은 재요청이면 `ACTION_TAKEN`과 반려 확인된 `REJECTED`를 뺀 기존 수신 부서(반려 종료에서는 기존 수신 부서 전체), 재발 재개면 재발한 조치를 등록한 부서다. 대상 부서는 1개 이상이어야 하며 없으면 422다.
- 대상에서 뺀 이전 회차 부서는 상태(조치, 반려 확인 포함)를 그대로 **이월**한다. 현재 회차의 부서 = 대상 부서 + 이월 부서다. 따라서 일부 부서만 다시 불러도 다른 부서의 조치가 요약과 후속 확인 조건에서 빠지지 않는다.
- 이전 회차의 부서별 상태·회신·조치·후속 확인 기록은 그 회차 기록으로 보존한다.
- 부서 단위 동작(자료 보완 재전달, 반려 부서 재요청, 회신 재촉, 반려 확인)은 회차를 바꾸지 않고 그 부서만 바꾼다. 요청이 `FOLLOW_UP`·`COMPLETED`·반려 종료이면 409이고, 이때 부서를 다시 부르려면 새 회차를 연다.

**요청 상태 요약** (현재 회차의 부서만 본다. 요청이 `FOLLOW_UP`·`COMPLETED`가 아닐 때 부서 상태가 바뀌거나 회차가 열릴 때마다 다시 계산하고, 위에서부터 처음 맞는 것을 쓴다)

| 순서 | 부서별 상태 조건 | 요청 상태 |
| --- | --- | --- |
| 1 | 모든 부서가 `REJECTED` | `REJECTED` (모두 반려 확인되면 반려 종료) |
| 2 | `REJECTED`가 아닌 부서가 모두 `ACTION_TAKEN` | `ACTION_TAKEN` |
| 3 | `ADOPTED`·`ACTION_TAKEN` 부서가 1개 이상 (일부 부서만 채택·조치했거나 다른 부서가 아직 회신·보완 중) | `ADOPTED` |
| 4 | `INFO_REQUESTED` 부서가 1개 이상 | `INFO_REQUESTED` |
| 5 | `ACKNOWLEDGED` 부서가 1개 이상 | `ACKNOWLEDGED` |
| 6 | 그 외 | `SENT` |

**종료와 다시 열기**

| 요청 상태 | 열린 요청 집계 | 빠져나가는 길 |
| --- | --- | --- |
| `SENT` ~ `ACTION_TAKEN` (요약) | 포함 | 부서 단위 동작으로 요약이 바뀜, 재요청(새 회차, `ACTION_TAKEN` 제외), `ACTION_TAKEN`이면 후속 확인 계획 |
| `REJECTED`, 반려 확인 전 부서 있음 | 포함 | 반려 확인(모두 확인되면 반려 종료), 부서 단위 새 근거 재요청 |
| 반려 종료 (`REJECTED`, 모두 반려 확인) | 제외 | 재요청(새 회차)만: 새 해결 기록 3건 후보 또는 새 근거 |
| `FOLLOW_UP` | 포함 | `COMPLETED`, 재발 재개(새 회차) |
| `COMPLETED` | 제외 | 재발 재개(새 회차)만 |

- 요청 상태가 `ACTION_TAKEN`이어도 반려 확인 전인 `REJECTED` 부서가 있으면 `FOLLOW_UP` 전이는 409이며, 화면은 `cs_agent` 할 일로 "반려 확인"을 보여 준다.
- 요청 상태 하나에 담기지 않는 정보는 화면에 부서별 상태와 `cs_agent` 할 일로 보여 준다: `INFO_REQUESTED` → 자료 보완 후 재전달, 반려 확인 전 `REJECTED` → 반려 확인 또는 새 근거 재요청, 회신 기한 경과 → 그 부서에 회신 재촉, 후속 확인 조건 충족 → 후속 확인 계획.
- 예: 품질 `ADOPTED`, 설계 `REJECTED`, 물류 `INFO_REQUESTED` → 요청 상태 `ADOPTED`. 품질은 바로 조치를 등록할 수 있고, `cs_agent` 할 일은 설계 반려 확인과 물류 자료 보완이다. 이후 재발로 품질만 다시 부르면 품질은 `SENT`, 설계(반려 확인)·물류는 이월되어 요청 상태는 다시 요약된다.

### 2.3 두 상태의 독립성

| 문의 상태 | 개선요청 상태 | 허용 | 설명 |
| --- | --- | --- | --- |
| `CLOSED` | `INFO_REQUESTED`, `SENT`, `FOLLOW_UP` | 가능 | 고객 문의가 끝나도 개선 검토는 계속된다 |
| `IN_REVIEW`, `ANSWERED` | `COMPLETED` | 가능 | 과거 조치가 완료된 고장에 새 문의가 들어올 수 있다. 재발 후보 판단은 별도 |
| `CLOSED` | (없음) | 가능 | 모든 문의가 개선요청을 만들지 않는다 |
| 어떤 상태든 | `ACTION_TAKEN` / `FOLLOW_UP` / `COMPLETED` → 새 회차(재발 재개) | 가능 | 재발 재개는 문의 상태와 무관 |

화면에서 두 상태를 한 배지로 합치지 않고 문의 상세(F03·F04)와 개선요청(F05)에 각각 표시한다.

### 3.1 상태 두 축과 요구 상태

| 구분 | 값 | 뜻 |
| --- | --- | --- |
| 산출물 상태 `output_status` | `INTAKE` 접수 · `ANALYZING` 분석 중 · `REVIEW_DRAFT` 검토본 작성 | 처리 작업 접수와 함께 `ANALYZING`, 검토본 저장으로 `REVIEW_DRAFT`. 입찰 통과·수주와 별개 |
| 판단 상태 `judgement_status` | `NEEDS_REVIEW` 검토 필요 · `CONDITION_CHECK` 조건 확인 필요 · `OWNER_CONFIRMED` 담당자 확인 | 프로젝트 단위 사람 판단 요약. 검토본 저장(아래 3.2)이 성공할 때 미해결 필수 조건이 하나도 없으면 `OWNER_CONFIRMED`, 남아 있으면 `CONDITION_CHECK` 유지. 저장 성공 여부와 별개의 축 |
| 요구 상태 `status` | `EVIDENCE_FOUND` · `CONDITIONAL` · `SPEC_GAP` · `INSUFFICIENT_EVIDENCE` | 자료 없음은 판단 근거 부족이지 미충족이 아님 |
| 요구 성격 `necessity` | `MANDATORY` · `PREFERRED` · `CONDITION_BOUND` · `UNDETERMINED` | 원문이 구분하지 않으면 `UNDETERMINED` |
| 변경 제안 `origin` / `status` | `web` · `customer_reply` · `pdf_annot` / `PENDING` · `APPROVED` · `REJECTED` | 세 입구가 같은 승인 대기 목록을 쓴다 |
| 고객 질문 `status` | `OPEN` · `REPLIED` | 작성 시 `OPEN`, 회신 기록으로 `REPLIED` |

### 3.2 전이 규칙

- 요구의 상태·성격·조건·사유를 바꾸는 입력은 웹 수정·고객 회신·(A12) PDF 메모 모두 변경 제안으로 들어오고, 승인된 제안만 요구의 새 판본이 되며 연결된 비교·보완·초안 문장에 `needs_rereview=true`가 붙는다. 사람의 결정 자체인 보완 경로·후보 선택과 초안 문장 수정만 바로 새 판본(`human_input`)이다.
- 재실행은 손대지 않은 요구만 `ai_draft` 새 판본으로 덮어쓰고, 손댄 요구(최신 판본 `human_input` 또는 승인된 제안 있음)는 차이를 제안(`origin=web`, 사유 "재실행")으로 남긴다.
- 쓰기 요청은 읽을 때 받은 `version`을 본문에 보내고 최신과 다르면 409 `TFT_VERSION_CONFLICT`다(C/S 조건 비교와 같은 방식). 상태를 만드는 POST는 `Idempotency-Key` 8~128자 필수. 모든 판본은 추가만 한다.
- 처리 작업은 플랫폼 `runtime.jobs`(`owner=tft`)를 재사용하고 상태·SSE는 플랫폼 작업 경로를 쓴다. worker 연결 전 접수는 503 `TFT_PROCESSOR_NOT_CONNECTED`, 진행 중 작업이 있으면 409 `TFT_JOB_IN_PROGRESS`.
- 검토본 저장 조건(명세 §4.9): 필수 요구 전부가 상태·근거 또는 다음 행동(`unresolved`+`next_owner_field`)을 가지고, 초안 문장의 `evidence_missing=0`·`needs_rereview=0`. 어기면 422 `TFT_DRAFT_INCOMPLETE`(요구·문장 ID 목록). 통과하면 `review_version`을 기록하고 `output_status=REVIEW_DRAFT`가 되며, 판단 상태는 3.1대로 정한다. 미해결 필수 조건이 다음 행동과 함께 남아 있어도 저장은 성공한다. 금지된 보완 경로 선택은 409 `TFT_INVALID_TRANSITION`, 제외 후보 선택은 422 `TFT_CANDIDATE_EXCLUDED`.
- 시연에서는 자기 제안을 자기가 승인할 수 있다. 감사 행에는 항상 `proposer`와 `approver`를 남긴다.

### 3.3 담당·책임자 지정 이력

| 항목 | 규칙 |
| --- | --- |
| 지정·변경 주체 | 해당 프로젝트를 **관리 대상으로 가진 `manager`만** (`PATCH /projects/{uuid}/assignment`) |
| 대상 | 담당 `sales`(`sales_user_id`)와 책임자(`responsible_user_id`). 책임자 후보는 그 프로젝트의 담당 `sales` 또는 그 프로젝트를 관리하는 `manager`의 로그인 사용자 ID(명세 §4.1) |

## 5. dept/project별 화면 행동

화면 번호는 WBS(F01~F13)를 따른다. 각 화면은 **서버가 허용한 범위**만 표시하고, 서버 검사는 UI 숨김과 무관하게 수행한다. 메뉴·버튼 숨김은 사용성 조치이지 권한 통제가 아니다.

### 5.1 공통 상태 UI (F01, KAN-129와 연결)

| 응답 | 화면 처리 | 메뉴·버튼 |
| --- | --- | --- |
| 401 `AUTH_REQUIRED` / `SESSION_EXPIRED` | "로그인 필요" 공통 화면으로 이동. 개발 모드에서는 계정 선택 화면. 자동 재로그인·모의 응답 전환 없음 | 업무 메뉴 비노출 |
| 403 `FORBIDDEN` / `APPROVAL_REQUIRED` | 현재 화면 안에서 "권한 없음" 안내. 객체 정보는 서버가 준 범위까지만 표시 | 해당 행동 버튼 비활성화 + 이유 표시 |
| 404 `NOT_FOUND` | "없거나 접근할 수 없음" 공통 화면. 범위 밖 객체와 실제 없는 객체를 구분해 표시하지 않음 | 목록으로 돌아가기 |
| 409 `INVALID_TRANSITION` | "상태가 바뀌어 처리할 수 없음" 안내 후 객체 재조회 | 전이 버튼을 현재 상태 기준으로 다시 계산 |
| 412 / 428 | "다른 사용자가 수정함" 안내 후 재조회. 사용자의 입력은 버리지 않고 재확인 | 저장 버튼 재활성화 |
| 501 `NOT_IMPLEMENTED` | "아직 연결되지 않은 기능" 안내. 모의 응답으로 자동 전환하지 않음 | — |

역할 자체가 접근할 수 없는 메뉴(예: `sales`에게 C/S 메뉴, `cs_agent`에게 제안 지원 메뉴)는 비노출한다. 역할은 되지만 범위 밖인 객체는 목록에 나타나지 않으므로 보통 404를 만나지 않는다. 직접 URL 접근 시에만 404 화면이 뜬다. 현재 앱의 `*` 경로 "페이지를 찾을 수 없습니다"는 라우트 없음이며 404 객체 화면과 구분한다.

## 6. 개발 모드(시연 계정 선택)의 적용 범위

| 항목 | 규칙 |
| --- | --- |
| 활성 조건 | 로컬 `DEV_AUTH_ENABLED=true`에서만 `/api/v1/platform/dev/*` 제공([플랫폼 인증](auth.md)) |
| 대체하는 것 | Microsoft 로그인만. 세션 발급 후의 역할·범위·상태 검사는 **production과 동일**하게 적용한다 |
| 대체하지 않는 것 | 역할 자동 부여, 범위 우회, 상태 전이 생략, 책임자 자동 지정. 클라이언트가 보낸 역할 헤더·`user_id` 외 필드는 거부 |
| 시연 계정 4개 | `cs_agent`(부서 없음), `dept_staff`(`TS_TRF`), `sales`(부서 없음), `manager`(부서 없음, 관리 대상 부서 `GCS_L1`). `manager`는 C/S 문의·개선요청 담당자 재배정을 시연할 수 있다. 책임자 지정·재배정 시연에는 관리 대상 프로젝트 fixture가 필요하다(확인 필요 3) |
| 미확정·서버 밖 행동 | 평가 실행 등 미확정 항목과 계정 관리는 개발 모드에서도 역할 검사로 열지 않는다. 로컬 확인은 `scripts/`·`eval.smoke` 등 서버 밖 명령으로 한다 |
| 모의 응답 | 로컬 프론트의 모의 응답 모드는 합성 예시만 반환하며 권한 검사를 대신하지 않는다. 실제 API 실패 시 자동 전환 금지 |
| production 금지 | `environment=production`이면 개발 인증 라우트를 등록하지 않고 관련 설정이 켜진 구성은 시작 시 거부한다. 개발 쿠키·임의 역할 헤더·모의 응답을 인증이나 데이터로 받지 않는다. 세 앱과 워커 모두 같은 환경 값을 검증한다 |
