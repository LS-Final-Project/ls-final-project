# 화면·업무 상태 전이·권한 행렬 (KAN-57)

기준일 2026-10-23. 담당 김종하, 검토 오새결. 이 문서는 KAN-57 "[D05] 화면, 업무 상태 전이, 권한 행렬 정리"의 설계 산출물이다. 역할·범위 모델, C/S와 TFT의 업무 상태 전이, 권한 행렬과 화면별 행동을 정리한다. **설계 합의이며 구현·검증 완료를 뜻하지 않는다.** 실제 검사 코드, 마이그레이션, OpenAPI는 각 기능 티켓(KAN-78·79 사용자·업무 권한, KAN-108 C/S 업무 상태, TFT 기능 티켓)에서 구현한다.

원본 우선순위는 Jira KAN-57 결정(2026-10-21 댓글) → [AGENTS](../../AGENTS.md#인증과-역할) → [아키텍처](../../docs/architecture.md#인증과-사람의-결정) → [데이터 계약](../../docs/data-contract.md) → [API 계약](../../docs/api-contract.md) → 최종 기획서 순이다. 기획서 발췌는 참고이며 저장소 문서와 어긋나면 저장소 문서를 따른다. 역할 이름은 AGENTS의 `cs_agent`, `dept_staff`, `manager`, `sales`를 그대로 사용한다.

이 문서의 상태 이름(영문 enum)은 **제안**이다. 실제 enum은 해당 서비스의 `schemas.py`에 두고 공통 패키지에 넣지 않는다([계약 수정 안내](../README.md)). 표에서 **확정**은 Jira·기존 문서에 결정된 것, **기본값(제안)**은 시연 흐름에 맞춰 이 문서가 제안한 값, **미확정(주체)**은 아직 결정하지 않은 것이다. 미확정 항목은 구현에서 기본 거부한다.

## 1. 역할·범위 모델

권한은 **역할 × 범위(dept/project) × 객체 상태**로 결정한다. 역할만으로 허용하지 않고, 범위만으로 행동을 허용하지 않으며, 범위 안이라도 객체 상태가 허용하지 않는 전이는 거부한다.

### 1.1 로그인 역할 (확정)

| 역할 | 설명 | 필수 속성 |
| --- | --- | --- |
| `cs_agent` | C/S 문의 처리와 개선요청 주관 | 없음 |
| `dept_staff` | 전문부서 담당자. 이관 문의 처리, 개선요청 회신·조치, TFT 후보 추천·검증 | 소속 부서 `dept` 필수. 없으면 로그인 거부(401) |
| `manager` | 주관회사 전체 집계 조회. 관리 대상 부서·프로젝트 안에서 상세 조회와 재배정 | 관리 대상 C/S 부서 목록, 관리 대상 TFT 프로젝트 목록(명시 부여, 기본 없음) |
| `sales` | RFP 등록, 요구·역할 검토, 부서 인력요청 발행, 구성안 준비 | 담당 프로젝트 목록 |

- 사용자 식별은 `tid + oid`다. 이메일은 표시용이다. 등록되지 않은 사용자에게 역할을 자동 부여하지 않는다.
- 한 사용자에게 여러 역할을 줄 수 있다(`identity.user_roles`). 행동 허용은 역할별 조건 중 하나라도 만족하면 되지만 범위 조건은 해당 역할의 범위로 검사한다.
- `manager`라는 이유만으로 상세 조회, 원문·파일 다운로드, 개인 메일함 열람, TFT 확정을 허용하지 않는다. 집계 조회권은 상세 API를 우회하는 근거가 아니다.

### 1.2 범위 (scope)

| 범위 | 정의 | 부여 주체 | 상태 |
| --- | --- | --- | --- |
| 자기 부서 | `dept_staff`의 `users.dept` | 사용자 등록 시 | 확정(필드 존재) |
| 관리 대상 부서 | `manager`에게 명시 부여한 C/S 부서 집합 | 사용자 등록 스크립트(서버 밖) | 확정, 저장 구조 미구현(KAN-78) |
| 관리 대상 프로젝트 | `manager`에게 명시 부여한 TFT 프로젝트 집합 | 사용자 등록 스크립트(서버 밖) | 확정, 저장 구조 미구현(KAN-78) |
| 담당 프로젝트 | `sales`가 담당하는 TFT 프로젝트 | 기본값(제안): RFP를 등록한 `sales`가 담당자로 기록. 추가·변경은 관리 대상 `manager` | 기본값(제안) |
| 요청 부서 | TFT 인력 요청서의 수신 부서. `dept_staff.dept`와 비교 | 요청서 발행 시 `sales`가 지정 | 확정 |
| 수신 부서 | C/S 개선요청의 전달 대상 부서(`proposed_depts`). 여러 부서 가능 | 전달 시 `cs_agent`가 확정 | 확정 |
| 프로젝트 책임자 | `projects.responsible_user_id`. 프로젝트별 속성이며 로그인 역할이 아님 | 관리 대상 `manager`가 해당 프로젝트의 `sales` 또는 `manager` 중에서 지정 | 확정 |

계정 등록·역할 지정·`manager` 관리 범위 부여는 **서버 밖 등록 스크립트(로컬은 seed)로만** 한다(확정 2026-10-23). 등록 값은 사내 관리자가 정한 것으로 가정하며, 실제 도입 시에는 사내 계정 시스템 연동으로 대체한다. 이를 위한 API·화면은 만들지 않으며 어떤 로그인 역할도 다른 사용자의 역할·범위를 바꿀 수 없다.

프로젝트 책임자는 사용자 속성이 아니라 **프로젝트 속성**이다. 같은 사용자가 프로젝트 A의 책임자이면서 프로젝트 B에서는 일반 `sales`일 수 있다. 생성자, 다른 `manager`, 담당 `sales`에게 자동 부여하지 않는다.

### 1.3 검사 순서와 오류 (확정 코드는 [API 계약](../../docs/api-contract.md#오류와-동시-수정) 사용)

| 순서 | 검사 | 실패 응답 |
| --- | --- | --- |
| 1 | 세션 유효성(활성 사용자, 유효 역할, 부서 조건) | 401 `AUTH_REQUIRED` 또는 `SESSION_EXPIRED` |
| 2 | 객체가 사용자의 **조회 범위** 안에 있는가 | 404 `NOT_FOUND` (범위 밖 객체의 존재를 숨김) |
| 3 | 역할·범위가 해당 **행동**을 허용하는가 | 403 `FORBIDDEN`. 승인권자 확인이 더 필요하면 403 `APPROVAL_REQUIRED` |
| 4 | 객체 **상태**가 전이를 허용하는가 | 409 `INVALID_TRANSITION` |
| 5 | 판본 일치(`If-Match`) | 428 `VERSION_REQUIRED` / 412 `VERSION_CONFLICT` (확인 필요 1 참고) |
| 6 | 필수 근거·입력 | 422 `VALIDATION_ERROR`, `EVIDENCE_REQUIRED` |

플랫폼이 세션을 검증하고 사용자 맥락을 내부 요청으로 중계하며, C/S·TFT 서비스는 호출자 인증과 함께 2~6을 **다시** 검사한다. 브라우저가 보낸 역할·사용자 헤더와 `approved=true` 같은 값은 근거로 쓰지 않는다. 조회 가능 범위 안에서는 404 대신 403을 내서 "보이지만 할 수 없음"을 구분한다.

## 2. C/S 업무 상태 전이

C/S에는 **문의(ticket) 상태**와 **개선요청(improvement request) 상태**가 있고 둘은 독립이다. 고객 문의 종결이 개선요청 완료가 아니며, 부서 회신이나 개선요청 완료가 문의 종결을 만들지 않는다(확정). AI 작업 상태(`SUCCEEDED` 등)와 메일 발송 상태(`ACCEPTED`, `UNKNOWN` 등)도 두 업무 상태와 별개이며 자동 전이를 일으키지 않는다.

### 2.1 문의 상태 (기본값 제안, enum은 KAN-108에서 확정)

워크플로우 ①~⑪(기획서 4.1)의 담당자 확인 게이트 ⑥을 중심으로 정리한다. 제공 데이터의 `status`는 `cs.ticket_source_records`의 사후 기록이며 운영 상태와 같은 칸을 쓰지 않는다([C/S 계약](../cs/tickets.md)).

| 상태 | 의미 |
| --- | --- |
| `RECEIVED` | 접수. AI 분석 작업 미완료 또는 미실행 |
| `IN_REVIEW` | 분석 결과·규칙 결과·초안이 있고 담당자 확인 대기(게이트 ⑥). 고객 회신 재투입 후에도 이 상태로 돌아옴 |
| `WAITING_CUSTOMER` | 추가 정보 요청을 발송하고 고객 회신 대기 |
| `ANSWERED` | 답변을 발송하고 고객 회신 또는 종결 판단 대기 |
| `TRANSFERRED` | 전문부서로 이관 확정. 부서 처리 중 |
| `CLOSED` | 종결. 사례 적재 가능 |

| 전이 | 트리거 | 허용 역할 | 범위 조건 | 거부 시 |
| --- | --- | --- | --- | --- |
| `RECEIVED` → `IN_REVIEW` | 분석 작업 완료(시스템) 또는 수동 접수 후 분석 건너뜀 | 시스템 / `cs_agent` | — | — |
| `IN_REVIEW` → `WAITING_CUSTOMER` | 추가 정보 요청 발송 승인 | `cs_agent` | 문의 조회 범위 | 403 / 409 |
| `IN_REVIEW` → `ANSWERED` | 답변 발송 승인(초안 수정 포함) | `cs_agent` | 문의 조회 범위 | 403 / 409 |
| `IN_REVIEW` → `TRANSFERRED` | 이관 확정(대상 부서는 규칙 제안을 사람이 확정) | `cs_agent` | 문의 조회 범위 | 403 / 409 |
| `WAITING_CUSTOMER`, `ANSWERED` → `IN_REVIEW` | 고객 회신 재투입(같은 문의에 연결, 재분석) | 시스템(메일 수신) / `cs_agent`(수동 연결) | — | — |
| `TRANSFERRED` → `IN_REVIEW` | 부서 처리 결과·회신 내용 등록. 문의는 `IN_REVIEW`로 돌아가고 `cs_agent`가 고객 발송 또는 종결을 판단 | `dept_staff` | **자기 부서로 이관된 문의** | 403 / 409 |
| `ANSWERED` → `CLOSED` | 종결 확정 | `cs_agent` | 문의 조회 범위 | 403 / 409 |
| `IN_REVIEW` → `CLOSED` | 종결 확정. **부서 처리 결과가 등록됐거나 이 문의에 고객 발송 완료 이력이 있을 때만** 허용. 둘 다 없으면 409 | `cs_agent` | 문의 조회 범위 | 403 / 409 |
| `CLOSED` → `IN_REVIEW` | 고객 회신 재투입으로 재개 | 시스템 / `cs_agent` | — | — |
| 담당자 재배정(상태 변경 없음) | 문의의 담당 `cs_agent` 변경 | `manager` | 관리 대상 부서에 배정·이관된 문의 | 403 |

종결 조건(기본값 제안): 종결은 `ANSWERED`에서, 또는 `IN_REVIEW`에서 부서 처리 결과가 등록됐거나 고객 발송 완료 이력이 있을 때만 허용한다(`TRANSFERRED`에서는 부서 결과 등록으로 `IN_REVIEW`를 거친 뒤 종결한다). 추가로 발송 결과가 `UNKNOWN`인 발송 의도가 없어야 하며, `cs_agent`가 명시적으로 종결을 확정한다. AI 작업 완료, SLA 만료, 부서 회신만으로 자동 종결하지 않는다. 사례 적재(⑧)와 고객 이력 확정값 저장(⑨)은 `CLOSED` 상태에서만 허용하며 종결 후 개선요청은 계속 진행할 수 있다.

고객 발송 주체는 `cs_agent`로 통일한다(기본값 제안). `dept_staff`는 처리 결과와 회신 내용을 등록하고 고객 발송은 `cs_agent`가 확인한다. RMA 번호·방문일·보증 승인은 AI가 생성하지 않으며 사람이 입력한 값만 발송 본문에 들어간다(확정).

### 2.2 개선요청 상태 (기획서 4.4 기반, 확정)

| 상태 | 의미 |
| --- | --- |
| `DRAFT` | 초안. 후보 기준(90일 내 서로 다른 고객 3곳 등) 충족으로 시스템이 생성하거나 `cs_agent`가 수동 생성 |
| `REVIEWED` | `cs_agent` 검토 완료. 전달 대상 부서 확정 |
| `SENT` | 부서에 전달(메일 발송 승인 완료). 재전달·재요청·재개도 이 상태로 돌아옴 |
| `ACKNOWLEDGED` | 수신 부서가 수신 확인 |
| `ADOPTED` | 채택 |
| `INFO_REQUESTED` | 추가 정보 대기. `cs_agent`가 자료 취합·재검토 주관. 문의가 종결돼도 유지 |
| `REJECTED` | 반려. 사유 필수 |
| `ACTION_TAKEN` | 실제 조치 등록(조치 내용·적용 대상·실제 적용일·근거) |
| `FOLLOW_UP` | 사전에 정한 후속 확인(대상·방법·기간) 진행 |
| `COMPLETED` | 사람의 완료 판단. 완료 후에도 추가 발생 감시 |

| 전이 | 트리거 | 허용 역할 | 범위 조건 | 거부 시 |
| --- | --- | --- | --- | --- |
| (생성) → `DRAFT` | 후보 기준 충족(시스템) / 수동 생성 | 시스템 / `cs_agent` | — | — |
| `DRAFT` → `REVIEWED` | 검토 완료, `cs_owner`·`reviewed_by` 기록, 제안 부서 수정 | `cs_agent` | — | 403 / 409 |
| `REVIEWED` → `SENT` | 전달(메일 발송 승인, `sent_at`) | `cs_agent` | — | 403 / 409 |
| `SENT` → `ACKNOWLEDGED` | 수신 확인(**부서별 상태**, 2.2.1) | `dept_staff` | **수신 부서** | 403 / 409 |
| `ACKNOWLEDGED` → `ADOPTED` / `INFO_REQUESTED` / `REJECTED` | 부서 회신(`dept_replies.reply_type`, 부서별 상태). 반려는 사유 필수 | `dept_staff` | 수신 부서 | 403 / 409 / 422 |
| `INFO_REQUESTED` → `SENT` | 자료 보완 후 그 부서에 재전달(새 판본, 부서별 상태) | `cs_agent` | — | 403 / 409 |
| `REJECTED` → `SENT` | 반려 사유와 다른 새 근거로 그 부서에 재요청(새 판본, 부서별 상태) | `cs_agent` | — | 403 / 409 / 422 `EVIDENCE_REQUIRED` |
| 반려 확인(부서별 상태 변경 없음) | 반려 사유를 확인하고 재요청하지 않음(`rejection_reviewed_by`·`_at` 기록) | `cs_agent` | — | 403 / 409 |
| `SENT`, `ACKNOWLEDGED`, `ADOPTED` → `SENT` | 재요청: 직전 전달 이후 새 해결 기록 3건마다 후보 → `cs_agent` 검토 후 재전달 | 시스템(후보) / `cs_agent`(전달) | — | 403 / 409 |
| `ADOPTED` → `ACTION_TAKEN` | 조치 등록(`action`, `action_scope`, `action_date`, `action_evidence`). **그 부서의 상태가 `ADOPTED`일 때** 허용하며 다른 부서의 회신을 기다리지 않는다 | `dept_staff` | 수신 부서 | 403 / 409 / 422 |
| `ACTION_TAKEN` → `FOLLOW_UP` | 후속 확인 계획(`followup_plan`) 확정. 모든 수신 부서가 `ACTION_TAKEN`이거나 반려 확인된 `REJECTED`이고 `ACTION_TAKEN`이 1개 이상일 때만. 아니면 409 | `cs_agent` (부서와 협의) | — | 403 / 409 / 422 |
| `FOLLOW_UP` → `COMPLETED` | `followup_result` 기록 후 완료 판단(`completed_by`, `completed_at`) | `cs_agent` | — | 403 / 409 |
| `ACTION_TAKEN`, `FOLLOW_UP`, `COMPLETED` → `SENT` | 재발 재개: 조치 적용 장비에서 1건이라도 재발이 확인되면 재발 후보 → `cs_agent` 검토 후 같은 요청을 다시 열어 전달(새 판본). 조치 전 장비의 발생은 재발이 아니며 재요청 집계로 간다 | 시스템(후보) / `cs_agent`(재개) | — | 403 / 409 |
| 담당자 재배정(`cs_owner` 변경) | 상태 변경 없음 | `manager` | 관리 대상 부서가 수신·제안 부서에 포함된 요청 | 403 |

- 완료 판단은 `cs_agent`(C/S 주관)가 한다(기본값 제안). 부서 회신·조치 등록만으로 `COMPLETED`가 되지 않는다. 재발 재개는 조치 이후 상태(`ACTION_TAKEN`, `FOLLOW_UP`, `COMPLETED`) 어디서든 가능하며 재개 시 진행 중이던 후속 확인 기록은 보존한다. 조치 전 장비의 발생은 재발과 구분해 따로 집계한다.
- 여러 부서에 전달한 요청은 부서마다 상태를 따로 두고, 요청 상태는 시스템이 요약한다(2.2.1, 확정 2026-10-23). `cs_agent`가 요청 상태를 직접 고르지 않는다.
- `manager`는 개선요청 진행 현황을 집계로 보고, 관리 대상 부서 관련 요청만 상세 조회한다. 상태 전이는 하지 않는다.

### 2.2.1 여러 수신 부서: 부서별 상태와 요청 상태 요약 (확정 2026-10-23)

수신 부서마다 `SENT → ACKNOWLEDGED → ADOPTED / INFO_REQUESTED / REJECTED → (ADOPTED이면) ACTION_TAKEN`을 독립적으로 진행한다. 부서별 현재 상태는 요청-부서 단위 행에 두고(이름은 C/S 개선요청 구현에서 정함), 회신 이력은 `dept_replies`에 남긴다. 반려는 "이 부서가 맡을 일이 아님"을 뜻하며 그 부서만 진행에서 빠진다. 부서 질문(`QA:`, `SCM:` 등)은 해당 부서에 묶는다.

요청 상태 요약 규칙(`SENT` 이후 `FOLLOW_UP` 전까지, 위에서부터 처음 맞는 것):

| 순서 | 부서별 상태 조건 | 요청 상태 |
| --- | --- | --- |
| 1 | 모든 부서가 `REJECTED` | `REJECTED` |
| 2 | `ADOPTED`·`ACTION_TAKEN` 부서가 1개 이상이고 그 부서가 모두 `ACTION_TAKEN` | `ACTION_TAKEN` |
| 3 | `ADOPTED`·`ACTION_TAKEN` 부서가 1개 이상 | `ADOPTED` |
| 4 | `INFO_REQUESTED` 부서가 1개 이상 | `INFO_REQUESTED` |
| 5 | `ACKNOWLEDGED` 부서가 1개 이상 | `ACKNOWLEDGED` |
| 6 | 그 외 | `SENT` |

- `FOLLOW_UP`·`COMPLETED`는 요약이 아니라 `cs_agent`의 전이로만 바뀐다. 재요청·재발 재개로 다시 전달하면 대상 부서의 상태가 `SENT`로 돌아가고 요약을 다시 계산한다.
- 요청 상태 하나에 담기지 않는 정보는 화면에 부서별 상태와 `cs_agent` 할 일로 보여 준다: `INFO_REQUESTED` → 자료 보완 후 재전달, 반려 확인 전 `REJECTED` → 반려 확인 또는 새 근거 재요청, 회신 기한 경과 → 재요청, 후속 확인 조건 충족 → 후속 확인 계획.
- 예: 품질 `ADOPTED`, 설계 `REJECTED`, 물류 `INFO_REQUESTED` → 요청 상태 `ADOPTED`. 품질은 바로 조치를 등록할 수 있고, `cs_agent` 할 일은 설계 반려 확인과 물류 자료 보완이다.

### 2.3 두 상태의 독립성

| 문의 상태 | 개선요청 상태 | 허용 | 설명 |
| --- | --- | --- | --- |
| `CLOSED` | `INFO_REQUESTED`, `SENT`, `FOLLOW_UP` | 가능 | 고객 문의가 끝나도 개선 검토는 계속된다 |
| `IN_REVIEW`, `ANSWERED` | `COMPLETED` | 가능 | 과거 조치가 완료된 고장에 새 문의가 들어올 수 있다. 재발 후보 판단은 별도 |
| `CLOSED` | (없음) | 가능 | 모든 문의가 개선요청을 만들지 않는다 |
| 어떤 상태든 | `ACTION_TAKEN` / `FOLLOW_UP` / `COMPLETED` → `SENT` | 가능 | 재발 재개는 문의 상태와 무관 |

화면에서 두 상태를 한 배지로 합치지 않고 문의 상세(F03·F04)와 개선요청(F05)에 각각 표시한다.

## 3. TFT 업무 상태 전이

TFT는 **역할 요청 상태**, **후보별 추천 기록·검증 기록**, **구성안 판본과 책임자 확정**, **책임자 지정·변경 이력**을 서로 다른 기록으로 둔다. 추천·검증·확정을 수행하는 사람과 범위를 분리하되, 추천과 검증은 같은 부서 담당자가 모두 할 수 있다(확정). 이 분리를 위해 별도 로그인 역할이나 중간 승인자를 두지 않는다.

### 3.1 역할 요청 상태 (기획서 4.5, 확정) — 역할·부서 요청서 단위

| 상태 | 의미 |
| --- | --- |
| `DRAFTING` | 작성 중. RFP 근거·과업·필수/우대 역량·요청 부서·투입 조건 편집 |
| `PUBLISHED` | 공지. 요청 부서에 서비스 내 공지(메일·Teams 알림은 후속) |
| `RECOMMENDING` | 후보 추천 접수. 요청 부서가 후보와 근거 입력 |
| `DEPT_VERIFYING` | 부서 검증. 유사 경험·필수·우대·가용성 항목별 확인 |
| `COMPARING` | 후보 비교. 역할별 비교·공백·투입 충돌 표시 |
| `PLAN_REVIEW` | 구성안 검토. 책임자가 확정 또는 보완 요청 |
| `CONFIRMED` | 확정. 해당 역할의 후보·참여 조건·검증 근거·책임자 확인이 모두 기록됨 |

| 전이 | 트리거 | 허용 역할 | 범위 조건 | 거부 시 |
| --- | --- | --- | --- | --- |
| (생성) → `DRAFTING` | RFP 등록·분석 후 역할 수요 도출, 요청서 작성 시작 | `sales` | **담당 프로젝트** | 403 |
| `DRAFTING` → `PUBLISHED` | 요청서 발행(담당 `sales` 검토 후, 중간 승인 없음) | `sales` | 담당 프로젝트 | 403 / 409 / 422(필수 항목 누락) |
| `PUBLISHED` → `RECOMMENDING` | 요청 부서의 첫 후보 추천 등록 | `dept_staff` | **요청 부서** | 403 / 409 |
| `RECOMMENDING` → `DEPT_VERIFYING` | 추천 후보에 대한 검증 기록 시작 | `dept_staff` | 요청 부서 | 403 / 409 |
| `RECOMMENDING`(추천 없음·정보 부족) | 담당 부서·다음 행동·회신 기한 기록. 상태 유지 | `sales` / `dept_staff` | 담당 프로젝트 / 요청 부서 | 403 |
| `DEPT_VERIFYING` → `COMPARING` | 부서가 검증 결과 제출(항목별 확인·추가 확인·미충족) | `dept_staff` | 요청 부서 | 403 / 409 |
| `COMPARING` → `RECOMMENDING` | 추가 후보·보강 요청 | `sales` 또는 현재 책임자 | 담당 프로젝트 / 해당 프로젝트 책임자 | 403 / 409 |
| `COMPARING` → `PLAN_REVIEW` | 구성안 판본 작성(역할별 제안 후보·이유·남은 조건) | `sales` | 담당 프로젝트 | 403 / 409 |
| `PLAN_REVIEW` → `RECOMMENDING` / `COMPARING` | 책임자 보완 요청(사유 기록) | **현재 프로젝트 책임자** | 해당 프로젝트 | 403 / 409 |
| `PLAN_REVIEW` → `CONFIRMED` | 최종 확정(확정자 ID·대상 구성안 판본 기록) | **현재 프로젝트 책임자만** | 해당 프로젝트 | 책임자 아님 403 `FORBIDDEN` / 책임자 미지정 409 `INVALID_TRANSITION` / 검증 미완료 역할 422 `EVIDENCE_REQUIRED` |
| `CONFIRMED` → `COMPARING` | RFP 범위·가용성 변경 시 재검토(이전 구성안 보존, 새 판본) | `sales` 또는 현재 책임자 | 담당 프로젝트 / 해당 프로젝트 | 403 / 409 |
| 담당자 재배정(상태 변경 없음) | 담당 `sales`·요청 부서 담당자 변경 | `manager` | **관리 대상 프로젝트** | 403 |

- 일부 역할의 `CONFIRMED`를 프로젝트 전체 구성 완료로 표시하지 않는다. 구성 완료는 필수 역할 모두가 `CONFIRMED`이고 공백 역할에 담당자·후속 요청 기록이 있는 상태다.
- 필수 역량 또는 참여 가능성이 "추가 확인"이면 구성안에서 **보강 필요**이며 확정 대상이 아니다. 자료가 없는 것은 "추가 확인"이지 "미충족"이 아니다.
- 요청 주체는 상태로 나뉜다. **보강 요청·추가 후보 요청**(`COMPARING` 이하)은 담당 `sales` 또는 현재 책임자가, **구성안 보완 요청**(`PLAN_REVIEW`)은 현재 책임자만 한다. `sales`는 자신이 책임자로 지정된 프로젝트에서만 구성안 보완 요청을 할 수 있다. 4.2 행렬과 5.5~5.7 화면 표도 이 구분을 따른다.

### 3.2 후보별 추천 기록과 검증 기록 (확정)

| 기록 | 필드 | 작성 | 범위 |
| --- | --- | --- | --- |
| 추천 기록 | 역할–후보 연결, 추천 이유, 추천자 ID, 추천 시각, 소속, 제출 경험·역량·가용성 입력 | `dept_staff` | 요청 부서. 후보 인력 ID는 로그인 사용자 ID와 별개 |
| 검증 기록 | 항목(유사 경험 / 필수 역량 / 우대 역량 / 가용성) × 결과(`CONFIRMED` 확인 / `NEEDS_CHECK` 추가 확인 / `NOT_MET` 미충족), 검증자 ID, 확인 시각, 근거 | `dept_staff` | 요청 부서. 추천자와 같은 사람 가능 |
| 가용성 확인 완료 조건 | 대상 기간, 투입률, 확인 주체, 확인 시각, 근거가 모두 있을 때만 `CONFIRMED` | — | [데이터 계약](../../docs/data-contract.md#업무별-데이터와-결정) |

추천 기록과 검증 기록은 같은 사람이 작성해도 **별도 행**으로 보존하며 화면에서 추천자·검증자를 각각 표시한다. 같은 사람이 추천·검증한 경우 독립 교차 검증으로 설명하지 않는다. 한 후보를 여러 역할에 추천하면 역할별 적합성과 투입 충돌을 별도 표시한다.

### 3.3 구성안 판본과 책임자 확정 (확정)

| 항목 | 규칙 |
| --- | --- |
| 구성안 판본 | `version` 양의 정수. 역할별 후보·상태(확정 / 보강 필요 / 공백)·추천 이유·남은 조건. 작성자 `sales`, 작성 시각 |
| 확정 기록 | 확정자 ID(현재 책임자), 대상 구성안 판본, 시각. 확정 후 판본을 수정하지 않고 새 판본을 만든다 |
| 보완 요청 기록 | 요청자(책임자), 대상 역할, 사유, 다음 담당자, 시각 |
| 책임자 미지정 | 확정 요청을 409 `INVALID_TRANSITION`으로 거부. 화면은 확정 버튼을 비활성화하고 "책임자 미지정" 안내 |
| 책임자 변경 후 | 이전 책임자의 확정·보완 요청 기록은 보존. 이후 확정은 현재 책임자만 검사 |

### 3.4 책임자 지정·변경 이력 (확정)

| 항목 | 규칙 |
| --- | --- |
| 지정·변경 주체 | 해당 프로젝트를 **관리 대상으로 가진 `manager`만** |
| 지정 후보 | 해당 프로젝트의 담당 `sales` 또는 해당 프로젝트를 관리하는 `manager`. 로그인 가능한 내부 사용자 ID만. 후보 인력 ID·이메일 사용 금지 |
| 자동 부여 | 없음. 프로젝트 생성자, 다른 `manager`, 담당 `sales`에게 자동 지정하지 않음 |
| 이력 필드 | 프로젝트 ID, 변경자 ID, 이전 책임자 ID(없으면 null), 신규 책임자 ID, 사유, 변경 시각 |
| 거부 | 관리 대상 밖 프로젝트 404 `NOT_FOUND`, 관리 `manager`가 아님 403 `FORBIDDEN`, 후보 조건 불일치 422 `VALIDATION_ERROR` |
| 자기 자신 지정 허용 여부 | 미확정(팀). 별도 결정 전 추가 제약을 넣지 않는다 |

## 4. 권한 행렬

O = 허용, X = 거부, △ = 조건부. 괄호는 범위 조건. "책임자" 열은 로그인 역할이 아니라 **해당 프로젝트의 현재 책임자**인 사용자에게 추가로 열리는 행동이다(책임자가 아닌 행동은 자기 로그인 역할 열을 따른다). `manager` 상세 조회의 "전체"는 집계만이다.

## 5. dept/project별 화면 행동

화면 번호는 WBS(F01~F13)를 따른다. 각 화면은 **서버가 허용한 범위**만 표시하고, 서버 검사는 UI 숨김과 무관하게 수행한다. 메뉴·버튼 숨김은 사용성 조치이지 권한 통제가 아니다.

### 5.1 공통 상태 UI (F01, KAN-129와 연결)

| 응답 | 화면 처리 | 메뉴·버튼 |
| --- | --- | --- |
| 401 `AUTH_REQUIRED` / `SESSION_EXPIRED` | "로그인 필요" 공통 화면으로 이동. 개발 모드에서는 계정 선택 화면. 자동 재로그인·모의 응답 전환 없음 | 업무 메뉴 비노출 |
| 403 `FORBIDDEN` / `APPROVAL_REQUIRED` | 현재 화면 안에서 "권한 없음" 안내. 객체 정보는 서버가 준 범위까지만 표시 | 해당 행동 버튼 비활성화 + 이유 표시 |
| 404 `NOT_FOUND` | "없거나 접근할 수 없음" 공통 화면. 범위 밖 객체와 실제 없는 객체를 구분해 표시하지 않음 | 목록으로 돌아가기 |
| 409 `INVALID_TRANSITION` | "상태가 바뀌어 처리할 수 없음" 안내 후 객체 재조회 | 전이 버튼을 현재 상태 기준으로 다시 계산 |
| 412 / 428 | "다른 사용자가 수정함" 안내 후 재조회. 사용자의 입력은 버리지 않고 재확인 | 저장 버튼 재활성화 |
| 501 `NOT_IMPLEMENTED` | "아직 연결되지 않은 기능" 안내. 모의 응답으로 자동 전환하지 않음 | — |

역할 자체가 접근할 수 없는 메뉴(예: `sales`에게 C/S 메뉴, `cs_agent`에게 TFT 메뉴)는 비노출한다. 역할은 되지만 범위 밖인 객체는 목록에 나타나지 않으므로 보통 404를 만나지 않는다. 직접 URL 접근 시에만 404 화면이 뜬다. 현재 앱의 `*` 경로 "페이지를 찾을 수 없습니다"는 라우트 없음이며 404 객체 화면과 구분한다.

평가 결과에는 `data_origin`·`derivation_kind`를 표시하고 test 597건의 사용 이력을 함께 보여 준다([평가 명세](../../docs/evaluation.md)). 합격선 수치와 실제 측정값을 같은 칸에 섞지 않는다.

### 5.9 고객 이력·관리자 현황 (F13)

| 역할 | 보이는 것 | 할 수 있는 것 | 숨김·비활성 |
| --- | --- | --- | --- |
| `cs_agent` | 조회 가능한 문의의 고객 이력 프로필(담당자 확정값) | 확정값 저장(`CLOSED` 문의 기준) | 관리자 집계 비노출 |
| `manager` | 주관회사 전체의 처리량·지연·진행 집계, 직원별 대응, 고객별 응대 부담, 개선요청 진행 현황. 관리 대상 부서의 상세 링크 | 상세 링크는 관리 대상 안에서만 이동 | 관리 대상 밖 상세 링크 비활성. 집계에서 원문·파일 다운로드로 직접 이동하는 경로 없음 |
| `dept_staff`, `sales` | — | — | 메뉴 비노출 |

### 5.10 실 API·SSE·권한·상태 통합 (F12)

SSE 구독과 작업 조회도 1.3의 검사 순서를 적용한다. 다른 소유자의 작업은 404, 조회 가능한 업무의 작업이라도 행동 권한이 없는 사용자는 결과 파일 다운로드에서 403이다. 작업 완료 이벤트가 와도 화면은 업무 상태를 서버에서 재조회하며 `SUCCEEDED`를 "발송됨"·"확정됨"으로 표시하지 않는다.

## 6. 개발 모드(시연 계정 선택)의 적용 범위

| 항목 | 규칙 |
| --- | --- |
| 활성 조건 | 로컬 `DEV_AUTH_ENABLED=true`에서만 `/api/v1/platform/dev/*` 제공([플랫폼 인증](auth.md)) |
| 대체하는 것 | Microsoft 로그인만. 세션 발급 후의 역할·범위·상태 검사는 **production과 동일**하게 적용한다 |
| 대체하지 않는 것 | 역할 자동 부여, 범위 우회, 상태 전이 생략, 책임자 자동 지정. 클라이언트가 보낸 역할 헤더·`user_id` 외 필드는 거부 |
| 시연 계정 4개 | `cs_agent`(부서 없음), `dept_staff`(technical), `sales`(부서 없음), `manager`(부서 없음, 관리 범위 없음). 현재 `manager` 계정은 범위가 없으므로 집계만 볼 수 있다. 책임자 지정·재배정 시연에는 관리 대상 프로젝트 fixture가 필요하다(확인 필요 3) |
| 미확정·서버 밖 행동 | 평가 실행 등 미확정 항목과 계정 관리는 개발 모드에서도 역할 검사로 열지 않는다. 로컬 확인은 `scripts/`·`eval.smoke` 등 서버 밖 명령으로 한다 |
| 모의 응답 | 로컬 프론트의 모의 응답 모드는 합성 예시만 반환하며 권한 검사를 대신하지 않는다. 실제 API 실패 시 자동 전환 금지 |
| production 금지 | `environment=production`이면 개발 인증 라우트를 등록하지 않고 관련 설정이 켜진 구성은 시작 시 거부한다. 개발 쿠키·임의 역할 헤더·모의 응답을 인증이나 데이터로 받지 않는다. 세 앱과 워커 모두 같은 환경 값을 검증한다 |

### 7.3 기존 문서와 어긋나 "확인 필요"로 둔 항목

기존 문서는 고치지 않았다. 각 담당 티켓에서 확인한다.

| 번호 | 내용 | 확인 상대 |
| --- | --- | --- |
| 1 | [API 계약](../../docs/api-contract.md)은 판본 충돌을 `If-Match` 기반 412 `VERSION_CONFLICT` / 428 `VERSION_REQUIRED`로 정하는데, [C/S 계약](../cs/tickets.md)의 KAN-102 구현은 본문 `version` 기반 409 `CS_TICKET_VERSION_CONFLICT`다. C/S 계약은 "KAN-56 확정 시 맞춘다"고 적었다. 이 문서는 API 계약 코드를 쓰되 C/S 구현 코드가 유지되면 5.1의 412/428 행에 409를 추가한다 | 김나영(KAN-102·108), KAN-56 |
| 2 | [AGENTS](../../AGENTS.md#인증과-역할)는 `users` 테이블의 단일 `role` 필드를 적었지만 실제 `identity` 마이그레이션(KAN-78)과 [결정 정리](../../docs/decisions.md#로그인과-사용자-권한)는 `user_roles` 다중 역할이다. 이 문서는 다중 역할을 전제로 한다 | 김나영(KAN-78), AGENTS 갱신 |
| 3 | 현재 `identity` 스키마에는 `users.dept`와 `user_roles`만 있고 관리 대상 부서·프로젝트, 담당 `sales`, `responsible_user_id`, 책임자 변경 이력의 저장 구조가 없다. 시연 `manager` 계정도 관리 범위가 없다. 범위 테이블의 소유(identity vs tft)와 시연 fixture가 필요하다 | 김나영(KAN-78·79), 김종하(TFT) |
